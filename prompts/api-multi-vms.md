# Задача: один API фронтенда для разных VMS — анализ и предложение

## Зачем это нужно

Прототип 10 (`index_10_api-server.html`) задал API между интерфейсом конфигуратора и бэкендом: контракт `api/openapi.json`, эталонный набор, тесты. Контракт писался под одну модель объектов — ту, что нарисована в макете: домены, серверы, устройства, папки, хранилища, тома, детекторы, правила, права.

В продукте за бэкендом будут **разные VMS-системы**:
- модели объектов у них похожи, но могут расходиться: где-то нет понятия, где-то оно устроено иначе, где-то названо по-другому;
- в каждой системе можно **заводить новые виды объектов** — со своими настройками и своей топологией: где объект может лежать, что может быть у него дочерним.

Нужно понять, получится ли сохранить для фронтенда **один API** — тот, что вышел из прототипа. Его разрешено править. Главное, чтобы он был **единым** (один контракт и один интерфейс для всех систем) и **гибким** (новый вид объекта в какой-то VMS не требует ни нового контракта, ни нового кода фронтенда, или требует минимум).

Результат — документ с ответом и обоснованным предложением. Это анализ: код и контракт пока не меняются.

## Постановка

- Фронтенд — один для всех систем. Он ходит только в бэкенд конфигуратора.
- Бэкенд стоит перед VMS: переводит API фронтенда в API каждой системы и обратно (адаптеры). Сами VMS фронтенд не видит.
- Модели объектов VMS частично совпадают. Расхождения бывают трёх видов:
  - **нет понятия** — у системы нет доменов, папок, томов или групповых операций;
  - **понятие устроено иначе** — хранилище у камеры, а не у сервера; другие режимы записи; другая вложенность;
  - **понятие есть только у неё** — свои виды устройств и детекторов, свои параметры.
- Новые виды объектов заводятся в самой VMS. У каждого свои настройки (поля, типы, ограничения, значения по умолчанию) и топология (допустимые родители и дети, место в дереве).

Если в этой постановке что-то неясно, — вопросы в конце: задай их до того, как делать выводы.

## Шаг 0. Изучи, что есть

5. `index_10_api-server.html` — где модель зашита в интерфейс. Ищи:

## Шаг 1. Где модель объектов зашита — инвентарь

Составь таблицу: **место → что в нём предполагается о модели → насколько это общее**. Минимум:

- **Перечисления, закрывающие список.** `Device.type`, `subtype`, `recordMode`, `detectorKind`, `archive.kind`, `storage`, коды прав (`dCam`, `dTel`…), события и действия правил. Новый вид объекта в VMS ломает их сразу.
- **Плоская схема `Device`.** Все поля всех видов в одной схеме (`codec`, `smtp`, `gateway`, `norm`…) при `additionalProperties: false` — новое поле означает новый контракт.
- **Топология.** Кто кому родитель (канал → регистратор, детектор и периферия → камера, служба → сервер, том → хранилище) зашита в код сервера и интерфейса, а не приходит данными.
- **Поведение по виду:** какие вкладки у карточки, какие групповые шаги допустимы, что значит «включить», у кого есть запись и детекторы.
- **Общие сущности, которых у какой-то VMS может не быть:** домен, папки, нераспределённые серверы, тома, поиск в сети, каталоги LDAP.
- **Идентификаторы:** UUID сервера конфигуратора и id объекта в VMS — одно ли это и уникально ли между системами.
- **Справочники** (`GET /reference`): что уже приходит с сервера, а что интерфейс знает сам.

Отдельно отметь, **что действительно общее для любой VMS**: идентичность, имя, родитель, домен или площадка, состояние связи, версия, папки, права, — и что относится к конкретной системе.

## Шаг 2. Прогон сценариев через нынешний контракт

Для каждого сценария — выдержит ли нынешний контракт и интерфейс без изменений, и если нет, то что ломается:

1. В VMS «А» завели новый вид объекта — например, радар. У него свои настройки (дальность, сектор, чувствительность), он лежит под сервером или в папке, у него бывают дочерние зоны.
2. У VMS «Б» нет доменов и нераспределённых серверов.
3. У VMS «В» хранилище принадлежит камере, а не серверу, и режимы записи другие (своё перечисление).
4. У VMS «Г» свои виды детекторов со своими параметрами; часть видов работает только на определённых моделях камер.
5. Две VMS за одним бэкендом одновременно, с пересекающимися id объектов — если такое вообще возможно (вопрос ко мне).
6. Новая версия VMS добавила поле в существующий вид объекта.
7. VMS не умеет какую-то операцию: групповую правку, поиск в сети, «Отменить», форматирование тома.
8. Права: новый вид объекта требует своих уровней доступа (как сейчас `cam`, `tel`, `mic`…).
9. Автоматизация: новый вид объекта даёт свои события и действия для правил.

## Шаг 3. Варианты устройства API — сравнение

Опиши варианты и сравни их по единству, гибкости, сложности для фронтенда, сложности для бэкенда-адаптера, проверяемости тестами и качеству интерфейса (UX). Не подгоняй под заранее выбранный ответ. Минимум три:

1. **Фиксированная богатая модель плюс расширения.** Нынешние схемы, к ним «свободный» объект (`ext`, `x-*`) для того, что у системы своё.
2. **Общее ядро плюс описания видов с сервера (метамодель).** У объекта общие поля и `settings`. Сервер отдаёт описания видов объектов (`GET /object-types` или в составе `/reference`):
   - подписи или их ключи, иконка;
   - допустимые родители и дети;
   - возможности — что с объектом можно делать: переименовать, включить, писать в архив, иметь детекторы, групповые шаги;
   - схема настроек (JSON Schema) с подсказками для интерфейса: группы и вкладки, единицы, подписи вариантов, только чтение;
   - правила проверки.
   
   Интерфейс строит карточку и форму по описанию, а для хорошо известных видов, возможно, оставляет свои экраны.
3. **Отдельный API под каждую систему** — и почему он не годится или в чём годится.

Можно добавить свои варианты или сочетания.

## Шаг 4. Предложение

Выбери вариант (или сочетание) и распиши его конкретно, на уровне контракта:

- **Что остаётся** из нынешнего API без изменений, а что меняется — по каждой схеме и операции из шага 1.
- **Наброски схем OpenAPI:** описание вида объекта, объект с `settings`, изменение настроек (как с ним работают версии, `If-Match`, JSON Merge Patch, групповые операции `set`), ошибки проверки с путём к полю.
- **Топология с сервера:** как интерфейс узнаёт, куда можно добавить объект и что может быть у него внутри; как это ложится на дерево, мастер добавления и перенос.
- **Возможности вместо видов:** интерфейс показывает кнопку или вкладку, потому что у объекта есть возможность, а не потому что он «камера».
- **Различия систем:** как бэкенд сообщает, что у системы нет доменов, папок, поиска и т. п., и как интерфейс это показывает.
- **Права и автоматизация:** откуда берутся уровни доступа и события и действия правил для новых видов.
- **Тексты и переводы** подписей видов и полей, которые приходят с сервера.
- **Идентификаторы** при нескольких системах.
- **Развитие контракта:** что считается совместимым изменением, как клиент обращается с незнакомыми полями и видами (сейчас везде `additionalProperties: false`), как версионировать.
- **Проверки:** как меняются эталонный набор (нужен ли набор с двумя системами и с «незнакомым» видом объекта), тесты API, критерии приёмки — например, «объект незнакомого вида показывается, правится и проверяется без нового кода фронтенда».
- **Что это значит для фронтенда** (`api/FRONTEND.md`) и для прототипа: что в интерфейсе станет общим (карточка и форма по схеме), что останется своим, где пострадает UX и как это смягчить.
- **Риски:** формы «по схеме» хуже сделанных руками; проверки в двух местах; производительность; расхождение описаний и данных; сложность адаптеров.
