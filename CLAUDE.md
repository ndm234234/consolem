# Правила работы с макетом

Над репозиторием работают несколько человек, все в ветке `main`, без PR.
Макет смотрят через GitHub Pages: https://ndm234234.github.io/consolem/

## index.html — только согласованное

`index.html` — основной макет. Он работает через API: интерфейс читает и меняет данные запросами к встроенному тестовому серверу (`api/`), своих данных у него нет. API — универсальная модель объектов (с контракта 0.2.0; текущая версия — `info.version` в `api/openapi.json`): виды объектов приходят с сервера (`/kinds`), объекты — одним складом (`/units`, адрес — `uid`), ручные экраны привязаны к профилю вида (`vms.camera/1`…), незнакомый вид показывается формой по схеме. Прежний макет и прежний контракт (`/devices`, `/servers`…) — только в истории git: `git show 47d1310:index.html`, `git show 47d1310:api/openapi.json`; таблица перехода — `api/README.md`, «Ломающие изменения против контракта старого макета». Его меняют **только по явной просьбе**: «в основной», «в index.html», «перенеси в основной» — или по запросу команды VMS (раздел «Запросы команд VMS»).

Любая правка `index.html` — с проверками из `api/TESTS.md`: как минимум `python3 tools/check_api.py`, `python3 tools/check_ui.py` и `python3 tools/check_perf.py --quick` (скорость на large, около 2,5 мин). Новые данные и действия — через контракт `api/openapi.json` и сервер, не константами в HTML; если в контракте их нет — расширь контракт или напиши запрос (раздел «Контракт API»).

`index.html` правим и мы, и altumur. Конфликт при `git pull --rebase` сводит тот, кто пушит вторым: сохрани обе правки, а если они несовместимы — спроси пользователя.

## Всё остальное — в прототип

Любую другую просьбу изменить макет выполняй в файле прототипа, даже если о прототипе ничего не сказано.

- Если в этом разговоре уже есть прототип или пользователь назвал его («в прототипе 03»), продолжай в нём.
- Новый прототип создавай, когда в разговоре его ещё нет или просят явно: «новый прототип», «другой вариант», «сделай два варианта» (тогда два файла, по одному на вариант).
- По умолчанию прототип — копия `index.html`, то есть сразу с API: данные и действия прототипа идут через контракт и встроенный сервер, а не константами. Контракт, сервер и набор `api/fixtures/demo.json` — общее с `index.html`: прототип только расширяет их, по порядку раздела «Контракт API» и с проверками `index.html`; ломающая правка — запрос. Проверка прототипа — `python3 tools/check_ui.py --page <файл>` и `<файл>?selftest`. «На основе прототипа NN» — копия файла NN.
- Порядок создания:
  1. `git pull --rebase`
  2. Номер — следующий после максимального среди `index_NN*.html` (учитывая и `index_01.html`) и номеров в `protos.html`, включая удалённые прототипы: номер удалённого не занимай заново. Имя `index_NN_<тема-латиницей>.html`, например `index_NN_filtry-nad-derevom.html`.
  3. Скопируй исходный файл и закоммить копию **до правок**: `Прототип NN: копия index.html` (или `копия прототипа MM`). Так `git diff` потом покажет только изменения прототипа.
  4. Добавь строку о прототипе в `protos.html`: номер, ссылка, автор (`git config user.name`), что проверяем, статус «обсуждается».
- Прототипы лежат в корне репозитория: в подпапке сломаются относительные пути к `assets/`.
- Чужие прототипы не меняй без явной просьбы. Удаление после переноса в основной — не исключение, а часть этой просьбы (раздел «Перенос в основной»).

## Карта кода

`index.html` и прототипы — больше 30 000 строк. Где что лежит, говорит `tools/outline.py`, а не десяток `grep` и `sed`:

- `python3 tools/outline.py [файл]` — обзор: разделы `// ── … ──` с диапазонами строк, разделы приложения, вкладки карточки по типам объектов и функции, которые их рисуют. Прочитай его один раз за сессию, до первой правки.
- `python3 tools/outline.py [файл] слово…` — где встречаются слова: функции и блоки CSS (от комментария над блоком до следующего) с диапазонами строк. Метка ‹…› — ближайший заголовок раздела выше строки.
- `python3 tools/outline.py [файл] -d имя…` — диапазон функции для `sed -n`.
- Работает и на `api/*.js`: там единицы — функции внутри обёртки `(() => { … })()`, а в большой функции (`create` сервера) — и вложенные. Прямая ссылка на карточку: `файл#node=<id>&tab=<вкладка>`.

Границы функций карта берёт из лексера (глубина скобок; строки, шаблоны, комментарии и регулярные выражения он пропускает), а обзор — из соглашений кода: заголовки разделов `// ── Заголовок ──`, `const ui={…}` в `paint()`, списки вкладок `["id","Подпись"]` в `tabsFor`/`tabsForHand`, проверки вкладок `tab==="id"`. Держи их в новом коде. `check_ui.py` проверяет опоры сам (`outline.py --check`): на `index.html` потеря опоры — отказ, на прототипе — предупреждение. Отказ — значит, код ушёл от соглашений или лексер не понял новый синтаксис: сообщение говорит, что поправить в `tools/outline.py`; после правки запусти `python3 tools/check_outline.py`.

## Публикация

Когда правка готова, сразу закоммить и запушь: `git pull --rebase && git push`. Дай ссылку на Pages, например
`https://ndm234234.github.io/consolem/index_NN_filtry-nad-derevom.html`. Сайт обновляется примерно через минуту.

## Перенос в основной

По просьбе «перенеси из прототипа NN в основной …»:
1. Посмотри изменения: `git log -- <файл>` и `git diff <коммит-копии> HEAD -- <файл>`.
2. Перенеси в `index.html` только то, что попросили, поверх текущего `index.html` (он мог уйти вперёд). Правила интерфейса соблюдай на перенесённых участках, остальное не трогай.
3. Проверки из `api/TESTS.md` (см. раздел про `index.html`). Коммит: `Макет: из прототипа NN — <что>`, плюс запись в `CHANGES.md`.
4. В `protos.html` поставь прототипу статус «принят» (или «частично принят»).
5. Принятое удали — после переноса оно мусор: два файла с одним и тем же расходятся, и непонятно, какой смотреть.
   - Прототип принят целиком — удали файл (`git rm`), в том числе чужой: просьба перенести и есть явная просьба. Строку в `protos.html` оставь: имя файла без ссылки с пометкой «(удалён)», статус «принят: …», как у прототипа 37. Отдельный коммит: `Прототип NN: удалён — перенесён в index.html`.
   - Принят частично — файл оставь: в нём ещё есть то, что не решено. В статусе перечисли, что перенесено. Когда остальное перенесут или отклонят — удали, как выше.
   - Ссылки на удалённый файл в живых документах (`*.md`, `protos.html`, другие прототипы) замени на имя с пометкой «(удалён)»; `CHANGES.md` и ответы на запросы — история, их не трогай. Файл остаётся в git: `git log --all -- <файл>`, затем `git show <коммит>:<файл>`.

## Контракт API (OpenAPI)

`api/openapi.json` — источник истины: если встроенный сервер расходится с контрактом, ошибка в сервере. Контракт ведёт **владелец — joynickray** в этом репозитории (`ndm234234/consolem`). altumur и команды VMS расширяют контракт здесь сами (ниже) или присылают запросы; форк `altumur/consolem` забирает контракт отсюда, а не пушит свой.

**API не меняем втихую.** Контракт, сервер, наборы, `tests/api-*.js` и документы `api/` любой пользователь может расширить сам — по порядку раздела «Правка контракта без владельца» и с уведомлением владельцу. Ломающую правку (снять или переименовать путь, поле, значение; изменить смысл или умолчание) делает только владелец (`git config user.name` — `joynickray`); остальные пишут на неё запрос. Владелец может отклонить любую правку в ответе на уведомление — тогда автор снимает добавленное новой младшей версией (в `api/README.md` — абзац «Снято в X.Y.Z»: что снято и по какому ответу), Порядок: сначала, по слову пользователя, автор убирает из `index.html` и прототипов то, что держится на добавленном, затем снимает добавленное из контракта; пользователь против — добавленное остаётся с `deprecated: true`. Это отмена своей правки, а не ломающая правка.

### Правка контракта без владельца

1. **Только добавлять.** Новый путь, необязательное поле, новое значение, событие, профиль. Ничего не снимать и не переименовывать: старое — `deprecated: true`, работает как раньше, сервер его по-прежнему учитывает. Умолчание нового поля сохраняет прежнее поведение. Нужна ломающая правка — запрос (ниже), не правка. Ломающая и так: новый отказ или новая проверка на прежнем запросе; `null` или новое значение в прежнем поле ответа, если контракт не говорит, что клиент пропускает незнакомое (новый тип события потока, новый вид, профиль, ключ `x-*` — можно); новая обязательная операция (например, в `capabilities.operations`); тест в `tests/api-*.js`, который строже к прежнему поведению — по этим тестам бэкенды проверяют готовность.
2. **Версия.** Следующая младшая после версии в `origin/main` (0.6.0 → 0.7.0), одна на законченную часть. В `api/README.md` — версия в шапке, раздел «Что добавлено в X.Y.Z» (по какому запросу, что добавлено) и, если что-то устарело, абзац «Устарело в X.Y.Z» (что, чем заменено, работает ли как раньше). В «Ломающие изменения» такая правка не входит.
3. **Файлы** — по «Порядку правки контракта» ниже. Сгенерированные файлы руками не правят.
4. **Проверки** — `check_api`, `check_ui`, `tools/run_api_tests.py`, `check_perf --quick` (`api/TESTS.md`). Сбой `check_perf` — по `api/TESTS.md`: повтори шаг с `--steps <id>`; повторился — сравни с запуском на коде до правки; новый сбой исправь до коммита, известный (тот, что `api/TESTS.md` называет) назови в уведомлении. Изменилось число тестов — поправь его в `api/TESTS.md`.
5. **Уведомление владельцу** — на каждую законченную часть: запрос `ГГГГ-ММ-ДД-ЧЧММССZ-<команда>-<тема>-done-request.md`, `Кому: владелец контракта`, `Статус: новый`, коммит контракта — тот, что ушёл на GitHub (после rebase). Разделы: «Что мы сделали» (версия, коммит, ссылки на исходные запросы, где описано), «Что проверить» — по пунктам исходного запроса с его номерами, «Сверх запросов» — что добавлено без запроса и решения, которые автор принял сам: владелец может их отклонить. Строка в таблице `api/requests/README.md`. Образец — `api/requests/2026-11-10-001016Z-mockup-edge-replication-done-request.md`.
6. **Без дублей.** Запрос на это изменение уже есть — второй не пиши, сошлись на него из уведомления. Статус чужого запроса не меняй: его ставит тот, кто запрос ведёт (раздел «Запросы команд VMS»). Свой исходный запрос и уведомление оставь в статусе «новый»: оба закрывает владелец ответом `…-done-response.md` рядом с уведомлением — «отвечен», а если правку отклонил — «отклонён» (что тогда делает автор — выше, в начале раздела).
7. **Коммиты и два push.** Сначала правка (`Макет: … ; контракт X.Y.Z` или `API: <команда> — … ; контракт X.Y.Z`) с записью в `CHANGES.md` — `git pull --rebase && git push`. Затем уведомление с коммитом правки из `origin/main` (`API: запрос <команда> — … внесено в контракт X.Y.Z, проверить`) — снова `git pull --rebase && git push`. Иначе rebase при push меняет хеш, и уведомление ссылается на коммит, которого нет.

Две правки одновременно. Контракт правят несколько человек, поэтому при `git pull --rebase` возможен конфликт:
1. Версию X.Y.Z уже занял другой — возьми следующую и поправь её в `openapi.json`, `api/README.md` и уведомлении.
2. `openapi.json`, `server.js`, `profiles.js`, `kinds.js`, тесты, `demo.json` и `api/*.md` сведи руками, сохрани обе правки. Несовместимы — спроси пользователя.
3. Сгенерированные файлы (`api/openapi.js`, `api/fixture.js`, `one-domain.json`, `large.json`) руками не своди: возьми любую сторону и собери заново (`tools/profile_fixture.py`, затем `tools/build_api.py`).
4. Проверки из п. 4 — ещё раз.

### Запрос вместо правки

Ломающая правка, или пользователь сказал «запросом»:
1. Запиши запрос в `api/requests/`: `ГГГГ-ММ-ДД-ЧЧММССZ-mockup-тема-request.md` (агент другой команды — со своей командой вместо `mockup`), в шапке дата, команда, коммит контракта, `Кому: …` (адресат из таблицы «Кому» в `api/requests/README.md`; API — `владелец контракта`) и `Статус: новый`, пункты с номерами: что нужно, зачем, что сломается у тех, кто уже работает по контракту. Строка в таблице `api/requests/README.md`, коммит `API: запрос mockup — тема`, `git pull --rebase && git push`.
2. Скажи пользователю: ссылка на запрос и что без него не сделать.
3. Ломающую часть не делай, делай то, что от запроса не зависит. Её сделает владелец.

Работая по запросу, сверх его пунктов контракт расширяй, только если без этого пункт не сделать, и назови это в «Сверх запросов» уведомления (п. 5). Остальное — отдельным запросом.

### Порядок правки контракта

1. `api/openapi.json`, затем `api/server.js` (хуки видов — `api/profiles.js`, описания видов — `api/kinds.js`), тесты `tests/api-*.js` и при необходимости `api/fixtures/demo.json` (правят руками). `one-domain.json` и `large.json` собирает `tools/profile_fixture.py`, руками их не правят.
2. `python3 tools/profile_fixture.py` (если менялся `demo.json` или описание видов), затем `python3 tools/build_api.py` — собирает `api/openapi.js` и `api/fixture.js`, руками их тоже не правят.
3. `python3 tools/check_api.py` и `python3 tools/check_ui.py`; что ещё запускать — `api/TESTS.md`.
4. Изменилась договорённость или поведение — поправь `api/README.md` и `api/BACKEND.md`.

Ломающую правку делает только владелец: следующая младшая версия, в `api/README.md` — раздел «Ломающие изменения в X.Y.Z» (что снято, чем заменено, что сделать клиенту и бэкенду). Раздел «Ломающие изменения против контракта старого макета» — только о переходе на 0.2.0, его не дополняют.

Где читать:
- `api/README.md` — как устроено, карта API, «Договорённости»: версии и `If-Match`, ошибки, групповые операции, поток событий, возможности системы.
- `api/BACKEND.md` — что реализовать бэкенду, подводные камни, тестовый стенд, когда готово.
- `api/FRONTEND.md` — что повторить в интерфейсе и что не переносить; `api/ACCEPTANCE.md` — критерии приёмки шагами пользователя.
- `api/TESTS.md` — какие проверки есть и когда их запускать.
- `api/requests/README.md` — как команды просят изменить API и как им отвечать.

## Запросы команд VMS

Команды, которые делают бэкенд за своей VMS, присылают запросы к API в `api/requests/`. Запрос — `ГГГГ-ММ-ДД-ЧЧММССZ-команда-тема-request.md` (время UTC), ответ на него — `…-response.md` рядом, с тем же началом, что у запроса (правила — `api/requests/README.md`). Расширить контракт по запросу может любой (раздел «Контракт API»). Кто запрос ведёт (ставит статус и пишет `…-response.md`), решает строка `Кому:`: запрос, где адресат — ты (таблица «Кому» в `api/requests/README.md`), ведёшь ты, по «Порядку» ниже. Запрос с `Кому: владелец контракта` ведёт владелец: ты только расширяешь контракт и пишешь уведомление (п. 5 «Правки контракта без владельца»), а статус и ответ — его. Пункты чужого запроса бери в работу — в `index.html` или в прототип — только по просьбе пользователя. Хук `.claude/hooks/new_requests.py` при старте сессии показывает отдельно запросы для пользователя (по `git config user.name` и таблице «Кому» в `api/requests/README.md`). Сам за запросы не берись: узнал о новом — скажи пользователю, сначала о тех, что для него, а работай по просьбе («ответь на запрос, где адресат — я», «что нового в запросах»).

Порядок (только для запроса, который ведёшь ты; иначе — расширь контракт и напиши уведомление):
1. `git pull --rebase`, прочитай запрос целиком. Если пункт неясен или решение за пользователем — спроси, прежде чем делать.
2. Статус в шапке запроса и в таблице `api/requests/README.md` — «в работе»; коммит `API: запрос <команда> — в работе`. Статус уже стоит — запрос ведёт тот, кто его поставил (`git log -- <файл>`): скажи об этом пользователю и не перехватывай без его слова.
3. Контракт и сервер — по разделу «Контракт API»: расширение — сам, с уведомлением владельцу; ломающий пункт делает владелец, а без него пункт ждёт. `index.html` — прямо (когда пользователь велел взяться, запрос и есть явная просьба), с проверками из `api/TESTS.md`. Коммиты — `Макет: по запросу <команда> — …`; запись в `CHANGES.md`.
4. Ответ — в `…-response.md`, начало имени как у запроса, шапка с датой ответа («Ответ от ГГГГ-ММ-ДД», UTC; она же — в таблице `api/requests/README.md`) и ссылкой на запрос, разделы по пунктам запроса с его номерами. По каждому пункту: что решили, коммит, где смотреть (раздел `BACKEND.md`, тест), как проверить. В конце — чего пока нет.
5. Статус «отвечен» (или «отклонён» — почему, в ответе) в шапке запроса и в таблице, в шапке запроса — ссылка на ответ. Пока пункт ждёт владельца контракта, статус остаётся «в работе». Текст запроса не правь: только строка статуса.

## Правила интерфейса

Соблюдай их в любой правке: в `index.html` и в прототипах. Если правишь участок, где правило ещё не выполнено, — доведи его до правила.

- **Тексты — простым языком (ASD-STE100).** Новый или изменённый текст интерфейса, русский и английский, пишут по `docs/TEXTS.md`: инструкция — инфинитив («Выбрать камеры»), у действия системы назван исполнитель («Консоль удалит правило после отсчёта»), без пассива, причастных оборотов и отглагольных существительных, полные предложения вместо тире, один термин — одна вещь (словарь там же). Старые тексты попутно не переписывают. Новый русский текст — новый ключ `i18n`: английский к нему и проверки тестов — по разделу «Как менять текст безопасно». Образец — «Примеры» там же.
- **Моргание при переходе по ссылке.** Любой переход по ссылке — из карточки, пути в шапке, списка, поиска, тоста, избранного, диалога — подсвечивает место, куда пришли: заголовок (или последний шаг пути), активную вкладку и строку дерева; дерево прокручивается к строке. Образец в `index.html` — «Права» (`accFlash`, класс `acc-flash`: два всплеска), в «Оборудовании» — `hwFlashLanding`. Клик в самом дереве и по вкладкам не моргает. Вспышка должна быть видна на своём фоне: на синем — белая, а не синяя.
- **Фильтры — по одному образцу, и плавно.** Фильтр над списком собирают из стандартных частей, а не свои чипы: блок `.bk-sum.bk-scope`, заголовок («Показать» или «Применить к») с чипом «все», `facetRowsHtml`, итог «Показано N из M»; счётчики и итог учитывают поиск. Плавность — часть образца: `paintMain` сам вызывает `bulkScopeSnap` и `bulkScopeFlip` для `#main .bk-scope`, поэтому без этого класса и без `data-fk` чипы прыгают, а второй вызов вокруг `paintMain` не нужен. Образец — список детекторов (`detFacetPaint`) и «Применить к».
- **Раскрытие не двигает соседей.** Раскрытие строки, папки или панели не меняет ширину столбцов и высоту других строк: внимание легко потерять. Таблице с раскрываемыми строками задают `table-layout:fixed` и ширины столбцов, текст в строке-заголовке не переносят, области прокрутки задают `scrollbar-gutter:stable`. Строки ниже съезжают плавно, новые проявляются; `prefers-reduced-motion` отключает движение.
- **Без кода в атрибутах.** Консоль VMS (w2c) отдаёт `index.html` под CSP `script-src 'self'`: атрибуты `onclick="…"`, `onchange="…"` и подобные там не выполняются. Обработчик в разметке — `${onEv("click",["имя",аргументы…])}`, в статической разметке — `data-on-click='[["имя"]]'`; вызываются только глобальные функции, значения на момент события — `onEv.value`, `onEv.checked`, `onEv.el`, `onEv.event`. Присваивание или выражение — отдельной маленькой функцией рядом. Описание — у `onEv` в `index.html`; `check_ui.py` падает, если в разметке появился атрибут `on…`.
- **Длинный список — с поиском.** Список выбора из 8 пунктов и больше (пустой «Выберите…» не считается) открывается с полем поиска: ввод сужает список, совпадения подсвечены, стрелки и Enter выбирают, Esc отменяет, внизу итог «Показано N из M». До 7 пунктов список остаётся обычным: их быстрее выбрать глазами. Обычному `<select>` ничего добавлять не нужно: компонент (`cbxOpen`, порог `CBX_MIN`) подключается сам, выбор приходит к обработчику обычным `change`, на сенсорных экранах остаётся системный выбор. Выбор из карточек или радиокнопок (шаблоны мастера) — поле поиска над списком, как в `ruleTplFilter`. Списки с собственным окном поиска (выбор устройств) под правило уже подходят. Образец в `index.html`.
- **Поле — в одну строку.** Текст в поле выбора и на кнопке не переносится на вторую строку. Ширина поля идёт от его текста (`field-sizing:content`), а строке формы задают `flex-wrap`: не влезло — поле уходит на следующую строку целиком. Если поле всё же уже текста, текст обрезан, а полный текст показывает подсказка. Стрелка списка не ложится на текст. Образец — поля правила в `index.html`.
- **Удаление — с вводом числа.** Каждое подтверждение удаления, одиночного и группового (устройства, хранилища, тома, папки, детекторы, домены), содержит поле, куда нужно ввести число удаляемых объектов; для одного объекта — `1`. Пока число не введено, «Удалить» неактивна, Enter в поле подтверждает только при верном числе. В диалоге перечислено, что пропадёт и что останется. После подтверждения — отсчёт в тосте с «Отменить». В `index.html` — `askConfirm(…, {typeCount:N})`.
