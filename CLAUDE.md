# Правила работы с макетом

Над репозиторием работают несколько человек, все в ветке `main`, без PR.
Макет смотрят через GitHub Pages: https://ndm234234.github.io/consolem/

## index.html — только согласованное

`index.html` — основной макет. Он работает через API: интерфейс читает и меняет данные запросами к встроенному тестовому серверу (`api/`), своих данных у него нет. Его меняют **только по явной просьбе**: «в основной», «в index.html», «перенеси в основной» — или по запросу команды VMS (раздел «Запросы команд VMS»).

Любая правка `index.html` — с проверками из `api/TESTS.md`: как минимум `python3 tools/check_api.py` и `python3 tools/check_ui.py`. Новые данные и действия — через контракт `api/openapi.json` и сервер, не константами в HTML.

## Всё остальное — в прототип

Любую другую просьбу изменить макет выполняй в файле прототипа, даже если о прототипе ничего не сказано.

- Если в этом разговоре уже есть прототип или пользователь назвал его («в прототипе 03»), продолжай в нём.
- Новый прототип создавай, когда в разговоре его ещё нет или просят явно: «новый прототип», «другой вариант», «сделай два варианта» (тогда два файла, по одному на вариант).
- По умолчанию прототип — копия `index.html`, то есть сразу с API: данные и действия прототипа идут через контракт и встроенный сервер, а не константами. Если прототип меняет контракт, сервер или набор `api/fixtures/demo.json` — это общее с `index.html`, такие правки делай совместимыми с основным макетом или договорись с пользователем. Проверка прототипа — `python3 tools/check_ui.py --page <файл>` и `<файл>?selftest`. «На основе прототипа NN» — копия файла NN.
- Порядок создания:
  1. `git pull --rebase`
  2. Номер — следующий после максимального среди `index_NN*.html` (учитывая и `index_01.html`), имя `index_NN_<тема-латиницей>.html`, например `index_04_filtry-nad-derevom.html`.
  3. Скопируй исходный файл и закоммить копию **до правок**: `Прототип NN: копия index.html` (или `копия прототипа MM`). Так `git diff` потом покажет только изменения прототипа.
  4. Добавь строку о прототипе в `protos.html`: номер, ссылка, автор (`git config user.name`), что проверяем, статус «обсуждается».
- Прототипы лежат в корне репозитория: в подпапке сломаются относительные пути к `assets/`.
- Чужие прототипы не меняй без явной просьбы.

## Публикация

Когда правка готова, сразу закоммить и запушь: `git pull --rebase && git push`. Дай ссылку на Pages, например
`https://ndm234234.github.io/consolem/index_04_filtry-nad-derevom.html`. Сайт обновляется примерно через минуту.

## Перенос в основной

По просьбе «перенеси из прототипа NN в основной …»:
1. Посмотри изменения: `git log -- <файл>` и `git diff <коммит-копии> HEAD -- <файл>`.
2. Перенеси в `index.html` только то, что попросили, поверх текущего `index.html` (он мог уйти вперёд).
3. Проверки из `api/TESTS.md` (см. раздел про `index.html`). Коммит: `Макет: из прототипа NN — <что>`, плюс запись в `CHANGES.md`.
4. В `protos.html` поставь прототипу статус «принят» (или «частично принят»). Удаляй файл прототипа только по просьбе.

## Запросы команд VMS

Команды, которые делают бэкенд за своей VMS, присылают запросы к API в `api/requests/`. Запрос — `ГГГГ-ММ-ДД-команда-тема-request.md`, ответ на него — `ГГГГ-ММ-ДД-команда-тема-response.md` рядом (правила — `api/requests/README.md`). Сам за запросы не берись: узнал о новом — скажи пользователю, а работай по просьбе («ответь на запрос w2c», «что нового в запросах»).

Порядок:
1. `git pull --rebase`, прочитай запрос целиком. Если пункт неясен или решение за пользователем — спроси, прежде чем делать.
2. Статус в шапке запроса и в таблице `api/requests/README.md` — «в работе»; коммит `API: запрос <команда> — в работе`.
3. Изменения — прямо в `index.html` и `api/` (запрос команды и есть явная просьба), с проверками из `api/TESTS.md`. Коммиты — `Макет: по запросу <команда> — …`; запись в `CHANGES.md`.
4. Ответ — в `…-response.md`, шапка со ссылкой на запрос, разделы по пунктам запроса с его номерами. По каждому пункту: что решили, коммит, где смотреть (раздел `BACKEND.md`, тест), как проверить. В конце — чего пока нет.
5. Статус «отвечен» (или «отклонён» — почему, в ответе) в шапке запроса и в таблице, в шапке запроса — ссылка на ответ. Текст запроса не правь: только строка статуса.
6. Коммит `API: ответ на запрос <команда> — …`, `git pull --rebase && git push`. Номера коммитов в ответе — после того, как они ушли на GitHub: при rebase они меняются.

## Коммиты

Сообщения коммитов на русском, в стиле существующих: `Макет: …`, `Прототип NN: …`.

## Правила интерфейса

Соблюдай их в любой правке: в `index.html` и в прототипах. Если правишь участок, где правило ещё не выполнено, — доведи его до правила.

- **Моргание при переходе по ссылке.** Любой переход по ссылке — из карточки, пути в шапке, списка, поиска, тоста, избранного, диалога — подсвечивает место, куда пришли: заголовок (или последний шаг пути), активную вкладку и строку дерева; дерево прокручивается к строке. Образец — «Права» (`accFlash`, класс `acc-flash`: два всплеска), в «Оборудовании» прототипа 07 — `hwFlashLanding`. Клик в самом дереве и по вкладкам не моргает. Вспышка должна быть видна на своём фоне: на синем — белая, а не синяя.
- **Удаление — с вводом числа.** Каждое подтверждение удаления, одиночного и группового (устройства, хранилища, тома, папки, детекторы, домены), содержит поле, куда нужно ввести число удаляемых объектов; для одного объекта — `1`. Пока число не введено, «Удалить» неактивна, Enter в поле подтверждает только при верном числе. В диалоге перечислено, что пропадёт и что останется. После подтверждения — отсчёт в тосте с «Отменить». В прототипе 07 — `askConfirm(…, {typeCount:N})`.
