# Контракт API

Правила из `CLAUDE.md` проекта вынесены сюда, потому что нужны только при работе с контрактом. Публикация, коммиты, прототипы и правила интерфейса — в `CLAUDE.md`. Запросы команд VMS, которые ведёшь ты, — скилл `vms-requests`.

`api/openapi.json` — источник истины: если встроенный сервер расходится с контрактом, ошибка в сервере. Контракт ведёт **владелец — joynickray** в этом репозитории (`ndm234234/consolem`). altumur и команды VMS расширяют контракт здесь сами (ниже) или присылают запросы; форк `altumur/consolem` забирает контракт отсюда, а не пушит свой.

**API не меняем втихую.** Контракт, сервер, наборы, `tests/api-*.js` и документы `api/` любой пользователь может расширить сам — по порядку раздела «Правка контракта без владельца» и с уведомлением владельцу. Ломающую правку (снять или переименовать путь, поле, значение; изменить смысл или умолчание) делает только владелец (`git config user.name` — `joynickray`); остальные пишут на неё запрос. Владелец может отклонить любую правку в ответе на уведомление — тогда автор снимает добавленное новой младшей версией (в `api/README.md` — абзац «Снято в X.Y.Z»: что снято и по какому ответу). Порядок: сначала, по слову пользователя, автор убирает из `index.html` и прототипов то, что держится на добавленном, затем снимает добавленное из контракта; пользователь против — добавленное остаётся с `deprecated: true`. Это отмена своей правки, а не ломающая правка.

### Правка контракта без владельца

1. **Только добавлять.** Новый путь, необязательное поле, новое значение в запросе, новый тип события потока (так добавлены события 0.3.0–0.6.0), вид, профиль. Ничего не снимать и не переименовывать: старое — `deprecated: true`, работает как раньше, сервер его по-прежнему учитывает. Умолчание нового поля сохраняет прежнее поведение. Нужна ломающая правка — запрос (ниже), не правка. Ломающая и так: новый отказ или новая проверка на прежнем запросе; `null` или новое значение в прежнем поле ответа, если контракт не говорит, что клиент пропускает незнакомое (ключ `x-*`, вид, профиль — пропускает); новая обязательная операция (например, в `capabilities.operations`); тест в `tests/api-*.js`, который строже к прежнему поведению — по этим тестам бэкенды проверяют готовность.
2. **Версия.** Следующая младшая после версии в `origin/main` (0.6.0 → 0.7.0), одна на законченную часть. В `api/README.md` — версия в шапке, раздел «Что добавлено в X.Y.Z» (по какому запросу, что добавлено) и, если что-то устарело, абзац «Устарело в X.Y.Z» (что, чем заменено, работает ли как раньше). В «Ломающие изменения» такая правка не входит.
3. **Файлы** — по «Порядку правки контракта» ниже. Сгенерированные файлы руками не правят.
4. **Проверки** — `check_api`, `check_ui`, `tools/run_api_tests.py`, `check_perf --quick` (`api/TESTS.md`). Сбой `check_perf` — по `api/TESTS.md`: повтори шаг с `--steps <id>`; повторился — сравни с запуском на коде до правки; новый сбой исправь до коммита, известный (тот, что `api/TESTS.md` называет) назови в уведомлении. Изменилось число тестов — поправь его в `api/TESTS.md`.
5. **Уведомление владельцу** — на каждую законченную часть: запрос `ГГГГ-ММ-ДД-ЧЧММССZ-<команда>-<тема>-done-request.md`, `Кому: владелец контракта`, `Статус: новый`, коммит контракта — тот, что ушёл на GitHub (после rebase). Разделы: «Что мы сделали» (версия, коммит, ссылки на исходные запросы, где описано), «Что проверить» — по пунктам исходного запроса с его номерами, «Сверх запросов» — что добавлено без запроса и решения, которые автор принял сам: владелец может их отклонить. Строка в таблице `api/requests/README.md`. Образец — `api/requests/2026-11-10-001016Z-mockup-edge-replication-done-request.md`.
6. **Без дублей.** Запрос на это изменение уже есть — второй не пиши, сошлись на него из уведомления. Статус чужого запроса не меняй: его ставит тот, кто запрос ведёт (скилл `vms-requests`). Свой исходный запрос и уведомление оставь в статусе «новый»: оба закрывает владелец ответом `…-done-response.md` рядом с уведомлением — «отвечен», а если правку отклонил — «отклонён» (что тогда делает автор — выше, в начале раздела).
7. **Коммиты и два push.** Сначала правка (`Макет: …`, `Прототип NN: …` или `API: <команда> — …`, всегда с `; контракт X.Y.Z`; запись в `CHANGES.md` — только если менялся `index.html`) — `git pull --rebase && git push`. Затем уведомление с коммитом правки из `origin/main` (`API: запрос <команда> — … внесено в контракт X.Y.Z, проверить`) — снова `git pull --rebase && git push`. Иначе rebase при push меняет хеш, и уведомление ссылается на коммит, которого нет.

Две правки одновременно. Контракт правят несколько человек, поэтому при `git pull --rebase` возможен конфликт:
1. Версию X.Y.Z уже занял другой — возьми следующую и поправь её везде в своей правке (`git grep -n X.Y.Z`: `openapi.json`, заголовки «Что добавлено в …» в `api/README.md`, тесты, `index.html`, `CHANGES.md`), в уведомлении и в сообщении ещё не отправленного коммита (`git commit --amend`).
2. `openapi.json`, `server.js`, `units.js`, `kinds.js`, `profiles.js`, `rule-engine.js`, тесты, `demo.json` и `api/*.md` сведи руками, сохрани обе правки. Несовместимы — спроси пользователя.
3. Сгенерированные файлы (`api/openapi.js`, `api/fixture.js`, `one-domain.json`, `large.json`, `xl.json`) руками не своди: возьми любую сторону и собери заново (`tools/profile_fixture.py`, затем `tools/build_api.py`).
4. Проверки из п. 4 — ещё раз.

### Запрос вместо правки

Ломающая правка, или пользователь сказал «запросом»:
1. Запиши запрос в `api/requests/`: `ГГГГ-ММ-ДД-ЧЧММССZ-mockup-тема-request.md` (агент другой команды — со своей командой вместо `mockup`), в шапке дата, команда, коммит контракта, `Кому: …` (адресат из таблицы «Кому» в `api/requests/README.md`; API — `владелец контракта`) и `Статус: новый`, пункты с номерами: что нужно, зачем, что сломается у тех, кто уже работает по контракту. Строка в таблице `api/requests/README.md`, коммит `API: запрос mockup — тема`, `git pull --rebase && git push`.
2. Скажи пользователю: ссылка на запрос и что без него не сделать.
3. Ломающую часть не делай, делай то, что от запроса не зависит. Её сделает владелец.

Работая по запросу, сверх его пунктов контракт расширяй, только если без этого пункт не сделать, и назови это в «Сверх запросов» уведомления (п. 5). Остальное — отдельной правкой со своей версией и уведомлением (п. 1–7) или отдельным запросом.

### Порядок правки контракта

1. `api/openapi.json`, затем сервер: `api/server.js`, склад — `api/units.js`, реестр видов — `api/kinds.js`, хуки профилей — `api/profiles.js`, движок правил — `api/rule-engine.js`; тесты `tests/api-*.js`; при необходимости `api/fixtures/demo.json` — там и описания видов и профилей (разделы `kinds`, `profiles`). Всё это правят руками. `one-domain.json`, `large.json` и `xl.json` собирает `tools/profile_fixture.py`, руками их не правят.
2. `python3 tools/profile_fixture.py` (если менялся `demo.json`), затем `python3 tools/build_api.py` — собирает `api/openapi.js` и `api/fixture.js`, руками их тоже не правят.
3. `python3 tools/check_api.py` и `python3 tools/check_ui.py`; что ещё запускать — `api/TESTS.md`.
4. Изменилась договорённость или поведение — поправь `api/README.md` и `api/BACKEND.md`.

Ломающую правку делает только владелец: следующая младшая версия, в `api/README.md` — раздел «Ломающие изменения в X.Y.Z» (что снято, чем заменено, что сделать клиенту и бэкенду). Раздел «Ломающие изменения против контракта старого макета» — только о переходе на 0.2.0, его не дополняют.

Где читать:
- `api/README.md` — как устроено, карта API, «Договорённости»: версии и `If-Match`, ошибки, групповые операции, поток событий, возможности системы.
- `api/BACKEND.md` — что реализовать бэкенду, подводные камни, тестовый стенд, когда готово.
- `api/FRONTEND.md` — что повторить в интерфейсе и что не переносить; `api/ACCEPTANCE.md` — критерии приёмки шагами пользователя.
- `api/TESTS.md` — какие проверки есть и когда их запускать.
- `api/requests/README.md` — как команды просят изменить API и как им отвечать.
