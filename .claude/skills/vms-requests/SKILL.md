# Запросы команд VMS

Правила из `CLAUDE.md` проекта вынесены сюда, потому что нужны только при работе по запросу. Контракт и сервер правят по скиллу `api-contract`. Публикация и коммиты — в `CLAUDE.md`.

Команды, которые делают бэкенд за своей VMS, присылают запросы к API в `api/requests/`. Запрос — `ГГГГ-ММ-ДД-ЧЧММССZ-команда-тема-request.md` (время UTC), ответ на него — `…-response.md` рядом, с тем же началом, что у запроса (правила — `api/requests/README.md`). Расширить контракт по запросу может любой (скилл `api-contract`). Кто запрос ведёт (ставит статус и пишет `…-response.md`), решает строка `Кому:`: запрос, где адресат — ты (таблица «Кому» в `api/requests/README.md`), ведёшь ты, по «Порядку» ниже. Запрос с `Кому: владелец контракта` ведёт владелец: ты только расширяешь контракт и пишешь уведомление (скилл `api-contract`, п. 5 «Правки контракта без владельца»), а статус и ответ — его. Адресатов несколько — каждый ведёт свои пункты: ответ один (`…-response.md`), каждый дописывает в него свой раздел; «в работе» ставит первый взявшийся, «отвечен» — последний ответивший. Пункты чужого запроса бери в работу — в `index.html` или в прототип — только по просьбе пользователя. Хук `.claude/hooks/new_requests.py` при старте сессии показывает отдельно запросы для пользователя (по `git config user.name` и таблице «Кому» в `api/requests/README.md`). Сам за запросы не берись: узнал о новом — скажи пользователю, сначала о тех, что для него, а работай по просьбе («ответь на запрос, где адресат — я», «что нового в запросах»).

Порядок (только для запроса, который ведёшь ты; иначе — расширь контракт и напиши уведомление):
1. `git pull --rebase`, прочитай запрос целиком. Если пункт неясен или решение за пользователем — спроси, прежде чем делать.
2. Статус в шапке запроса и в таблице `api/requests/README.md` — «в работе»; коммит `API: запрос <команда> — в работе`. Статус уже «в работе» и его поставил другой человек твоего же адресата — запрос ведёт он (`git log -- <файл>`); у запроса с несколькими адресатами свои пункты ведёшь ты (выше). Если ведёт он — скажи об этом пользователю и не перехватывай без его слова.
3. Контракт и сервер — по скиллу `api-contract`: расширение — сам, с уведомлением владельцу; ломающий пункт делает владелец, а без него пункт ждёт. `index.html` — прямо (когда пользователь велел взяться, запрос и есть явная просьба), с проверками из `api/TESTS.md`. Коммиты — `Макет: по запросу <команда> — …`; запись в `CHANGES.md`.
4. Ответ — в `…-response.md`, начало имени как у запроса, шапка с датой ответа («Ответ от ГГГГ-ММ-ДД», UTC; она же — в таблице `api/requests/README.md`) и ссылкой на запрос, разделы по пунктам запроса с его номерами. По каждому пункту: что решили, коммит, где смотреть (раздел `BACKEND.md`, тест), как проверить. В конце — чего пока нет.
5. Статус «отвечен» (или «отклонён» — почему, в ответе) в шапке запроса и в таблице, в шапке запроса — ссылка на ответ. Пункт, который ты сам внёс в контракт, владельца не ждёт: ставь «отвечен» и сошлись в ответе на уведомление; отклонит владелец правку — допиши ответ, статус остаётся «отвечен». Пока ломающий пункт ждёт владельца, статус остаётся «в работе». «Заменён» ставит отправитель, когда переписал запрос новым файлом; в столбце «Ответ» — ссылка на новый. Текст запроса не правь: только строка статуса.
6. Коммит `API: ответ на запрос <команда> — …`, `git pull --rebase && git push`. Номера коммитов в ответе — после того, как они ушли на GitHub: при rebase они меняются.
