# Профили

В этой папке лежат профили видов. Файл `<имя>.json` — источник истины. Таблицу `<имя>.md` собирает `tools/build_api.py`, руками её не правят.

## Что такое профиль

Профиль — договорённость об именах полей особого экрана. В него входят все поля, которые экран показывает. Профиль называет свойства (`properties`), наблюдаемое состояние (`status.observed`) и предметные пути (`apis`). Для каждого имени профиль фиксирует тип и смысл.

Вид объявляет профиль в `implements`. Такой вид несёт свойство под тем же именем, того же типа и с тем же смыслом. Тогда ручной экран консоли работает с видом без правки. Поля вида сверх профиля живут под своими именами. Поля, которого нет на особом экране, в профиле нет: оно есть только в схеме вида и в «Все параметры».

Профили публикует сервер: `GET /kinds` отдаёт их в разделе `profiles` (схема `Profile` в `api/openapi.json`). Раздел `profiles` в `api/fixtures/demo.json` собирает `tools/build_api.py` из этих файлов.

## Файл профиля

Старшая версия 1 лежит в `<имя>.json`: `vms.camera/1` — в `vms.camera.json`. Старшая версия N ≥ 2 лежит рядом, в `<имя>.<N>.json`: `vms.camera/2` — в `vms.camera.2.json`. Таблицу для людей собирает `build_api.py` в `<имя>.md` и `<имя>.<N>.md`.

| Поле | Что значит |
|---|---|
| `id` | имя и старшая версия: `vms.camera/1` |
| `version` | младшая версия вместе со старшей: `1.5`. Старшая версия равна номеру в `id` |
| `label` | название профиля для людей |
| `owner` | кто ведёт профиль |
| `reviewers` | кто смотрит правку: команды бэкендов, которые объявили профиль |
| `uses` | от каких профилей и с какой младшей версии зависит профиль: поле ссылается на профиль или ручной экран читает его объект. Список `{id, version}` |
| `properties`, `status` | поля: у каждого `schema` (кусок JSON Schema), `meaning` (смысл) и `since` (версия, с которой поле есть). Необязательный `absent: "unsupported"` значит «нет значения — у сервера нет такой возможности»: особый экран консоли прячет поле у объекта, если значения нет ни в `properties`, ни в `status.observed` и поле нельзя править (`Unit.writable`; без него — схема вида без `readOnly` и `x-immutable`). Пустое поле, которое можно править, экран показывает. Метки собирает `tools/build_api.py` в `window.CONSOLEM_PROFILE_ABSENT` (`api/fixture.js`), `GET /kinds` их не передаёт |
| `apis` | предметные пути объекта, например `recording-days` |
| `changes` | что менялось по версиям, новые сверху. У строки есть `version`, `what` и необязательный список `removed` (снятые поля) |

## Версии

- Новое поле — новая младшая версия: поднять `version`, поставить полю `since` этой версии, добавить строку в начало `changes`.
- Поле переименовано или сменило тип — новая старшая версия. Создать файл `<имя>.<N+1>.json` с профилем `<имя>/<N+1>` рядом со старым файлом: старый файл остаётся. Заменить `/1` на `/2` в том же файле нельзя: проверка покажет «старшую версию кладут рядом». Для контракта новый файл — добавление. Старый профиль снимает его owner после ответа reviewers.
- Поле, которого нет на особом экране, снимают младшей версией: поднять `version`, убрать поле из `properties` (или `status`), добавить в начало `changes` строку с этой же `version` и списком `removed` с именем поля. Основание — отчёт `tools/profile_coverage.py` (список `remove`) и правило «правило сервера / тест профиля»: поле, которое читает правило сервера или тест профиля, остаётся. Проверка отказывает, если поле снято без `removed`, если `removed` назвал поле, что осталось в профиле, или если версия не поднялась. Поле остаётся в схеме вида и в «Все параметры». Поле, которое экран показывает, снимают только старшей версией.
- Тесты профиля — слой `profile:<id>` (`profile:vms.camera/1`): у файла тестов `ApiTest.fileLayer`, у отдельного теста `layer`. Тест поля новой младшей версии получает `since` (`{ layer: "profile:vms.camera/1", since: "1.6" }`): у системы с более старой версией профиля тест пропускается. Правила — [`api/TESTS.md`](../TESTS.md#1-тесты-api).
- Ключ `absent` у поля ставят и снимают новой младшей версией: поднять `version`, добавить строку в начало `changes`. Тип и `since` поля не меняются.
- Вид пишет в `implements` только старшую версию: `vms.camera/1`. Младшую версию сервер отдаёт в `GET /kinds`.

Клиент читает версию так:

1. Сервер прислал младшую версию выше, чем знает клиент (`1.7` при известной `1.5`). Особый экран работает. Новые поля клиент показывает в «Все параметры».
2. Сервер прислал младшую версию ниже (`1.4` при известной `1.5`). Особый экран не показывает поля, которых в `1.4` нет.
3. Сервер прислал незнакомую старшую версию (`vms.camera/2` без `vms.camera/1`). Клиент пропускает профиль и открывает объект формой по схеме.

## Зависимости

Профиль называет в `uses` каждый профиль, на который ссылается. Если в схеме поля есть `x-ref` на другой профиль, этот профиль должен быть в `uses`. Версия в `uses` — самая младшая, с которой профиль работает. Профиль не использует сам себя. Взаимные зависимости разрешены.

Если у зависимости появилась новая старшая версия, проверка показывает, какие профили это задело. Например, ломающая правка камеры (`vms.camera/2`) сразу задевает кассу.

## Как собрать и проверить

1. Поправить файл профиля. Если правка меняет вид, поправить схему вида в `api/fixtures/demo.json`.
2. Запустить `python3 tools/build_api.py`: он собирает раздел `profiles` в `demo.json`, наборы, таблицы `<имя>.md`, `api/openapi.js` и `api/fixture.js`.
3. Запустить `python3 tools/check_api.py`: он проверяет профили пятью строками «Профили …»:
   - файлы устроены по формату;
   - раздел `profiles` наборов собран из файлов;
   - виды несут поля профиля того же типа, а `status` объектов совпадает со схемой профиля;
   - версия профиля выросла вместе с правкой (в том числе при смене `uses`), снятых полей и пропавших файлов нет (сверка с `origin/main`);
   - зависимости из `uses` есть, и их версия не ниже указанной.

`python3 tools/build_api.py --check` проверяет, что собранные файлы не отстали от файлов профилей. Наборы one-domain, large и xl он не проверяет: их сверяет `check_api.py`.

## Кто ведёт

`owner` ведёт профиль, `reviewers` смотрят правку: оба названы в файле профиля. Адресатов правки называет `python3 tools/layers.py`. Правка только профиля версию контракта не поднимает: она поднимает `version` профиля. Правила процесса — в `CLAUDE.md` и в скилле `api-contract` (`.claude/skills/api-contract/SKILL.md`, раздел «Слои: механизм и подсистема»).
