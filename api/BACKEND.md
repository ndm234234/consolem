# Памятка для команды бэкенда

С чего начать бэкенд конфигуратора и как понять, что он готов. Как устроен прототип и о чём договорились, — в [README](README.md). Здесь — что сделать, где подводные камни и чем проверить.

## Что реализовать

| Что | Где описано |
|---|---|
| REST API конфигуратора — 60 операций, плюс 3 служебные для тестового стенда | [`openapi.json`](openapi.json) — контракт, OpenAPI 3.1 |
| Модель данных: домены, серверы, устройства, папки, хранилища, тома, правила, права, опции, журнал, справочники | [README, «Модель данных»](README.md#модель-данных); схемы — в контракте |
| Эталонные данные: на них и проверяется бэкенд | [`fixtures/demo.json`](fixtures/demo.json), [README, «Эталонный набор»](README.md#эталонный-набор) |
| Правила поведения: что происходит на экране и почему | прототип [`index_10_api-server.html`](../index_10_api-server.html) (Pages: `https://ndm234234.github.io/consolem/index_10_api-server.html`); откуда взялись данные и правила — [`INVENTORY.md`](INVENTORY.md) |

Пример реализации — встроенный сервер [`server.js`](server.js). Это JavaScript в браузере, в продукт его не переносят. Он пример, а не источник требований: требования — контракт и описания операций в нём. Если сервер с контрактом расходится, ошибка в сервере. Совпадение маршрутов сервера и контракта проверяет `tools/check_api.py`, ответы по схемам — тесты API.

## Как устроен встроенный сервер

Порта у него нет, и по сети он не работает. Это обычный объект JavaScript, который живёт в той же вкладке, что и интерфейс. Страница подключает его тегом `<script src="api/server.js">` и создаёт один раз при загрузке:

```js
const server = ConsolemServer.create({ fixture: CONSOLEM_FIXTURE, openapi: CONSOLEM_OPENAPI });
const API = ConsolemApi.create({ server });
```

Интерфейс сервер напрямую не трогает: он вызывает только клиент `API.get/post/put/patch/del`. Клиент ([`client.js`](client.js)) превращает вызов в обычный вызов функции:

```
интерфейс ── API.patch("/devices/3…", {name: "Вход"}, 3) ──▶ client.js
client.js ── server.handle("PATCH", "/devices/3…", {name: "Вход"}, {"If-Match": "\"3\""}) ──▶ server.js
server.js ── { status: 200, body: {…устройство…}, headers: { ETag: "\"4\"" } } ──▶ client.js ──▶ интерфейс
```

- **Запрос — как HTTP, но без сети.** `handle(method, url, body, headers)` получает те же метод, путь со строкой запроса, тело JSON и заголовки, что пришли бы бэкенду. Возвращает статус, тело и заголовки. Маршрутизация — по путям контракта (`/devices/{id}` и т. д.).
- **Ответ — «как по сети».** Клиент копирует тело (через JSON) и отдаёт его обещанием (`Promise`), даже если сервер ответил мгновенно. Поэтому интерфейс не может случайно поменять данные сервера по ссылке и с первого дня написан асинхронно, как для настоящего бэкенда. Статус от 400 клиент превращает в исключение `{status, problem}`.
- **Поток событий — подписка, а не SSE.** Вместо `GET /stream` клиент вызывает `server.subscribe(fn)`, и сервер передаёт каждое сообщение `StreamMessage` в эту функцию. Сообщения те же, что пошли бы в SSE.
- **Данные — в памяти вкладки.** При загрузке сервер берёт эталонный набор ([`fixture.js`](fixture.js) — тот же `fixtures/demo.json`), сдвигает его даты на «сейчас − `capturedAt`» и дальше хранит всё у себя. Перезагрузка страницы возвращает набор в исходное состояние. У каждой вкладки свой сервер: две открытые вкладки друг друга не видят.
- **Часы — свои.** Шаги групповых операций, находки поиска, форматирование и синхронизация выполняются по таймеру сервера (раз в 40 мс он проверяет, что наступило). На странице тестов часы остановлены и идут только по `POST /test/clock`.

**Три способа связаться с сервером** — интерфейс и тесты в каждом из них одни и те же, меняется только то, что подставлено под клиент:

| Режим | Как включить | Куда уходит запрос | Порт |
|---|---|---|---|
| Встроенный сервер (по умолчанию) | просто открыть `index_10_api-server.html` — с диска или с Pages | вызов функции `server.handle(…)` в этой же вкладке | нет |
| Настоящий бэкенд или стенд | `index_10_api-server.html?api=https://адрес` | `fetch` по HTTP на этот адрес, поток — `EventSource` на `адрес/stream` | тот, что в адресе |
| Образец стенда на своей машине | `node tools/serve_api.mjs` (порт по умолчанию — 8787), затем `?api=http://127.0.0.1:8787` | по HTTP в Node, где работает тот же `server.js`, обёрнутый в HTTP-сервер с CORS и SSE | 8787 или указанный |

Есть ещё петля для тестов: `tests/api.html?api=loopback`. В ней Service Worker перехватывает запросы страницы к `…/tests/loopback-api/…` и отвечает тем же `server.js`, но уже настоящими HTTP-ответами с заголовками и потоком SSE. Так проверяется сетевой путь клиента без бэкенда. Отдельного порта у петли тоже нет: ей нужна только раздача страницы по HTTP, её поднимает `tools/check_loopback.py`.

Для бэкенда из этого следует одно: **клиенту всё равно, кто отвечает.** Если бэкенд отвечает на те же запросы теми же ответами и шлёт те же сообщения в `GET /stream`, интерфейс работает с ним без переделки, а тесты проходят так же, как на встроенном сервере.

## На что обратить внимание

- **Версии и 412.** У каждой изменяемой записи есть `version`, она растёт на 1 с каждым изменением. Ответы на чтение и изменение отдают её в `ETag` (`"3"`). Изменение без `If-Match` — `428 PRECONDITION_REQUIRED`, с чужой версией — `412 VERSION_MISMATCH` и актуальная запись в `current`. У прав (`/access`) и опций (`/settings`) версия одна на весь снимок. Состояние, которое меняет не администратор, версию не трогает: связь устройства (`online`, `fault`) и нагрузка. Иначе правка администратора падала бы с 412 из-за мигания связи.
- **Групповые операции и частичный успех.**
  - **Долгая** — `POST /operations`. Шаги выполняются по одному: изменить поля (`set`), задать папки (`folderIds`), создать дочернее устройство (`create`). У каждого шага свой итог: `ok`, `fail` с кодом, `cancel`. Перед запуском сверяются `expectedVersions` всех объектов: не совпала хоть одна — `412`, ничего не выполняется. Объект, над которым идёт другая операция, — `409 BUSY`.
  - **Отказы по шагу:** сервер устройства без связи — `SERVER_OFFLINE`, включение камеры с превышенной лицензией — `LICENSE_EXCEEDED`.
  - **«Отменить»** (`/revert`) — новая операция: сервер помнит, каким был объект до каждого выполненного шага, и возвращает его. Если объект после этого менял кто-то ещё, шаг отката — `fail VERSION_MISMATCH`: чужое не затирается.
  - **Быстрые** — синхронные запросы с ответом `{done, failed}`: `/servers/assign`, `/devices`, `/devices/update`, `/objects/delete`. Операции «всё или ничего» в API нет; там, где это нужно (права), — один снимок и одна версия.
- **Идемпотентность.** У всех групповых запросов есть `idempotencyKey`. Повтор с тем же ключом в течение 10 минут возвращает прежний ответ и ничего не выполняет снова. Двойной клик и повтор после сетевой ошибки не должны применять действие дважды.
- **Поток событий и досылка.** `GET /stream` — SSE. На сообщение — строки `id:` и `data:` (JSON по схеме `StreamMessage`), без `event:`.
  - Каждое изменение записи шлёт `entity.changed` / `created` / `deleted` с `kind`, `entityId`, `version`. Шлёт и своё: клиент по версии видит, что уже знает.
  - Долгие операции шлют ход: `operation.progress` на каждый шаг, `discovery.progress` на каждую находку.
  - По `Last-Event-ID` нужно дослать пропущенное по порядку. Если досылать уже нечего — `stream.reset`, и клиент перечитает всё.
  - Встроенный сервер хранит 500 последних сообщений.
- **Удаление и отмена.** Отсчёт «Отменить» ведёт клиент. `DELETE` приходит, когда отсчёт закончился, поэтому мягкое удаление серверу не нужно. Каскады — на сервере:
  - **устройство** — с дочерними, из всех папок и из `recordDetectorIds` камер;
  - **папка** — с подпапками; устройства остаются;
  - **хранилище** — с томами. У камер, писавших сюда, основным становится первое дополнительное хранилище, а без него `recordMode: none`;
  - **домен** — по `moveTo`: серверы становятся нераспределёнными в целевом домене, туда же переезжают папки, устройства, сетевые хранилища и найденное поиском. Последний домен — `409 LAST_DOMAIN`, непустой без `moveTo` — `422 DOMAIN_NOT_EMPTY`.
- **Права администратора.** Встроенный сервер их не проверяет: все запросы идут от `me` набора, у которого неограниченный доступ. В продукте:
  - операции раздела проверяются по функциям роли администратора (`DEVICES_SETUP`, `ARCHIVES_SETUP`, `DETECTORS_SETUP`, `PROGRAMMING_SETUP`, `USERS_RIGHTS_SETUP`, `SETTINGS_SETUP`, `DOMAIN_MANAGING_OPS` из `reference.access.features`); нет права — `403 PERMISSION_DENIED`;
  - объект, который администратору не виден, ведёт себя как несуществующий: `404 NOT_FOUND`, в списках его нет;
  - для тестов прав у стенда есть `actAs`.
- **Права пользователей — снимок и пакет.** `POST /access/apply` принимает права целиком (`AccessWrite`) с версией снимка. Сервер проверяет:
  - имена ролей, групп, каталогов и логины не повторяются, без учёта регистра (`409 NAME_TAKEN`, `LOGIN_TAKEN`);
  - ссылки ведут в существующие записи (`422`);
  - защиту от самоблокировки: остаётся хотя бы один включённый администратор с `global.unr` и действующим назначением, и текущий администратор среди них (`409 SELF_LOCKOUT`).
  
  `dryRun: true` — только проверка. Состояние синхронизации каталогов и групп (`status`, `lastSyncAt`, `message`, `entries`) ведёт сервер: присланное клиентом для существующих записей не берётся. Записи истории приходят текстом с указанием, кого касаются; время и автора ставит сервер.
- **Долгие действия.** Поиск устройств в сети (`POST /domains/{id}/discovery`), форматирование тома, синхронизация каталога и групповые операции отвечают сразу (`202`, состояние «идёт»), а итог приходит в поток. Новый поиск заменяет итог прежнего; второй запуск во время поиска — `409 BUSY`, клиент подхватывает идущий. Добавленное из найденного (`candidateId`) уходит из итога поиска.
- **Коды ошибок** — схема `ProblemCode`, тело — `application/problem+json`: `{code, message, field?, params?, current?}`. Интерфейс показывает свои тексты по `code`, поэтому новый код без согласования с фронтендом пользователь увидит как «ошибка: КОД». Тела запросов проверяются по схемам: лишнее поле, чужой тип, значение не из перечисления — `422 VALIDATION_FAILED` с `field`.
- **Идентификаторы** — UUID. Записи «Оборудования», хранилищ и правил создаёт сервер и выдаёт id в ответе. Номер устройства (`identifier`) не задан — сервер выдаёт следующий свободный среди камер, регистраторов, источников событий и СКУД; занятый — `409 IDENTIFIER_TAKEN`. Роли, пользователи, группы и каталоги создаются в черновике прав, поэтому их UUID задаёт клиент, а сервер принимает их как есть. Устаревшие ссылки в данных — ошибка бэкенда, а не повод для эвристики: права ролей ссылаются на папки и объекты по id.
- **Что считает сервер, а что клиент.**
  - **Сервер:** версии, каскады, выдачу номеров, проверку дисков тома (`409 DISK_TAKEN`), перенос при удалении, защиту от самоблокировки, ход долгих действий, сдвиг сроков по своим часам (`GET /me` отдаёт `serverTime` и `timezone`).
  - **Клиент:** дерево и счётчики, поиск по всему, план «было → станет», последствия черновика прав для людей и вкладку «Проверка» — это показ над прочитанным.
- **Что встроенный сервер упрощает — так переносить нельзя:**
  - нет входа, сессий и прав администратора (см. выше); данные живут в памяти вкладки и пропадают при перезагрузке;
  - в сеть он не ходит:
    - «отвечает ли адрес» — по хешу адреса;
    - модель устройства — по сумме чисел адреса;
    - проверка подключения к NAS или бакету — по заполненности полей;
    - синхронизация каталога всегда «изменений нет»;
    - имя, нагрузку и диски нового сервера он придумывает;
  - поиск в сети находит то, что записано в `network` набора, и отдаёт заводские логин и пароль найденных (`DiscoveryCandidate.password`) — открытым текстом;
  - времена фиксированы: шаг операции — 90–230 мс, находка — раз в 140 мс, форматирование и синхронизация — 1,5 с;
  - отказы шагов операции — только `SERVER_OFFLINE`, `LICENSE_EXCEEDED`, `VERSION_MISMATCH`. В продукте нужны и `DEVICE_OFFLINE` (учётные данные и видео не применить к устройству без связи), и отказы самого устройства;
  - политику паролей (`reference.access.passwordPolicy`, код `PASSWORD_POLICY`) он не проверяет: пароли новых пользователей интерфейс пока на сервер не передаёт (см. «Что ещё не решено»);
  - смысл правила (хотя бы одно событие и действие, окно у двух событий) не проверяется: незаконченное правило сохраняется, подсказку показывает интерфейс;
  - защиты от правки объекта, который в этот момент удаляется по отсчёту у другого администратора, нет.

## Тестовый стенд

Чтобы бэкенд проверялся теми же тестами, что встроенный сервер, ему нужны 3 служебные операции (тег `test-support`). В боевой системе их нет.

| Операция | Что делает |
|---|---|
| `POST /test/reset` | Загружает [`fixtures/demo.json`](fixtures/demo.json) заново: все даты и моменты сдвигаются на «сейчас − `capturedAt`», даты — на целые сутки. По умолчанию останавливает часы. `fixturePatch` — изменения набора на один прогон, JSON Merge Patch (RFC 7396): объекты сливаются, `null` удаляет поле, массивы заменяются целиком. `actAs` — логин, от имени которого идёт прогон. Шлёт в поток `test.reset` |
| `POST /test/clock` | Сдвигает часы на `advanceSec` и выполняет всё, что за это время наступило, в свой момент: шаги операций, находки поиска, форматирование, синхронизацию. В ответе — что сработало (`fired`) |
| `POST /test/events` | Событие извне: `device.signal` — устройство потеряло или вернуло связь (`online`, `fault`), `device.fault` — сменилась причина. Запись меняется, изменение уходит в поток, версия не растёт |

Образец стенда — [`tools/serve_api.mjs`](../tools/serve_api.mjs): встроенный сервер за HTTP, с CORS и потоком SSE ровно так, как их ждёт клиент (`node tools/serve_api.mjs`). На нём проверено, что всё ниже работает со страницы с диска.

Запуск: откройте `tests/api.html?api=https://адрес-стенда` — с диска (двойной клик) или со своей раздачи. Итог — строка вверху страницы и `data-apitest="pass|fail"` у `<html>`, чтобы гонять без человека. Один тест — `&only=<имя>`. Прототип с `?api=https://адрес-стенда` работает с бэкендом вместо встроенного сервера.

**CORS.** Страница с диска приходит с `Origin: null`, с сайта — со своим адресом. Стенд должен отвечать так:

- `Access-Control-Allow-Origin` — тот `Origin`, что пришёл (в том числе строкой `null`, только на стенде), и `Access-Control-Allow-Credentials: true`: клиент шлёт запросы с `credentials: "include"`, поток — `EventSource` с `withCredentials`;
- на предварительный `OPTIONS` — `Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE` и `Access-Control-Allow-Headers: Content-Type, If-Match, Last-Event-ID`;
- `Access-Control-Expose-Headers: ETag` — без него клиент не увидит версию записи;
- кука сессии — `SameSite=None; Secure`, если страница и стенд на разных адресах.

## Когда готово

1. `tests/api.html?api=<стенд>` проходит целиком: итог «Тесты API: все N прошли», `data-apitest="pass"`.
2. Покрытие — 100%: строка «Каждая операция контракта покрыта тестами» — PASS. Исключений нет.
3. Каждый ответ стенда соответствует схемам контракта: строка «Ответы соответствуют openapi.json» — PASS.
4. Прототип с `?api=<стенд>` работает так же, как со встроенным сервером. Проверка — те же сценарии интерфейса: `index_10_api-server.html?api=<стенд>&selftest`; сценарии идут по одному, перед каждым — `POST /test/reset` с идущими часами (`freezeClock: false`).

Всё это разом: `python3 tools/check_stand.py https://адрес-стенда`.

Для этого стенд должен стартовать с эталонным набором, а `/test/reset` — возвращать его в любой момент.

## Что ещё не решено

| Вопрос | Варианты | Рекомендация |
|---|---|---|
| Права администратора на операции и видимость объектов | (а) по функциям роли (`DEVICES_SETUP` и т. д.) на раздел; (б) ещё и по правам на папки, как у операторов | (а) сейчас, (б) — отдельной задачей: модель прав на папки для администраторов не спроектирована |
| Последствия черновика прав для людей («получат вход», «потеряют вход») | считает клиент, как сейчас; или `dryRun` возвращает их с сервера | сервер — в `dryRun`: алгоритм итоговых прав тогда живёт в одном месте; клиентский расчёт оставить только для показа матрицы |
| Пароли новых пользователей и каталогов | интерфейс их не хранит и не передаёт (так было и в макете); передавать в `AccessWrite` полем `password` только записи | передавать в пакете, в ответе — только `hasPassword`; проверять `passwordPolicy` на сервере |
