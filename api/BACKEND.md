Пример реализации — встроенный сервер [`server.js`](server.js) поверх [`kinds.js`](kinds.js), [`units.js`](units.js), [`profiles.js`](profiles.js) с движком «Автоматизации» [`rule-engine.js`](rule-engine.js). Совпадение маршрутов сервера и контракта проверяет `tools/check_api.py`, ответы по схемам — тесты API.

## Как устроен встроенный сервер

Порта у него нет, и по сети он не работает. Это обычный объект JavaScript, который живёт в той же вкладке, что и интерфейс. Страница подключает его тегами `<script src="api/contract.js">`, `kinds.js`, `units.js`, `profiles.js`, `rule-engine.js` и `server.js` (из `api/`) и создаёт один раз при загрузке:

```js
const server = ConsolemServer.create({ fixture: CONSOLEM_FIXTURE, openapi: CONSOLEM_OPENAPI });
const API = ConsolemApi.create({ server });
```

Интерфейс сервер напрямую не трогает: он вызывает только клиент `API.get/post/put/patch/del`. Клиент ([`client.js`](client.js)) превращает вызов в обычный вызов функции:

```
интерфейс ── API.patch("/units/3…", {name: "Вход"}, 3) ──▶ client.js
client.js ── server.handle("PATCH", "/units/3…", {name: "Вход"}, {"If-Match": "\"3\""}) ──▶ server.js
server.js ── { status: 200, body: {…объект Unit…}, headers: { ETag: "\"4\"" } } ──▶ client.js ──▶ интерфейс
```

- **Запрос — как HTTP, но без сети.** `handle(method, url, body, headers)` получает те же метод, путь со строкой запроса, тело JSON и заголовки, что пришли бы бэкенду. Возвращает статус, тело и заголовки. Маршрутизация — по путям контракта (`/units/{uid}` и т. д.).
- **Ответ — «как по сети».** Клиент копирует тело (через JSON) и отдаёт его обещанием (`Promise`), даже если сервер ответил мгновенно. Поэтому интерфейс не может случайно поменять данные сервера по ссылке и с первого дня написан асинхронно, как для настоящего бэкенда. Статус от 400 клиент превращает в исключение `{status, problem}`.
- **Поток событий — подписка, а не SSE.** Вместо `GET /stream` клиент вызывает `server.subscribe(fn)`, и сервер передаёт каждое сообщение `StreamMessage` в эту функцию. Сообщения те же, что пошли бы в SSE.
- **Данные — в памяти вкладки.** При загрузке сервер берёт эталонный набор ([`fixture.js`](fixture.js) — тот же `fixtures/demo.json`), сдвигает его даты на «сейчас − `capturedAt`» (кроме календаря — расписаний и особых дней: праздники не сдвигаются) и дальше хранит всё у себя. Перезагрузка страницы возвращает набор в исходное состояние. У каждой вкладки свой сервер: две открытые вкладки друг друга не видят.
- **Часы — свои.** Шаги групповых операций, находки поиска, форматирование и синхронизация выполняются по таймеру сервера (раз в 40 мс он проверяет, что наступило). На странице тестов часы остановлены и идут только по `POST /test/clock`.

### Запрос без сети: что именно происходит

По умолчанию запросов в сеть нет совсем: клиент их только изображает. Во вкладке DevTools → Network при работе с прототипом не видно ни одного обращения к API. Видна только загрузка самих файлов страницы.

Возьмём одно действие: администратор переименовал камеру в дереве. Интерфейс в обоих режимах выполняет одну и ту же строку:

```js
API.patch(`/units/${uid}`, { name: "Вход" }, 3)   // путь, тело, версия объекта для If-Match
```

Дальше клиент делает одно из двух — смотря как его создали при загрузке страницы:

| Шаг | Встроенный сервер (по умолчанию) | Бэкенд (`?api=https://адрес`) |
|---|---|---|
| 1. Собрать запрос | метод `PATCH`, путь `/units/…`, тело `{"name":"Вход"}`, заголовок `If-Match: "v3k"` | то же самое |
| 2. Отправить | вызвать функцию `server.handle("PATCH", "/units/…", тело, заголовки)` в этой же вкладке. Тело перед этим копируется через JSON — сервер получает копию, а не объект интерфейса | `fetch("https://адрес/units/…", { method: "PATCH", body: '{"name":"Вход"}', headers: {…}, credentials: "include" })` |
| 3. Обработать | `server.js` находит маршрут `PATCH /units/{uid}`, проверяет тело по схеме контракта и по схеме вида объекта, сверяет версию, меняет объект в своей памяти, шлёт `entity.changed` подписчикам потока | бэкенд делает то же у себя |
| 4. Ответить | функция возвращает объект `{ status: 200, body: {…}, headers: { ETag: '"v3m"' } }` | HTTP-ответ `200`, тело JSON, заголовок `ETag: "v3m"` |
| 5. Отдать интерфейсу | клиент копирует тело через JSON, делает имена заголовков строчными и отдаёт результат обещанием. С `?latency=300` — через 300 мс | клиент читает тело и заголовки ответа и отдаёт их обещанием |
| 6. Ошибка | статус от 400 — исключение `{ status, problem }` | то же самое |

После шага 5 интерфейс не знает, какой из двух путей сработал. Ему пришло одно и то же: тело, статус, `ETag`.

Вся разница — в одной функции клиента `raw(method, path, body, headers)`. Всё остальное (`get/post/put/patch/del`, превращение ошибок в исключения, заголовок `If-Match` из версии) у клиента общее:

```js
// ?api=https://адрес — настоящий запрос
const raw = (method, path, body, headers) => fetch(base + path, { method, headers, body: JSON.stringify(body), credentials: "include" }) …

// по умолчанию — вызов функции, но ответ ведёт себя как сетевой
const raw = (method, path, body, headers) =>
  Promise.resolve().then(() => {
    const res = server.handle(method, path, copy(body), copy(headers));
    return later({ status: res.status, body: copy(res.body), headers: res.headers });
  });
```

Поток событий устроен так же. С бэкендом клиент открывает `new EventSource("https://адрес/stream")`, со встроенным сервером — вызывает `server.subscribe(fn)`. Сервер передаёт в `fn` те же сообщения, что ушли бы строками `data:` в SSE.

**Зачем изображать, а не ходить по сети:**
- макет открывается двойным кликом или с GitHub Pages и работает без бэкенда и без раздачи по HTTP;
- код интерфейса при этом уже асинхронный, ждёт ответа, обрабатывает `412`, `422`, частичный успех — ровно как будет с бэкендом;
- копирование тела «туда и обратно» не даёт интерфейсу менять данные сервера по ссылке. Если бы оно ему понадобилось, это выглядело бы как работа без запроса, и с настоящим бэкендом такой код сразу сломался бы;
- договорённости контракта (пути, тела, коды, версии, поток) проверяются на каждом клике в макете, а не только тестами.

**Как убедиться, что изображение честное:**
- **петля** (`tools/check_loopback.py`): те же тесты API проходят по настоящему HTTP через Service Worker;
- **образец стенда** (`tools/check_stand.py`): тесты API и самопроверка прототипа проходят против `node tools/serve_api.mjs` — там запросы настоящие и видны в DevTools → Network.

### Три способа связаться с сервером

Интерфейс и тесты в каждом из них одни и те же, меняется только то, что подставлено под клиент:

| Режим | Как включить | Куда уходит запрос | Порт |
|---|---|---|---|
| Встроенный сервер (по умолчанию) | просто открыть `index.html` — с диска или с Pages | вызов функции `server.handle(…)` в этой же вкладке | нет |
| Настоящий бэкенд или стенд | `index.html?api=https://адрес` | `fetch` по HTTP на этот адрес, поток — `EventSource` на `адрес/stream` | тот, что в адресе |
| Образец стенда на своей машине | `node tools/serve_api.mjs` (порт по умолчанию — 8787), затем `?api=http://127.0.0.1:8787` | по HTTP в Node, где работает тот же `server.js`, обёрнутый в HTTP-сервер с CORS и SSE | 8787 или указанный |

Есть ещё петля для тестов: `tests/api.html?api=loopback`. В ней Service Worker перехватывает запросы страницы к `…/tests/loopback-api/…` и отвечает тем же `server.js`, но уже настоящими HTTP-ответами с заголовками и потоком SSE. Так проверяется сетевой путь клиента без бэкенда. Отдельного порта у петли тоже нет: ей нужна только раздача страницы по HTTP, её поднимает `tools/check_loopback.py`.

Для бэкенда из этого следует одно: **клиенту всё равно, кто отвечает.** Если бэкенд отвечает на те же запросы теми же ответами и шлёт те же сообщения в `GET /stream`, интерфейс работает с ним без переделки, а тесты проходят так же, как на встроенном сервере.

## На что обратить внимание

- **Версии и 412.** У каждой изменяемой записи есть `version` — **непрозрачная строка**. Клиент сравнивает её только на равенство и возвращает как есть; он не разбирает её, не упорядочивает и не вычисляет следующую. Ответы на чтение и изменение отдают версию в `ETag` (`"v3k"`). Изменение без `If-Match` — `428 PRECONDITION_REQUIRED`, с чужой версией — `412 VERSION_MISMATCH` и актуальная запись в `current`. У прав (`/access`) и опций (`/settings`) версия одна на весь снимок.

  Что сервер обязан соблюдать, чтобы версия защищала от затирания чужих правок:
  1. **Меняется при любом изменении** того, что видно в записи API. Если устройство собрано из нескольких записей VMS, — при изменении любой из них. Например, версия может быть склейкой версий частей (`"a12.b7.c3"`) или меткой из общего счётчика.
  2. **Никогда не возвращается к прежнему значению** той же записи. Устройство изменили, а потом вернули как было, — версия всё равно новая; иначе администратор со старой копией тихо затрёт чужую правку. Склейка монотонных версий частей это гарантирует. Хеш только содержимого — нет: его повтор нужно исключить отдельно.
  3. **Не меняется без изменений.** Чтение, связь устройства (`online`, `fault`) и нагрузка версию не трогают; иначе правки администратора падали бы с 412 из-за мигания связи.
  4. **Пригодна для заголовка:** печатные символы ASCII без пробела и кавычек (схема контракта проверяет это шаблоном).

  Встроенный сервер выдаёт версии из общего счётчика (`v1`, `v2`, … `v3k`): у одной записи они идут скачками и не повторяются — поэтому ни интерфейс, ни тесты не могут опереться на «+1».
- **Групповые операции и частичный успех.**
  - **Долгая** — `POST /operations`. Шаги выполняются по одному; шаг — `uid` объекта и ровно одно из: `patch` (правка, как `PATCH /units/{uid}`), `folders` (папки объекта), `createUnit` (создать дочерний), `move` с `params` (перенести к родителю: сервер — в домен), `action` с `params` (команда вида), `delete: true`. У каждого шага свой итог: `ok`, `fail` с кодом, `cancel`; указатель отказа — `params.field` (JSON Pointer в теле шага: `/properties/ip`, `/folders/0`, `/params/preset`), слово схемы — `params.keyword`. Перед запуском сверяются `expectedVersions` всех объектов: не совпала хоть одна — `412`, ничего не выполняется. Объект, над которым идёт другая операция, — `409 BUSY`. Объекта шага нет — `422 VALIDATION_FAILED` на всю операцию, `field: /items/{i}/uid`, `params.targetId` — этот uid (как неизвестное устройство в `POST /folders/{id}/devices` старого макета). Состав папок в шагах (`folders` и `patch {folders}`) проверяется до запуска, как `POST /folders/{id}/devices` и шаг `folderIds` старого макета: папки нет, папка другого домена, запись в папки не входит — `422` на всю операцию, ничего не применено; `field` — указатель в теле запроса (`/items/{i}/folders/0`, `/items/{i}/patch/folders/0`), `params.targetId` — объект шага. Права «Администратора» и связь с центром домена папки судятся при выполнении (у шагов одной папки отказ одинаков). Итог шага `move`, после которого объекта шага нет (сервер вида `camera` принят камерой), называет новый объект: `createdId` и его `version`. **`wait: true`** — быстрая запись: если все шаги мгновенные (`patch`, `folders`, `move`), сервер выполняет их в самом запросе и отвечает `200` законченной операцией (`state: done`, итог по строкам в `items`); иначе — `202`, как без `wait`. Так интерфейс пишет состав папки, привязки и приём серверов без опроса, как синхронные пути старого макета; план карточки и выборки идёт без `wait` — с ходом и отменой. Пока операция не завершена, её объекты заперты и для остальных запросов: правка, перенос и удаление объекта (любым путём: `DELETE`, `/objects/delete`, шаг `delete`), смена его папок, удаление того, внутри чего он лежит, повтор и откат другой операции — `409 BUSY` с `params.targetId`; в пакетном `/objects/delete` — `failed` с кодом `BUSY`, остальные объекты выполняются. Паузы нет (прототип 11): `/pause` и `/resume` устарели и остаются, пока ими пользуется `index.html`; операцию можно только отменить — неначатые шаги получают `cancel`, текущий доходит до конца.
  - **Отказы по шагу:** сервер-исполнитель объекта без связи — `SERVER_OFFLINE` (папки объекта — не запись на его сервер: их судит центр домена папки), включение камеры с превышенной лицензией — `LICENSE_EXCEEDED`, не по схеме вида — `VALIDATION_FAILED` с указателем.
  - **«Отменить»** (`/revert`) — новая операция: сервер помнит значения до и после каждого шага. Шаг откатывается, если текущие значения его полей равны записанным; иначе `fail VERSION_MISMATCH`: чужое не затирается, правка другого поля не мешает. Одиночная правка — тоже операция из одного шага: `GET /operations`, новые сверху, 50 последних, не дольше 7 суток. Правки, создание, удаление и форматирование хранилищ и томов — в той же стопке. Шаг, который снимает созданное, сверяет версию созданного объекта, а не родителя из цели шага; созданное меняли или в созданное хранилище уже пишут — `fail NOT_SUPPORTED`. Адрес и размер тома, удаление, форматирование — тоже `fail NOT_SUPPORTED`. Откат идёт строго по стопке: стопка — законченные операции с удачными шагами, не откачанные и не сами откаты; откатить можно только верхнюю, предыдущая становится доступной после её отмены, новая правка становится верхней. Откат не откатывается, а повторяется: `POST /operations/{id}/redo`, как в редакторе. Повтор доступен только для последней отменённой операции (отменили B, затем A — сначала A, потом B), это новая операция с `redoOf`, снова верхняя в стопке. Шаг применяет значения после правки, сверяя текущие с теми, что были до неё: другое значение — `fail VERSION_MISMATCH`. Не откатившиеся шаги не повторяются, снятый откатом созданный объект заново не создаётся: шаг `fail NOT_SUPPORTED`. Правка, попавшая в стопку, очищает повтор целиком; правка сервера в стопку не входит и его не очищает. Удаление, папки, пароль, адрес и объём тома не откатываются: шаг `fail NOT_SUPPORTED`, остальные идут. Откатить нельзя вовсе — `409 NOT_REVERTIBLE`, причина в `params.reason`: `notLast`, `isRevert`, `expired`, `reverted`, `running`, `empty`, у повтора — `notLast`, `stale`.
  - **Быстрые** — синхронные запросы с ответом `{done, failed}`: `POST /units` (строки с детьми), `/objects/delete`, `/rules/update`; `POST /operations` с `wait: true` (выше). Операции «всё или ничего» в API нет; там, где это нужно (права), — один снимок и одна версия.
- **Идемпотентность.** У всех групповых запросов есть `idempotencyKey`. Повтор с тем же ключом в течение 10 минут возвращает прежний ответ и ничего не выполняет снова. Двойной клик и повтор после сетевой ошибки не должны применять действие дважды.
- **Поток событий и досылка.** `GET /stream` — SSE. На сообщение — строки `id:` и `data:` (JSON по схеме `StreamMessage`), без `event:`.
  - Каждое изменение записи шлёт `entity.changed` / `created` / `deleted` с `kind`, `entityId`, `version`. Шлёт и своё: клиент по версии видит, что уже знает.
  - Долгие операции шлют ход: `operation.progress` на каждый шаг, `discovery.progress` на каждую находку.
  - По `Last-Event-ID` нужно дослать пропущенное по порядку. Если досылать уже нечего — `stream.reset`, и клиент перечитает всё.
  - Встроенный сервер хранит 500 последних сообщений.
- **Удаление и отмена.** Отсчёт «Отменить» ведёт клиент. `DELETE` приходит, когда отсчёт закончился, поэтому мягкое удаление серверу не нужно. Каскады — на сервере:
  - **объект** — с дочерними по `parentId` (камера — с потоками и детекторами), из всех папок и из `recordDetectorIds` камер. У `ipsrv` с записью устройства камеры остаются: `parentId: null`, `entity.changed`. `ipsrv` с `derived: true` выведен из устройства, записи нет: `PATCH`, `DELETE`, `folders` — `422 NOT_SUPPORTED`. Объект или потомок под операцией — `409 BUSY`;
  - **папка** — с подпапками; объекты остаются, из их `folders` папка уходит;
  - **хранилище** — с томами. У камер, писавших сюда, основным становится первое дополнительное хранилище, а без него `recordMode: none`;
  - **домен** — `DELETE /units/{uid}?moveTo=<домен>`: серверы становятся нераспределёнными в целевом домене, туда же переезжают папки, устройства, сетевые хранилища и найденное поиском. Последний домен — `409 LAST_DOMAIN`, непустой без `moveTo` — `422 DOMAIN_NOT_EMPTY`, `field: /moveTo`;
  - **объект в правилах** — уходит из целей правил и их версий истории в `gone` по имени (правило с ним — ошибка, пока цель не заменят); у правила новая версия и `entity.changed`;
  - **правило** (`/objects/delete`) — с историей версий и своими расписаниями «только здесь» (`owner.kind: rule`), если они больше нигде не используются; журнал его запусков остаётся;
  - **расписание** — режим объекта с ним включается только вручную, условие «Время» правила и окно обслуживания переходят на встроенное «Никогда»; встроенные — `409 BUILTIN`;
  - **группа особых дней** — уходит из исключений расписаний;
  - **режим объекта** (`PUT /modes` без него) — уходит из условий «Режим объекта», включённый вручную — снимается; системный — `409 BUILTIN`;
  - **окно обслуживания** — со своим расписанием, если оно больше нигде не используется.
- **Автоматизация.** События, условия и шаги «Тогда» ссылаются на объекты и области **по `uid`** (`RuleTarget`: `include` — `{uid}` объекта или `{area: folder | server | domain, uid}`; `exclude`; `gone` — удалённое по имени; `fromEvent` — объект из события). Событие — `{source: "unit", kinds | implements, event, match}` из `UnitKind.events`, действие объекта — `{type: "unitAction", action, target, params}` из `UnitKind.actions` (`ruleAction`). `actions` — дерево `steps` с шагами хода выполнения (ждать, ждать событие, спросить оператора, эскалация). У правила «Только журнал», приглушение, порядок, кто запускает и от чьего имени. У камеры `status.observed.disabledByRuleId` + `disabledByRuleAt`, `armed`.
- **Метки серверов.** Свойство `labels` сервера (`vms.server/1`), правка — `PATCH /units/{uid}`; `reference.serverLabels` — известные метки. `labels` у камеры, детектора, строки `extraArchives`, правила — где работает; выбор сервера детектора заменён метками. Новый серверный детектор просит `gpu`; нет сервера с меткой — причина в `faultText`. Встроенный сервер записи никуда не размещает.
- **Состояние словами.** `status.observed` камеры: `faultText`, `recordState`, `recordReason`, в строках `extraArchives` — `state`, `reason`: только чтение, показ — вкладка «Архив». Тревожные виды — свойство `alarmKinds`, варианты — коды событий видов (`UnitKind.events` с `alarm` не `false`).
- **Журнал.** `GET /journal` отбирает по `deviceId` (`uid` объекта), `from`, `to`, `source`, `limit`, время — `occurredAt`; в записи ещё `kind`, `fields`; в ответе `truncated`, `withheldCount`. Встроенный сервер права не проверяет, `withheldCount` у него 0.
- **Учётки потоков.** `/stream-accounts`: `GET`, `POST`, `PATCH {disabled}`, `DELETE`, `POST …/password`. Пароль приходит один раз. Доступ к камерам — `Access.streamGrants`, возможность `streamGrants`: учётка, все камеры, папки, камеры. Как у человека, права учётки — гранты (V/03.6): перевод в строки на `*`, `folder:F`, `unit:cam/<id>` делает V/11. Ролей у учётки нет: она не человек домена. Строки только складываются, запрета нет. Идёт в `POST /access/apply` вместе с правами, нет поля — не меняется. Удаление учётки, камеры, папки убирает их из списка и двигает версию снимка.
- **Профиль при добавлении.** `configMode`, `templateId` — свойства камеры с `x-transient`: действуют только в строке `POST /units`, в объекте их нет, `PATCH` — `422`, связи с источником нет. `current` ничего не меняет. `default` — умолчания модели уходят на камеру, без модели — `422`, `field: /properties/configMode`. `template` — разовая копия с камеры той же модели: разрешение и частота кадров потоков, сами потоки, `firmware`; адрес, логин, пароль, имя, записи, папки, детекторы и `norm` не копируются. `firmware` — версия драйвера, обновления прошивки нет. Встроенный сервер описаний моделей не имеет: умолчания у него одни на всех.
- **Единицы СКУД.** `acfa_sensor`, `acfa_lock`, `acfa_fence` и `relay` в СКУД заводит оператор: родитель — `acfa`, камера-домофон или `ipsrv`, у реле — запись СКУД. Адрес — свойство `path`, шаблон — `model` из `unitOptions` родителя, правка шаблона — `422 NOT_SUPPORTED`. `acfa` с `parentId` — контроллер: своего подключения нет, `ip`, `port`, `vendor` — `422 NOT_SUPPORTED`, снимается с вложенным. В папки единицы и контроллер не входят (`folders` нет в `capabilities`). Настройки — свойство `properties` единицы, ключи из `unitOptions`. События — `UnitKind.events` вида, `match.word` из `events` шаблона; тревогой событие делает правило. Команды — свойство `operations` и `UnitKind.actions`: из карточки — `POST /units/{uid}/actions/{action}`, в правиле — `unitAction`; `output` на реле двери — `422 NOT_SUPPORTED`. Отказ устройства — `409 DEVICE_REFUSED`, причина в `params.reason`. Команда, которую объект называет своей в `operations`, а вид не описывает (реле под замком: `on`, `off`), — тоже отказ устройства: `409 DEVICE_REFUSED`, `reason: noOperation`, как `/devices/{id}/operations/{op}` старого макета; команды нет ни у объекта, ни у вида — `404`.
- **Источник событий.** Сервер — свойство `serverId`; без него выбирает система, предупреждение — в `faultText`. Переноса при падении нет. `ip`: адрес сервера или имя кассы, `0.0.0.0` и `::` — `422 VALIDATION_FAILED`, `field: /properties/ip`. Второй источник на порт сервера создаётся, но не запускается: причина в `faultText`. Событие — `text`, `match.word` из `words` объекта. Здесь только настройка `cameraId`, `overlayDelayMs`, `overlayDurationSec`, `words`: титры рисует клиент просмотра.
- **PTZ** (`vms.ptz/1`). Свойства камеры `ptz`, `presets`, `presetMax`, своей записи нет. `presets` — все сохранённые номера: без подписи имя пустое, форма показывает номер. `PUT /units/{uid}/presets/{n} {}` запоминает положение, записи нет — создаёт с пустым именем; судят связь и `ptz`. `PUT {name}`, пустое тоже, положения не трогает и устройству не идёт, связь и `ptz` его не судят: записи нет — создаёт, есть — заменяет имя, пустое снимает подпись, запись остаётся. Запись снимает только `DELETE`, первым шагом, затем просьба камере при `ptz` и связи, иначе 200 и положение остаётся в камере. Кнопка «Пресет» заводит строку, «Запомнить здесь» пишет положение. ADR-0112 доп. (4). `PUT /units/{uid}/ptz {pan, tilt, zoom, focus, ttlSec}` — аренда на человека и камеру, скорости от -1 до 1, срок до 5 с; клиент повторяет `PUT` раньше срока, на отпускание шлёт `DELETE`. Нет продления — камера останавливается сама. Двое на одной камере — действует последняя сменившаяся аренда (V/01.4 Н1.4г). Встроенный сервер камерами не движет и двух людей не изображает.
- **Детекторы** (`vms.detector/1`). Встроенный: `det` с `builtin: true` и `template` из `detectorOptions` камеры, поля нет — встроенный не предлагается, запись — `422 NOT_SUPPORTED`, `field: /properties/builtin`. `detectorKind`: вне перечня — `other`, подпись — `name` шаблона; в правиле это событие `other` с `match.template`. `sensitivity` — в диапазоне шаблона, настройки нет — `422 NOT_SUPPORTED`, поле скрыто. Несовместимые на одном канале (`conflicts`): включение — `409 BUSY`, `params: {reason: "incompatible", with}`, шаг операции — `fail BUSY` с теми же `params`. Детекторов одного вида на камере сколько угодно. `zone` — `{shape, points}` в долях кадра, у встроенного и серверного: `rect`, `line` — две точки, `polygon` — от трёх. Серверному — `stream`, `params`.
- **`recordMode` хранилища.** Нет поля — режим «Авто»: при сбое, а у камеры без основной записи в кластере из одного — постоянно (V/02.6 Н1.7). Значения — `x-archive.archiveModes` вида, порядок ничего не значит. `x-archive.archiveModeDefault` — что предлагать при создании: значение уходит явно, нет поля — форма предлагает «Авто» и поле не шлёт. `PATCH` с `properties.recordMode: null` снимает поле, откат возвращает и отсутствие поля.
- **Скан и обход.** `status.observed.archiveJobs: false` — камере недоступны: камера-кластер и чужая камера, таблицы живут в кластере записи, `POST` — `422 NOT_SUPPORTED`, `field: deviceId`. Создание требует `edit` на камеру, правка и снятие — `admin`: иначе `403 PERMISSION_DENIED`, признака в контракте нет, форма показывает отказ и перечитывает список. Встроенный сервер права на камеру не считает: `admin` — администратор или `DEVICES_SETUP`.
- **`status.observed.class` сервера.** Только чтение: `server` или `camera`, у стучащегося в домен тоже. Форма показывает слово в строке «Нераспределённых серверов». Подтверждение при приёме — этап домена.
- **Виды хранилищ.** Вид хранилища — вид объекта `archive.<код>` с профилем `vms.archive/1`, что он умеет — `x-archive` описания вида (схема — `UnitKind.x-archive` в контракте): форма показывает те виды, что отдал сервер, и с полями этого вида, подписи — из описания. Вид вне `GET /kinds` не заводится: `422 NOT_SUPPORTED`, `field: /kind`. `address` решает поля тома: `disk`, `nas`, `bucket`, поэтому `archive.network` у разных систем разный. У w2c пять видов строки `rec/volumes.kind`: `local`, `network`, `backup`, `edge`, `incidents`, `cloud` не объявляется, ADR-0112 доп. (5) п. 2. `recordModes` — режимы камеры на виде: пусто — камеры не привязываются, только `backup` — хранилище бывает лишь дополнительным. `serverWide` — одно на сервер, работает со всеми камерами сервера: строка `readOnly` в `extraArchives` видна у камер сама, посылать её нельзя, изменение хранилища меняет `version` этих камер. `archiveModes` — значения `recordMode` самого хранилища. Эталонный набор `demo.json` отдаёт шесть видов: эти пять (`archive.local`, `archive.network` с адресом `nas`, `archive.backup`, `archive.edge`, `archive.incidents`) и `archive.cloud` с адресом `bucket` — для макета (запрос mockup 2026-11-03); профиль `one-domain`, как w2c, — пять, без `archive.cloud`.
- **`replica` и `backup`.** `replica` забирает записи без постоянного потока. `replicaFrom` у камеры и строки `extraArchives`: `null` — встроенное хранилище, иначе `uid` другого хранилища этой камеры с `x-archive.replicaSource`. Встроенное у камеры или её регистратора; нет его — `replicaFrom` обязателен, `422 VALIDATION_FAILED`. Со встроенного — только основной поток, другой — `422 NOT_SUPPORTED`, `field: /properties/stream`. Из хранилища — поток источника, другой — `422 VALIDATION_FAILED`, `field: /properties/stream`. Цикл и сам у себя — `422 VALIDATION_FAILED`, `field: /properties/replicaFrom`. Источник сняли — запись ждёт, `recordState: waiting`, причина словами, забранное живёт своим сроком. План проверяется по итогу всех шагов одного объекта, а не по шагу. `backup` — только дополнительная запись на виде с `backup` в `recordModes`: живой поток идёт туда лишь на время сбоя основной. Период выбирает сервер, настройки нет. `replicaLagSec` — отставание, только чтение, показ — вкладка «Архив». Потеря минут: запись `replica.lost` в журнале и слово в `recordReason` или `reason`; то же для «источник больше архива». `status.link` камеры (`online`, `offline`) — соединение держателя с устройством (у держателя: `running`, `idle`, `held`), состояние, а не проба: простаивающая камера без потока не опрашивается. Идёт ли видео, связь не говорит: у `replica` постоянного потока нет. Событие `silent` — обрыв открытого потока, а не потеря связи с устройством: у камеры без потока его нет. ADR-0112 доп. (5).
- **Настройки записи.** `recordScheduleId` камеры — расписание режима `sched`, одно на камеру: нет — `422 VALIDATION_FAILED`, `field: /properties/recordScheduleId`; расписание сняли — запись ждёт и говорит причину. `retentionDays` и `minDepthDays` — у камеры и строки `extraArchives`, свои у каждой записи: `retentionDays` хранилища остаётся умолчанием, его правка записи со своим сроком не меняет; глубина больше срока — `422 VALIDATION_FAILED`, `field: /properties/minDepthDays`. `audioDeviceId` — объект `mic` этой камеры, `null` — первый микрофон. Сроки журнала — `Settings.values`: `events.retentionDays`, `alarms.retentionDays`; форма показывает только ключи, которые отдал сервер.
- **Обход и скан архива.** Обход — задача без конца: детектор смотрит архив устройства, поток на сервер не идёт, поэтому камере нужно встроенное хранилище, своё или регистратора. Один на камеру и вид. `keep: hits` сохраняет минуты вокруг находок в `archiveId` этой камеры; архив сняли — обход остаётся с `keep: none`. Скан кончается: `result {end, covered, asked, events, partial}`, итог — `entity.changed` с `kind: archiveScan`. У обоих `mask`, `alarms`, `labels`, `params`. `mask` — зона того же вида, что `zone` детектора, форма берёт её у детектора камеры; `labels` по умолчанию пусты, значение ставит бэкенд. Встроенный сервер считает итог от длины отрезка: 1 событие на 10 минут. В стопку отката задачи не входят: это не настройка оборудования.
- **Карта камеры w2c.** Объект вида `storage` под камерой: правятся только `recordMode` и `sizeBytes` (остальное — `readOnly` в схеме, `Unit.writable`), заводится сам, в перечне хранилищ (`implements=vms.archive/1`) не попадает. Меньший `sizeBytes` стирает старое, как у тома: только с `confirmShrinkBytes` (`x-transient`), равным новому объёму, иначе `422 VALIDATION_FAILED`, `field: /properties/sizeBytes`, в шаге операции так же; поле не хранится. Объём откат не возвращает: шаг `fail NOT_SUPPORTED`, ADR-0112 доп. (6) п. 4. `recordMode` — `always` или `backup`, другое — `422 VALIDATION_FAILED`. `replicaFrom: null` у такой камеры значит запись с этой карты. `Unit.writable` объекта главнее схемы вида: у обычного `storage` правок нет.
- **Том** (`vms.volume/1`). Меньший `sizeBytes` стирает старое: только с `confirmShrinkBytes`, равным новому объёму, иначе `422 VALIDATION_FAILED`, `field: /properties/sizeBytes`; в шаге операции так же. Поле не хранится. `status.observed.shrinkPendingBytes` — объявленная другим писателем меньшая квота, которую ещё не подтвердили. `enabled: false` — том выключен, состояние `off`. Свойство `admits: false` хранилища — новые привязки камер отвергаются, прежние живут; у вида с `x-archive.admits: false` всегда так. Второй том того же хранилища на том же диске — `409 DISK_TAKEN`, в том числе соседней строкой одного `POST /units`. Форматирование (`format`, долгая команда: `202` и операция до конца по часам) том не занимает, как в старом макете: во время него том правится и удаляется любым путём; занят он только для нового `format` — `409 BUSY`. Шаг такой операции — `free`: объект операции не запирается.
- **Потоки и разрешение** (`vms.stream/1`). Поток — дочерний объект вида `stream` под камерой: первый — основной, его `res`, `fps` — это `res`, `fps` камеры. Заводится, правится и снимается путями ядра (`POST /units` под камерой, `PATCH`, `DELETE /units/{uid}`), правка — одиночная операция в стопке отката. Основной поток не удаляется, поток с записью или детектором — тоже. `res` пишется `1920x1080`, латинская x. `resOptions` камеры и потока — варианты устройства, нет поля — ввод руками. `codec` только чтение, `bitrate` нет. `stream` камеры и строки `extraArchives` — `streamId` потока. Дочерними в дереве потоки не считаются (`hasChildren`).
- **Живое видео** (`vms.live/1`). Закладка «Просмотр» в карточке камеры и показ для настройки — один клиент WHEP, порядок V/08.3 Н1.2. `POST /units/{uid}/live {width, height, network?, streamId?}` → `{whepUrl, token, expiresAt, gateway?}`. Дверь соответствует раздаче и `where`: создать раздачу (`409 exists` — норма), отдать дверь шлюза с токеном. `whepUrl` — полный адрес оффера, с `?stream=` или `?width=&height=`.
  - **Клиент.** Офер только на приём, видео и звук, `Authorization: Bearer`, `201`, `Location`. Повторы 404 `not yet`, 500, 503, сбой сети и `503` этой двери — через 1,5 с, всего 21 офер, пока до `expiresAt` не меньше 5 с. 404 `stream refused` — `detail` словами. 403 — дверь заново один раз. Исчерпаны — дверь один раз заново: другой адрес или шлюз дают новую серию, тот же — «Шлюз не взял поток». Отбой — `DELETE` на дверь плюс `Location` свежим токеном, при закрытии страницы — `keepalive`. Обрыв: `failed`, `closed` — 1 с, `disconnected` — 5 с, плюс до 3 с случайно, затем заново.
  - **`expiresAt`** — срок токена, он же предел окна повторов, поэтому не позже конца `grace`. Клиенту его нужно меньше, чем объекту камеры: идущей сессии токен не нужен, только отбою.
  - **Другая сеть.** `409 OTHER_NETWORK`, `params.labels` — метки раздачи. `PUT /units/{uid}/live {network}` переразмещает и рвёт сессии, форма переподключается сама, `403 PERMISSION_DENIED` без права: форма предлагает кнопку всем, право судит система.
  - **Другой кластер, камера за NAT (`direct: false`).** `409 OTHER_CLUSTER`, `params.url`, в форме кнопка «Открыть», как на этапе 7.
  - **H.265** идёт как отдаёт камера. У браузера без него форма отказывает словами до офера, если выбранный поток или все потоки камеры — H.265; статические номера нагрузки уходят в 96–127. Смешанные потоки решает шлюз по оферу.
  - **CSP консоли** задаёт только `script-src`, `object-src`, `base-uri`, `default-src` нет: `connect-src`, `media-src` не ограничены, офер на шлюз другого адреса проходит. Появится `default-src` или `connect-src` — двери шлюзов придётся называть в нём. Шлюз обязан отдать `Access-Control-Expose-Headers: Location`, иначе клиент не прочитает сессию и отбоя не будет.
  - **Заглушка.** `stub://live/whep/<id>` выдаёт только стенд. На него отвечает сама страница, `api/whep-stub.js`: второй `RTCPeerConnection` в странице и тестовая картинка с canvas, без внешней сети, подпись на кадре и поверх него. Файл входит в сборку WebUI, отвечает и на `stub://live/talk/…`: иначе `check_webui` не проверит клиент под CSP; настоящий бэкенд такого адреса не выдаёт. Раздачу встроенный сервер держит 60 с от последнего `POST`.
- **Закладка «Просмотр»: работа с живым (этап 8, часть 2).**
  - **PTZ.** Те же `PUT`, `DELETE /units/{uid}/ptz`, кнопки держат аренду, отпустили — стоп. Задания пресетов на закладке нет, оно на вкладке «Видео». `status.observed.direct: false` — движения нет.
  - **Лента.** `GET /journal?deviceId=&from=&limit=30` с начала показа минус 30 с, дальше `journal.event` потока: опроса нет. `deviceId` журнала — `uid` камеры, в отбор входят и объекты про неё: дети и `eventsrc` с её `cameraId`. Сообщение несёт `payload` — `JournalEvent`, с `cameraId`: карточка источника может быть не в кэше. `stream.reset` — журнал перечитывается. `withheldCount` показан строкой.
  - **Титры.** Строки `kind: text` источника, `fields.lines` — список строк, `fields.word` — совпавшее слово. Цвет, задержка, срок — из карточки источника, она читается один раз на показ. В кадр не вжигается, показывается текстом. Только поверх живого: в записи титров нет.
  - **Разговор** (`vms.talk/1`). `POST /units/{uid}/talk` динамика → `{url, token, expiresAt, gateway?}`. Форма: микрофон, эта дверь, офер только на отправку на `url`. Занятость — `409 busy` от двери на офере, выдача адреса её не судит. `404 not yet`, `500`, `503` — через 1,5 с, всего 9 оферов, после `500` дверь снова. `201` — кнопка конца. Уход с закладки кончает разговор, микрофон закрывается.
  - **Реле.** Команда `output` вида: `POST /units/{uid}/actions/output {state, pulseMs?}`. Дети камеры форма читает `GET /units?parentId=` при открытии закладки: кэш дерева их не знает, пока ветку не раскрыли.
- **Шкала и записи (часть 3, `vms.timeline/1`).** Дверь дорогая, около 1 + R × (1 + 2P) вызовов на чтение: форма читает при открытии закладки и по кнопке окна, таймера нет.
  - **`GET /units/{uid}/timeline?from&to`.** Общее правило страницы: `{items, nextCursor?, unavailable}`, `items` — спаны. Спан: `spanId`, `start`, `end`, `archiveId` (том), `recordingId`, `epoch`, `source`, `backupOnly`, `fenced`. `unavailable: [{what, id, reason}]`: регистратор, том, кластер. Не ответившее не утрачено.
  - **`GET /units/{uid}/playback?spanId&at`** → `{url, from, to, expiresAt, spanId}`. Без `spanId` выбирает сервер: неотсечённый над моментом, нет такого — отсечённый. Токен внутри `url`: элемент видео заголовков не шлёт. Куски по 60 с, сетка от начала спана.
  - **Очередь в форме.** Следующий кусок — от конца поставленного, каждый момент один раз. Выбранный щелчком спан играет, пока идёт, даже отсечённый. Кусок не отдан: подпись, через 5 с новый адрес, не вышло — дальше.
  - **События.** `GET /journal?deviceId=&from&to&source&limit=200`, засечки и список, переход к `occurredAt`. Подсистема — `source`. `truncated`, `withheldCount` сказаны словами.
  - **Заглушка.** Спаны считаются из id камеры и часов, не хранятся: живут и на 250 000 камер. `stub://piece/…` — один файл `assets/stub-piece.mp4`, 60 с тестовой картинки с подписью; он входит в сборку WebUI, как `whep-stub.js`.
- **Удержания и отметки (часть 4).**
  - **`Hold`.** `GET`, `POST /units/{uid}/holds`, `DELETE /holds/{id}`, `POST /holds/{id}/verify`. `id` — ключ `{камера}-{from}-{to}`, целые секунды. Повтор ключа — `200`, `recordingIds` объединяются, заметка и `releasedAt` не стираются. Без `recordingIds` — все записи камеры сейчас. События `entity.*`, `kind: hold`, с `payload.deviceId` (`uid` камеры), всем. Другой кластер — `409 OTHER_CLUSTER`. Битую метку `DELETE` не снимает: предел.
  - **`status.observed.heldBy` тома.** Строка или `null`. Форма читает хранилища вида `archive.incidents` и их тома: держателя нет — предупреждение «удержанное держится, только пока его хранит архив записи».
  - **`status.observed.incidentsLost`, `incidentsAtRisk` тома.** Необязательные, только чтение, том `archive.incidents`: перевод `incidents_lost {метка: секунды}`, `incidents_at_risk [метка]` пульса держателя, V/02.7. Пустых нет. Там же, где держатель: потеря — предупреждение, на весь том, а не только этой камеры; под угрозой — слабее.
  - **Отметка.** `GET`, `POST /units/{uid}/bookmarks {note, type?, occurred?, to?}`, только создать и смотреть. Тип — `moment` или `span` (ADR-0117 доп. (1)): у отрезка `to` позже `occurred`, иначе `422`, `field: /to`; `to` у момента — тоже `422`; у старых строк типа нет — это момент. Отрезок попадает в окно `from`/`to` перечня, если пересекает его. `occurred` — момент на шкале, нет поля — сейчас; при проигрывании форма шлёт момент кадра. Срок — срок журнала. Нет права `bm` — `403`.
  - **«Закрепить».** `POST /units/{uid}/archive-fetch {archiveId, from, to}` → `{accepted, refused: [{from, to, reason}]}`. Интервал — из спанов `backupOnly` и `device`, склейка при зазоре до 3 с. Просьба на сутки, `per_person` 7. `refused` только о подаче, отказ регистратора приходит поздно, в журнале `archive.backfill.refused`. Основной записи нет — `409 NO_PRIMARY`.
- **Выгрузка (ADR-0117).** Предметный API, как шкала: `GET /me/export?ids=<uid,…>`, `GET /units/{uid}/recording-days` (профиль `vms.camera/1`), `POST /exports/check`, `POST /exports` (202), `GET /exports`, `GET`/`DELETE /exports/{id}`, `POST …/cancel`, `POST …/retry-failed`, `POST …/files/{fileId}/link`.
  - **Камера — по `uid`.** `ExportCamera.uid`, `ExportPart.uid`, `ExportFile.uid`, `ExportCheck.files[].uid`, `ExportGrant.devices[].uid` — объект, чей вид реализует `vms.camera/1`. Нет объекта — `404 NOT_FOUND`, другой вид — `422 NOT_SUPPORTED` с `params.kind`, `params.profile`; `field` — `/cameras/i`. Записи камеры — та же шкала, что `vms.timeline/1`.
  - **Заказ и части.** Тело одно у проверки и создания (`ExportCreate`). Часть — камера × запись, ход и итог у каждой; частичный успех — норма. Ход — `export.progress`, итог — `export.finished`, только автору; истина — `GET`. Вид записи в потоке — `exportJob`: код `export` в модели занят видом объекта «Агент экспорта».
  - **Ошибки с путём.** `field` — JSON Pointer по телу: `/cameras/0/area`, `/periods/1/to`, `/password`; ошибки схемы тела — тоже указатель, как на путях ядра. Новые коды: `PASSWORD_REQUIRED`, `NO_RECORDING`, `LIMIT_EXCEEDED`, `EXPORT_EXPIRED` (410), `SUPERVISOR_REQUIRED`, `SUPERVISOR_REJECTED`. `PASSWORD_REQUIRED` система может не отдавать никогда: окно на него не полагается.
  - **Надзор над выгрузкой.** Признак один — `ExportGrant.supervisorRequired`, от `accessSupervision` не зависит: та отвечает только за правку `Role.supervision`. Нет `supervisor` — `403 SUPERVISOR_REQUIRED`, указан и не подходит — `403 SUPERVISOR_REJECTED`, `field: /supervisor`; так же в `errors` у `checkExport` и у `retry-failed`. Повтор — новый заказ: прежний супервизор не действует, его присылают заново. Подводный камень: `Export.request.supervisor` хранит логин, и при повторе его нельзя принять за подтверждение.
  - **Маска, которую система не делает.** `403 PERMISSION_DENIED`, `params.reason: privacy`, `field` — `/cameras/i` или нет; окно пишет текст `ExportGrant.refusal` и не просит пароль.
  - **Область кадра** — `cameras[i].area {x, y, w, h}` в долях кадра, обрезает и видео, и кадр; `w > 0`, `h > 0`, `x + w ≤ 1`, `y + h ≤ 1`, иначе `422`.
  - **Справочник** — `reference.export`: форматы, ступени, пределы. Окно строит списки только из него, необязательное прячет по `export*` в `capabilities.features`.
  - **Файл** — по ссылке с токеном, сроком `limits.linkTtlSec`; дверь отдаёт `attachment` и `Range`. Стенд отдаёт `stub://`. Права стенда — `stand.exportGrant`, `stand.exportDenied` (uid), супервизор — `stand.exportSupervisor {login, password}` (по умолчанию `supervisor` / `supervisor`), сбой части — `stand.exportFail {uid: code}`.
- **Адрес камеры.** `rtspUrl` — чтение и запись. Без него нужны `vendor`, `model`: это адрес драйвера. Ни того ни другого при создании или после правки — `422 VALIDATION_FAILED`, `field: /properties/rtspUrl`. Камера под регистратором идёт через него. `reference.deviceModels` наполняет сервер из описаний драйверов; пустой список форме не мешает, модель вводится руками. MAC камеры, источника и СКУД — только из поиска.
- **Входы и выходы.** Номер — свойство `channel`, внутри своего вида, с 1, сквозной по устройству: у камеры бывают 3 и 7. Событие `io.input` — у вида `sensor`, команда `output` — у `relay`, номера в правиле нет; `match.port`, `port`, если есть, значат то же самое, расхождение — `422 RULE_INVALID`. `match.value`: `active` — начало тревоги, `normal` — конец, считается сравнением сигнала с `norm`. `videoChannel` — с 1.
- **Автоматизация — что считает сервер.**
  - **Проверка правила.** Включённое правило с ошибкой не сохраняется: `422 RULE_INVALID`, что не так — кодом в `params.issue` (`rule.noAction`, `trigger.noTarget`, `rule.targetGone`…). Выключенное сохраняется незаконченным. Те же проверки интерфейс показывает подсказкой заранее.
  - **Запуск** (`/rules/{id}/run`), **пробный запуск** (`/rules/test` — в том числе неприменённого черновика, на выбранных событиях и времени, с выбранными исходами ветвлений) и **повтор невыполненного** (`/rules/{id}/fires/{fireId}/retry`) — трасса `RuleFire`: что пришло, какие проверки (условия, окно, приглушение, окна обслуживания, лимит), что выполнено на каких объектах и почему нет. Всё — **кодами с параметрами** (`device.offline`, `cond.mode`, `ask.answer`…): подписи собирает интерфейс. Новый запуск — `entity.created` с `kind: ruleFire`.
  - **Расписания и режим объекта.** Действует ли расписание и какой сейчас режим, сервер считает в часовом поясе системы (`GET /me` → `timezone`): учитываются особые дни, срок действия, цикл смен, восход и закат. Текущий режим — `GET /modes/current`; в нём нет версии, потому что меняется он со временем, а не правкой. Смена — событием `objectMode`.
  - **История версий.** Версию истории сервер пишет сам при каждом изменении содержимого правила (`PUT`, `POST`, смена состояния в `/rules/update`), с автором и временем. Приглушение и порядок версию истории не пишут. `historyNote` в запросе — пометка: `restore` (возврат к версии), `undo` (отмена — версия, которую отменяют, убирается, если она последняя; «Изменено» — `changedAt`, `changedBy` — и «в наблюдении с» — `logOnlySince` — возвращаются из неё, как было до отменённой правки).
- **Дополнения (2026-10-30, совместимо).**
  - Расписание «Задать только здесь…» может принадлежать правилу: `owner.kind: rule`, `owner.id` — id правила. Правило должно существовать, иначе `422 VALIDATION_FAILED` с `field: owner`. Удаляется вместе с правилом (см. каскады). У нового правила интерфейс задаёт владельца после его сохранения.
  - У источника событий (титры) — `overlayDelayMs` и `overlayDurationSec`: задержка показа и длительность, целые ≥ 0. В правке (`UnitPatch.properties`) — можно `null`.
  - `historyNote.code: undo` возвращает и «Изменено», и «в наблюдении с» (см. «История версий»); версия записи — новая.
- **Страницы и дерево по запросу (этап 7, ADR-0113 доп. (8), (10)).** Режим один на любом размере: форма читает по запросу и на трёх камерах.
  - **Общее правило страницы.** `limit` 1–1000, по умолчанию 200, `cursor`. Ответ `{items, nextCursor?, total?}`, нет `nextCursor` — конец. Пустые `items` при живом `nextCursor` законны. `cursor` непрозрачный, хранит место, живёт круг вида; просроченный или чужой — `422 INVALID_CURSOR`, форма читает с начала. `total` — оценка, только без фильтра. Пределы — `reference.limits`: `pageMax`, `idsMax`, `selectMax`, `watchMax`, `scanPartsMax`; форма их не вшивает.
  - **Перечни.** Страницами: `/units` (объекты любых видов), `/tree/children`, `/journal`, `/operations`, `/rules/{id}/fires`, `/archive-watches`, `/archive-scans`, `candidates` в `/domains/{id}/discovery`, `/access/users`, `/access/groups`, `/access/history`, `/access/cell-history`, `/access/roles/{id}/objects`. Целиком: `/kinds`, `/schedules`, `/day-groups`, `/maintenance-windows`, `/licenses`, `/stream-accounts`, `/rules`, `/rules/{id}/versions`. Домены и серверы — `GET /units?implements=vms.domain/1`, `vms.server/1` (серверов — до `SERVERS_MAX` 500).
  - **`GET /units`** отдаёт объекты `Unit` (`fields` сужает состав), полная запись — тот же объект, `GET /units/{uid}`. Отборы: `q` (имя, короткое имя, свойства с `x-search` и `uid` — только целиком; `fields` — где искать; без `fields` у устройств находит то же, что `/devices?q=` старого макета: имя, номер, адрес, производитель, модель — на demo по «1» 242 устройства), `kind`, `implements`, `status`, `domainId`, `noFolder`, `noRecord`, `noDetector` — ограниченный проход, порядок разделов: не меньше `scanPartsMax` разделов на запрос, дальше страница дописывается до `limit` или до бюджета времени (ниже, «Страница ограниченного прохода»); только `implements` (можно с `domainId`) — чтение по профилю вместо таблиц `/domains`, `/servers`, `/folders`, `/archives`, `/volumes`: по индексу вида, страницы полные; порядок — как у этих таблиц старого макета: домены и серверы — в порядке заведения (принятый в домен или исключённый сервер встаёт последним, как в `/servers`), сначала домены, потом серверы; папки, хранилища, тома — по разделам. `kind` (один или несколько через запятую) вместе с `domainId` и без других отборов — тоже по индексу вида, страницы полные, порядок по разделам (узкое чтение: хранилища нужных видов домена). `kind` без `domainId` остаётся проходом, как `type` у `/devices`: страница дописывается по общему правилу прохода (ниже, «Страница ограниченного прохода»), бэкенд вправе отдать её короче. Выбор цели правила читает одну первую непустую страницу и показывает в дереве то, что пришло: у заглушки на demo — все 143 камеры (старый макет брал 76 — первую страницу из `scanPartsMax` разделов); `serverId`, `parentId`, `archiveId`, `ref` — один член, порядок по имени; `ids` — до `idsMax`; `folderId` — постоянная цена, дверь членов папки, страница бывает короче и пустой. `noFolder`, `noRecord` — только отбор: групп «Без папки», «Без записи» на сервере нет, узлы строит форма, числа у них — по загруженному. `noDetector=<вид>` — камеры без детектора этого вида, по `status.observed.detectorKinds` камеры (виды встроенных и серверных детекторов, `cameraId`, без повторов): отбор ассистента «камеры без детектора движения», ADR-0093 доп. (15) п. 4.
  - **Камера-кластер в перечне:** `parentId` — `null`, сервера нет, `hasChildren: true` значит «может быть»; у объекта в перечне и полного объекта одна `Unit.version`. `/objects/delete` сверяет её. Выбор и удаление — до `selectMax`, сверх предела `422 VALIDATION_FAILED`.
  - **Дерево.** `GET /tree/children?layout=&parentId=`, `layout`: `folders`, `servers`, `archives`, `detectors`. Счётчиков у узлов нет, ответ несёт `parentCount`. `GET /tree/paths?layout=&ids=` — цепочки от корня для объекта любого вида (по `parentId`, у корня домена — по раскладке: папки объекта, хранилища записи, сервер), шаг — `{id, kind, name}` с кодом вида; у объекта в нескольких папках цепочек несколько. Порядок по имени только внутри члена, на верхнем уровне и в папках — порядок сервера, неизменный между страницами, не алфавитный.
  - **Папки.** Папка — объект вида `folder` (`vms.folder/1`): `name`, `parentId` — подпапка или корень домена. Состав — `Unit.folders` у членов: `PATCH /units/{uid} {folders}` у объекта или шаги `folders` (и `patch` только с `folders`) одной операции `POST /operations`, шагов по папкам до `selectMax`; папки вне отката: шаг отката `fail NOT_SUPPORTED`. Папки, и создание, и состав, ведёт только «Администратор» (`403 PERMISSION_DENIED`) и только при связи с центром домена папки (`409 SERVER_OFFLINE`); сервер-исполнитель объекта здесь не участвует: правка только `folders` не идёт на его сервер.
  - **Права.** `GET /access` — `version`, `roles` с `objectAccessCount`, `catalogs`. `POST /access/apply {dryRun?, version, changes, history, cellHistory}`, `changes: [{kind, id, op, value}]`, `If-Match` больше нет: `version` в теле, чужая правка — `412 VERSION_MISMATCH`.
  - **Поток при нескольких экземплярах (ADR-0112 доп. (12) п. 2).** Список наблюдаемых держит поток. `PUT /stream/{clientId}/watch` не тому экземпляру — `404`: форма переоткрывает поток с `GET /stream?watch=<id,id,…>`, до `watchMax`, сверх предела — `422`, `field: watch`, и перечитывает кэш, как при `stream.reset`, полный перечень не читается. Такой поток список уже держит, поэтому после его `stream.hello` форма шлёт `PUT` только если список разошёлся, в том числе после переподключения браузера по старому адресу. Стенд: `POST /test/stream-elsewhere` делает открытые потоки чужими для `PUT`.
  - **Поток.** Первое сообщение — `stream.hello {clientId}`. `PUT /stream/{clientId}/watch {ids}`, до `watchMax`: события устройств — только по ним и их детям, остальное всем. `tree.changed {layout, parentIds}` — ветка изменилась вне наблюдения, частота от размера домена не зависит. `stream.reset`: форма перечитывает только то, что есть в кэше.
  - **`Domain.stateSummary?`** `{total, offline, silent, at, unread?}`: числа не пересекаются, выключенные вне `total`. Поля нет, пока круг не прошёл. Встроенный сервер считает `silent` как `online: false` с `fault: drv`, круг — 20 минут его часов. Круг считай одним проходом на все домены, а не проходом на домен: на `xl` четыре домена по 250 000 камер, и четыре прохода по миллиону камер — заметная задержка старта. Встроенный сервер так и делает (`domainSummary` в `profiles.js`: `Map` домен → итог; итог, которому круг ещё не вышел, проход не трогает).
  - **Страница ограниченного прохода — дописывай до `limit` или до бюджета ~100–200 мс.** Проход по разделам не отдаёт ответ, пока страница не набрала `limit`, не вышел бюджет времени запроса или не кончились разделы; только тогда — `nextCursor`, если проход не дошёл до конца. Продолжение — с места остановки: ничего не теряется и не повторяется. Иначе редкий поиск по большому домену — сотни почти пустых страниц (на `large` у заглушки с 4 096 разделами и `scanPartsMax` 8 — 512 запросов на одно имя), и на каждую форма отвечает волной и перерисовкой. Пустая страница с курсором законна — бюджет вышел, ничего не нашлось; форма её выдерживает. `scanPartsMax` — нижняя граница разделов на запрос, форма на него не опирается: поле остаётся в `reference.limits`. Заглушка — 40 мс (`SCAN_BUDGET_MS`): она работает в той же вкладке, что и страница. Проверка: `tests/api-pages.js` («страница дописывается…», «бэкенд вправе страницу не дописывать…»).
  - **Заглушка.** `partsCount`, порядок разделов, курсор и `stand.hiddenIds`, `stand.unread`, `stand.summaryOff`, `stand.sparsePages` (страница не дописывается: ровно `scanPartsMax` разделов, пустые страницы с курсором подряд) — приёмы стенда, не норма. `fixture=large` считает записи из чисел при загрузке: 250 000 камер, 500 серверов; `fixture=xl` — тот же `large` с другими числами: 1 000 000 камер, 2 000 серверов, 1 200 папок в четырёх доменах (Москва, Санкт-Петербург, Казань, Новосибирск), каждый — как `large` (`stand.large.domains`, `domainNames`; README, «Набор профиля one-domain»).
- **Домен шире кластера (вариант В ADR-0110).** Домен в ответе один, `GET /units?implements=vms.server/1` — серверы всех кластеров, имя `<кластер>/<сервер>`. Записи кластера в контракте нет. Списки зависят от того, кто спрашивает.
  - **Потеря связи:** `status.link: offline` домена и `stream.reset`, ответы несут только свой кластер, `entity.deleted` не шлётся. Форма пишет «нет связи с доменом, показано только своё» и не считает пропавшие цели правил удалёнными. Папки без связи — `409 SERVER_OFFLINE`, шаг `folders` — `fail SERVER_OFFLINE`, строка `POST /units` с `folders` — `failed` с `SERVER_OFFLINE`, `field: /folders`.
  - **Копии записи (V/11.4 Н1.14).** `RecordingTargetRequest {serverId, copies: [serverId]}`, `status.observed.recordingTarget` камеры так же. **Несовместимо с этапом 7:** `copies` было числом. `serverId` — основной приёмник, `copies` — дополнительные, без него, порядок значимый. Копия — это кластер: на кластер один сервер. Повтор, несуществующий, два сервера одного кластера, сервер кластера основного — `422 VALIDATION_FAILED`, `field: copies`, склеивать молча нельзя. Пусто — копий нет. На чтении может вернуться другой сервер того же кластера: назначение держит кластер. Карту кластера origin V/11 добавляет сама и в ответ не отдаёт, стенду это не нужно. Кластер на стенде — начало имени `<кластер>/<сервер>`.
  - **Правка камеры-кластера.** Применяет её камера с периодом отчёта. Срок ответа вышел — `409 SERVER_OFFLINE`, `params: {targetId, kept}`: правка хранится и применится, это не отказ, откатить её нельзя. У шага операции — `code`, `params` с теми же `targetId`, `kept`. Повтор той же правки новую не заводит, другая до применения первой — `412`. Форма пишет «Принято, применится», строкой элемента, и говорит словами про `412`.
  - **Камера w2c** — объект `camera` без своего сервера: `status.observed.direct: false`, адресных свойств нет, `Unit.writable` без них, запись — `422 NOT_SUPPORTED`. Молчит — `409 DEVICE_OFFLINE`. Движение арендой — `422 NOT_SUPPORTED`, `field: direct`. Сохранение положения пресета, `PUT {}`, — `409 OTHER_CLUSTER` без ссылки, предел: положение пишет устройство в момент просьбы (ADR-0111 доп. (1), V/11.4). Подпись `PUT {name}` работает: положения не трогает. `status.observed.recordingTarget`, `PUT /units/{uid}/recording-target` — приёмник записи, `null` снимает.
  - **`serverId` камеры.** Форма не решает сама: сервер объявляет его в `Unit.writable`. Объявлен — настройка, как в наборе `demo`. Не объявлен — наблюдение: форма не закрепляет сервер, выбор хранилища зависит только от вида.
  - **Другой кластер:** живое и PTZ — `409 OTHER_CLUSTER`, `params.url`, в форме кнопка «Открыть».
  - **Правка не сразу.** Устройство другого кластера и камера w2c правятся каналом домена, 2–30 с: `PATCH` держит ответ до 30 с, клиент ждёт 35 с. Ход по шагам — `POST /operations`.
  - **Поиск и `probe`** идут на серверах кластера входа. Параметры `login`, `password` команды `probe` (`POST /kinds/camera/actions/probe`) необязательны.
  - **Вход.** Один адрес, другой — только если этот недоступен: операции, откат, память `idempotencyKey` у адреса свои. После `5xx` и смены адреса запись сначала перечитывается.
  - **Приём.** `status.observed.fingerprint` сервера, `POST /units/{uid}/move {parentId: <домен>, params: {fingerprint}}`: без него или с чужим — `409 FINGERPRINT_MISMATCH`; исключить — `parentId: null`. Только администратор домена, иначе `403`. Камера после приёма — `entity.deleted` сервера и `entity.created` камеры, ответ — объект камеры. Создание сервера (`POST /units` вида `server`) и опрос адресов (`POST /kinds/server/actions/probe`) система может не объявлять.
  - **Ретрансляторы.** `GET /domains/{id}/relays`, `GET /domains/{id}/relays/{name}`: `members` могут быть и кластерами, и камерами, закладка «Топология» сверяет их с именами кластеров.
- **Сценарии между камерами (V/07.5, ADR-0112 доп. (10)).** Отдельно от `Rule`: документ домена `GET`, `PUT /domains/{id}/scenarios`, пишется целиком с `If-Match`, чужая правка — `412`, это предел: правки разных сценариев конфликтуют. Предел `reference.limits.scenariosMax`, виды событий `reference.scenarioKinds`. Форма говорит `deviceId`, `backend` выводит `ref`, `when.member`, `then.member`. Состояние — `GET /domains/{id}/scenarios/status` из пульса `shared`, версию не двигает. Вне отката, истории версий нет. Отказ `Rule` из нескольких кластеров остаётся `field: steps`. Встроенный сервер документ хранит и не исполняет, состояние задаёт `POST /test/events` `scenario.outcome`.
- **Роль на весь домен (запрос 11 п. 15, ADR-0110 Д-3).** Для человека роль одна, запись одна. Права расходятся по кластерам групповой операцией: итог на каждый кластер, отказ одного не откатывает прочие. `AccessApplyResult.notApplied: [{cluster, serverId?, roleId?, code}]`, `clusters` — на сколько кластеров расходилось. `RoleRow.spread: [{cluster, state, at?}]` — расхождение, пока оно есть: `local`, `pending`, `refused`, из `role_spread`. Повтор — `POST /access/apply` с `retryClusters`, `changes` пустые. Люди, группы и сами роли пишутся одной записью. Встроенный сервер считает кластер по началу имени сервера, отказ задаёт `stand.refuseClusters`.
- **Автоматизация — ответ оператора и ход правила.** Оператор работает здесь, в этой форме: другой консоли нет (ADR-0112), экран ответа — колокольчик в шапке, он читает двери ниже. Контракт ответа — `GET /rule-prompts`, `POST /rule-prompts/{id}/answer`, события `prompt.opened`, `prompt.closed`. Форма шлёт `GET /rule-prompts` сразу после старта, поэтому дверь в 15 запросов старта не входит; опроса нет: без событий потока экран устаревает.
  - **Запуск ждёт** на шаге `ask` и на уровнях `escalate`: `RuleFire.result: waiting`, строка шага `state: waiting`. Решён шаг — запись меняется, `entity.changed` с `kind: ruleFire`, запуск идёт веткой и следующими шагами. `/rules/test` не ждёт: исходы задаёт `branches`. `/fires/{id}/retry` шаги ожидания не повторяет. «Только журнал» идёт тем же ходом, но никого не спрашивает: `RulePrompt` не заводится, `ask` ждёт срок и кончается веткой `default`, `escalate` — сроком последнего уровня (ADR-0112 доп. (9) п. 2). Пределы п. 4: роль без строк грантов не видна — `canAnswer` ложь, ответ `403`; кончившийся вопрос после ухода имени запуска из `done` — `404` вместо `409`. Встроенный сервер судит роль по строкам `folderAccess`, `objectAccess`, уход из `done` — сутками после закрытия: срок условный.
  - **Вопрос** — `RulePrompt`, по одному на `ask` и на уровень `escalate`. Уровень открывается своим сроком, прежний остаётся открытым до конца эскалации: `until` — конец последнего уровня. `ack` на любом открытом уровне останавливает эскалацию и закрывает все её вопросы. `canAnswer` говорит, есть ли роль у спросившего: экрану не надо считать роли самому.
  - **Ответ.** Отвечает человек с ролью шага, `403` иначе. Считается первый по времени. `202` значит «принято»: система вправе судить ответы своим проходом, итог — `prompt.closed` с `reason`: `answered` (с `answer`, `by`), `expired`, `reset`, `stopped`. На закрытый ответом вопрос — `409 BUSY`, `params.reason: answered`. Срок вышел, запуск снят — `409 NOT_RUNNABLE`, `params.reason.code: over`.
  - **Тревога** — событие журнала, а не запись: жизненного цикла нет, закрывать нечего, поэтому `alarmclose` система может не объявить. Квитируется шаг эскалации. `stop: reset` — конец события входа: сигнал того же входа вернулся в норму; запуск без события (`run`, цепочка) им не кончается.
  - **Пределы.** `wait`, `waitEvent`, `ask`: 1…3600 с. `escalate`: до 5 уровней, `waitMin` 1…120, у последнего 0…120. Сверх — `RULE_INVALID`, `control.sec`, `escalate.tooMany`, `escalate.wait`; выключенное хранится. `repeat: queue` — очередь до 16 запусков, сверх — как `skip`.
  - **Перезапуск.** Ход пишется в строку запуска: срок считается от записанного момента, шаг, поданный перед падением, подаётся снова с тем же именем и не выполняется дважды. Правка, выключение, удаление правила, смена «Только журнал» снимают запуск: его вопросы закрываются, `reason: stopped`. Приглушение и порядок запуск не снимают. Встроенный сервер держит ход в памяти, перезапуска у него нет.
  - **Права при записи.** Автор отвечает за всё, что правило называет: устройства событий и шагов, папки, серверы, домены, цель `waitEvent`; условия и `exclude` не судятся. Нет права — `403`, `params.target`, и у выключенного тоже. Судится только запись: снятие права у автора правило не останавливает. `/rules/update` не судится: состав целей он не меняет. `runAsRoleId` сужает выполнение: шаг без права у роли — `fail`, `role.denied`; роль автор выбирает любую.
- **Автоматизация — поля и действия.**
  - `Rule.validForSec`, 10–600, нет поля — 30: сервер отдаёт его всегда. `Rule.status` только для чтения, `{state, reason}`: `watching`, `refused`, `unfit`, `unchecked`; у выключенного поля нет, в версию не входит, события не шлёт. `RuleTrigger.match` открыт: любой ключ, сравнение строгое, с типом.
  - `det/detect` — детектор на камере на `minutes`, 1…1440: повтор продлевает срок, свой включённый детектор этого вида второго не заводит. `det/scan` — проверка архива за окно `beforeSec`, `afterSec` вокруг события, 0…3600, умолчание 60; оба нуля — `action.scanWindow`. `archive` — хранилище записи камеры. Камере без записи — шаг `fail`, `target.noRecord`, правило `unfit`.
  - Правило на несколько доменов: `serverId` выбирает домен, цели только из другого — `422 VALIDATION_FAILED`, `field: serverId`. `reference.ruleCrossDomainActions` объявляет, что такое правило исполняет, другой шаг — `422 NOT_SUPPORTED`, `field: steps`, `rule.crossDomain`. Поля нет — ограничения нет. `Settings.values["alarms.domain"]` — что считать тревогой на весь домен.
- **Ассистент: план правил (ADR-0112 доп. (8), V/10.7).** Поля типа в `AssistTurnRequest` нет: что за реплика — настройка устройств, правило или вопрос о системе, — бэкенд решает сам по каждой реплике, в одном разговоре бывает и то, и другое; выбранное он держит в себе, в событиях его нет. Встроенный сервер решает по словам просьбы вместе с прежним `context`: «сколько», «покажи», «дай список» — вопрос о системе, конечное событие `answer {text, context}`; слова правил — план правил; иначе — план настройки. План — `AssistEvent.rules: [{table, op, id?, ref?, body}]`: `table` — `scenarios`, `schedules`, `windows`, `op` — `create`, `update`, правка только у правил: расписание и окно план заводит, контракт иного не допускает, форма такую строку отказывает без записи. `ref` — имя нового расписания, ссылка на него `"@<ref>"`. `body` — поля `Rule` контрактными словами, у `update` только изменённые.
  - **Ход ничего не пишет.** Пишет человек, нажатием, своей сессией, по порядку записей: `POST /rules`, `PUT /rules/{id}`, `POST /schedules`, `POST /maintenance-windows`. Расписание, на которое ссылается только окно, отдельно не пишется: форма подставляет его строку объектом в `schedule` окна. Есть ссылка и от правила — своя запись, у правила id созданной строки, у окна та же строка объектом: ссылок дверь окна не берёт, окно с готовым расписанием несёт копию его строки. `PUT` — запись целиком: чтение поверх изменённых полей, версия чтения в `If-Match`. Форма читает запись, когда показывает план: человек видит разницу, а изменившееся после показа даёт `412 VERSION_MISMATCH`.
  - **Новое правило** заводится `logOnly: true` или выключенным, никогда — действующим: форма правит тело сама, что бы ни пришло в плане. `logOnlySince` — день записи по часам сервера в поясе системы: поле — дата. **Новое окно** заводится `enabled: false`: наблюдения у него нет, включённое сразу и молча глушит рабочее правило. Недостающие поля `RuleWrite` — умолчания перевода. Правка действующего правила наблюдения не заводит, это предел: форма показывает «было → станет», выпавшие условия и шаги отмечены.
  - **Отказ** стоит за своей строкой: записанное остаётся, отката нет, запись со ссылкой на несозданное расписание не идёт и называется. Что форма не выражает, отказывает ассистент (`refused`), сама форма принимает любой законный `RuleWrite`.
- **Ассистент: план выгрузки (ADR-0093 доп. (47), V/11.20).** «Выгрузи», «экспорт», «кадр с камеры» — конечное событие `plan {summary, context, export}`: `export` — `AssistExport`, тело `ExportCreate` без `password`, `supervisor`, `idempotencyKey`. Ход ничего не пишет. Такой план бывает, только если объявлен `createExport`: справочник для модели — `reference.export`, время — `me.serverTime`, `me.timezone`. Права, пароль, супервизор, `BUSY` и наличие записи ход не судит: окно открывает заказ в разделе «Экспорт», зовёт `POST /exports/check`, показывает `errors` у своих полей, пароль и супервизора вводит человек, `POST /exports` — по кнопке «Экспорт». Камеры заказа — `uid` объектов вида с профилем `vms.camera/1` (`ExportCamera.uid`). Встроенный сервер: камеры по словам имени, «кадр» — кадр архива минуту назад, «живой кадр» — `source: live`, иначе видео за последние N минут (10 по умолчанию); маски и облако — `refused`.
- **Автоматизация — версия записи.** Правила выполняют то же обязательство, что и остальное. «Отменить» и «Вернуть эту версию» возвращают **содержимое**, но версия записи — новая. Приглушение до срока хранится как `until`: когда срок истёк, запись не менялась, версия та же («приглушено сейчас» клиент считает от `serverTime`). Расписание, на которое ссылается правило, — отдельная запись: его правка версию правила не меняет. Режимы объекта — одна версия на весь список, как у опций.
- **Права администратора.** Встроенный сервер судит `POST /access/apply`, папки и их состав, почту, права команд (`ActionDescriptor.right`), событий и действий правил, предметных путей (`apiRights`): остальные запросы идут от `me` набора без проверки. В продукте:
  - операции раздела проверяются по функциям роли администратора (`DEVICES_SETUP`, `ARCHIVES_SETUP`, `DETECTORS_SETUP`, `PROGRAMMING_SETUP`, `USERS_RIGHTS_SETUP`, `SETTINGS_SETUP`, `DOMAIN_MANAGING_OPS` из `reference.access.features`); нет права — `403 PERMISSION_DENIED`;
  - объект, который администратору не виден, ведёт себя как несуществующий: `404 NOT_FOUND`, в списках его нет;
  - для тестов прав у стенда есть `actAs`.
- **Итоговый доступ.** Форма считает то, что решит `may` платформы. Внутри роли действует первый ярус, где у неё есть значение: исключение объекта, иначе ближайшая папка, где оно задано, из нескольких папок наибольшее, иначе умолчание. Между ролями наибольшее: исключение остаётся в своей роли и не отнимает того, что даёт другая. Встроенная роль решает раньше всех. Пары из `reference.access.joins` дают вместе уровень выше обоих: `MON` и `ONLY_ARCHIVE` — `ARCHIVE`, потому что сервер считает каждую подсистему отдельно. Прототип 11 с исключением сильнее других ролей отклонён ADR-0099.
- **Функции и уровень.** Функция настройки действует там, где уровень этой роли что-то даёт в этой подсистеме: `RoleGlobal.feat`. Тревоги и отметки: `RoleGlobal.alert`, `RoleGlobal.bm`.
- **Пароль.** `password` в `AccessUserWrite` только на запись: у нового пользователя и при смене. В ответах `hasPassword` и необязательное `passwordByAdmin`. Политика — `reference.access.passwordPolicy`, отказ `422 PASSWORD_POLICY`. У пользователя из каталога пароля нет: `422 VALIDATION_FAILED`.
- **Кто применяет.** Администратор — всё. Человек с `USERS_RIGHTS_SETUP` ведёт пользователей, группы, роли и права, камер и архива функция не даёт. Он не трогает «Администратора»: не назначает и не снимает, не меняет, не выключает и не удаляет его пользователей, не меняет им пароль, не меняет группы с ним, не включает и не снимает `USERS_RIGHTS_SETUP` у роли. Такой пакет — `403 PERMISSION_DENIED` целиком, ничего не записано. Судится разница: строки, которых пакет не меняет, не проверяются. Цель не прочитать — `503`. Остальные применять не могут. `dryRun` судит только черновик.
- **Повышение.** «Администратора» нельзя назначить, напрямую или через группу, пользователю, чей последний пароль задал не он сам и не администратор: `409 PASSWORD_NOT_ADMIN`, `field: roleIds`, `params.id`. Администратор сначала меняет пароль, можно в том же пакете. `passwordByAdmin: false` — форма предупреждает заранее.
- **Почта.** `AccessUser.email` видят администратор и люди с `USERS_RIGHTS_SETUP`, остальным пустая строка, кроме своей записи.
- **Папки.** Создание, правку и удаление папки и состав папок (`folders` объекта: `PATCH /units/{uid} {folders}`, шаги `folders` и `patch` только с `folders`) ведёт только встроенная роль: функции роли и `folderAccess` этого не дают, иначе `403 PERMISSION_DENIED`, у шага — `fail PERMISSION_DENIED`. Связь судится центром домена папки, а не сервером объекта.
- **Права пользователей — снимок и пакет.** `POST /access/apply` принимает права целиком (`AccessWrite`) с версией снимка. Сервер проверяет:
  - уровни, функции, запреты и плагины есть в `reference.access`: иначе `422 NOT_SUPPORTED` с путём поля. Интерфейс строит списки только оттуда: вида нет в `levels` — нет столбца, уровня нет — нет в выборе. Подписи держит у себя по коду, незнакомый код показывает как есть;
  - имена ролей, групп, каталогов и логины не повторяются, без учёта регистра (`409 NAME_TAKEN`, `LOGIN_TAKEN`);
  - ссылки ведут в существующие записи (`422`);
  - встроенная роль «Администратор» (`global.unr`) одна: меняются только её назначения, остальное — `409 BUILTIN`, удалить нельзя. `unr` у другой роли и снятие `unr` у встроенной — `422 NOT_SUPPORTED`, `field: global.unr`. Исключения других ролей на её пользователей не действуют, администратором делает назначение;
  - защиту от самоблокировки (`409 SELF_LOCKOUT`): остаётся хотя бы один включённый бессрочный администратор. Срок учётной записи, срок назначения или срок ролей группы последним не считаются, иначе система запиралась бы сама. Текущий администратор не снимает с себя роль и при втором администраторе, никто не выключает и не удаляет сам себя.
  
  `dryRun: true` — только проверка. Состояние синхронизации каталогов и групп (`status`, `lastSyncAt`, `message`, `entries`) ведёт сервер: присланное клиентом для существующих записей не берётся. Записи истории приходят текстом с указанием, кого касаются; время и автора ставит сервер.
- **Долгие действия.** Поиск устройств в сети (`POST /domains/{id}/discovery`), форматирование тома, синхронизация каталога и групповые операции отвечают сразу (`202`, состояние «идёт»), а итог приходит в поток. Новый поиск заменяет итог прежнего; второй запуск во время поиска — `409 BUSY`, клиент подхватывает идущий. Добавленное из найденного (`candidateId`) уходит из итога поиска.
- **Коды ошибок** — схема `ProblemCode`, тело — `application/problem+json`: `{code, message, field?, params?, current?}`. Интерфейс показывает свои тексты по `code`, поэтому новый код без согласования с фронтендом пользователь увидит как «ошибка: КОД». Тела запросов проверяются по схемам: лишнее поле, чужой тип, значение не из перечисления — `422 VALIDATION_FAILED` с `field`.
- **Отказ инфраструктуры (5xx).** Перед бэкендом может стоять консоль или прокси: `502`, `503`, `504`, код `UPSTREAM_UNAVAILABLE`, при `503` — `Retry-After`, тело — `Problem`, если есть. Интерфейс показывает «сервер недоступен, повторите» и сам запрос не повторяет. Запись после 5xx могла пройти: повтор — с тем же `idempotencyKey`, где он есть, иначе после перечитывания.
- **Время в потоке.** `at` в `StreamMessage` — время события на сервере, а не отправки: у изменений записей — когда изменение принято хранилищем, при досылке после переподключения прежнее. В `AssistEvent` — когда бэкенд произвёл событие.
- **Ассистент** (`POST /assist/turns`, возможность `assist`). Модель, инструменты и проверка плана — на бэкенде, клиент ведёт разговор и показывает план. Состояния у бэкенда нет: `context` клиент возвращает как есть. Секреты — отдельным массивом, в `context` их нет, модели значение не уходит: бэкенд сам подставляет его в `patch` строки плана. Без «Применить» ничего не пишется. План настройки форма применяет групповой правкой: объекты плана — в дереве отбором и выбором, значения — в черновике групповой карточки по объектам, «Применить» — одна операция `POST /operations` с `version` плана в `expectedVersions`; объект изменился после плана — `412 VERSION_MISMATCH`, ничего не записано. Частичных планов нет. Поток без завершающего сообщения — обрыв, клиент показывает `UPSTREAM_UNAVAILABLE` и повторяет только по просьбе человека.
- **Ассистент: отбор `found` (ADR-0093 доп. (14), (15)).** «Дай список», «покажи», «выведи» — конечное событие `found {text, context, conditions, ids | filter, total?, truncated?, action?}`, ничего не пишет. Отбирает бэкенд по свойствам объектов, не модель: модель составляет `conditions` словами контракта. Ровно одно из двух: `ids` — `uid` объектов по имени, без повторов, до `selectMax` 500, когда бэкенд отбирает сам (охват до `LIST_MAX`); `filter` (`AssistFoundFilter`: `kinds`, `implements`, `q`, `fields`, прочие — как у `GET /units`) — когда больше: форма листает их тем же ограниченным проходом, что фильтр дерева. `total` — только при полном проходе, иначе поля нет и стоит `truncated`; больше 500 в `ids` — первые и `truncated`. Найдено 0 — `found` с `ids: []`, не отказ. `action` — команда вида над отобранным, её выполняет человек. Разговор продолжается с `context`. Встроенный сервер отбирает по словам: вид («камеры», «контроллеры»), запись (нет, всегда, по движению), включена, на связи, производитель, папка, «имя содержит», «без детектора движения»; без условия — `question`.
- **Ассистент: учебные ссылки (`answer.learn`, запрос w2c, ADR-VMS-0004).** На просьбу научить («покажи, как создать правило», «как настроить детекторы») бэкенд отвечает обычным `answer` и, если в каталоге обучения консоли есть подходящие главы, полем `learn: [{catalog, topic, chapter}]` (`AssistLearnLink`, 1–3 ссылки): `catalog` — `version` каталога (`sha256:…`), `topic` и `chapter` — устойчивые ID темы и главы (`rules`, `rules.simple`). Каталог — `learn-catalog.json` сборки WebUI (`tools/build_webui.py`, его пишет `node tools/learn_catalog.mjs` из тех же `assets/tour.js` и `tour-demos.js`, что исполняет показ): `format`, `version`, `available`, `topics[]` с `id`, `title`, `goal`, `lang`, `fixture` и `chapters[]` с теми же полями. `version` — SHA-256 строки `JSON.stringify({format, topics})` (в Python — `json.dumps(…, ensure_ascii=False, separators=(",", ":"))`), меняется при любой правке каталога. Сборка `--without-learn` кладёт тот же файл с `available: false` и пустым `topics`: ссылок тогда не давать. URL, разметки, селекторов и команд в ссылке нет: карточку («Открыть учебный пример»: название, цель, язык) и запуск форма берёт из своего каталога, показ запускает человек кнопкой. Ссылка на главу, которой нет, или на другую `version` не запускается: форма предлагает свой каталог. Подходящей главы нет — `answer` без `learn`. Встроенный сервер подбирает главу по словам просьбы в названиях и цели (`assistLearnStub`), каталог ему даёт страница (`ConsolemServer.create({learn})`); это не модель. Имена полей, формат и место каталога — предложение w2c: их утверждает владелец договора.
- **Служба демо-страницы.** Страница на Pages статическая, сервер живёт в браузере, модели в ней нет. С `?assist=URL` ход идёт из браузера прямо в службу: `POST <адрес>/assist/turns`, куки не уходят, те же `AssistEvent` потоком. Своих данных у службы нет: `AssistTurnRequest.world` (`AssistWorld`) несёт снимок встроенного сервера; необязательные `roles` — только `id`, `name` из `GET /access`, `servers`, `licenses` — как в `GET`: читать нельзя — ключа нет, служба отвечает «этих данных нет». Поля `kind` нет ни в запросе, ни в событиях: тип выбирает служба по каждой реплике и держит в себе, форма тип не показывает и не выбирает; лишнее поле в событиях (мост Пилота шлёт `kind` в `progress`) форма молча пропускает. `explain` — вопрос о системе, только чтение: конечное событие `answer {text, context}`, плана нет, форма подписывает его как ответ ассистента: в замере Пилота 27 из 30, бывают уверенно неверные числа. Тип выбирают так же, как у встроенного сервера (см. план правил выше). **V/11 поле `world` не принимает и не отдаёт**, код доступа и `secrets` здесь не про него: бэкенд читает свою систему сам, сессия — его. Снимок собирается теми же обработчиками, только на наборе `demo`, с `?api=` службы нет. `secrets` в службу не уходят никогда: форма не отправляет и просьбу о пароле, и ответ на вопрос о пароле. Служба открыта всем: кода по умолчанию нет. `401` службы — не выход из системы: `onUnauthorized` клиента не вызывается, код сбрасывается, появляется поле кода, и пока кода нет, отвечает заглушка. `X-Assist-Code` уходит, только если код введён. Без адреса — заглушка, как раньше. Стенд: `ASSIST_BRIDGE_URL=… node tools/serve_api.mjs` ведёт ход `?api=` стенда в мост Пилота, без `world`.
- **Идентификаторы** — UUID. Записи «Оборудования», хранилищ, правил, расписаний, особых дней и окон обслуживания создаёт сервер и выдаёт id в ответе. Номер устройства (`identifier`) не задан — сервер выдаёт следующий свободный среди камер, регистраторов, источников событий и СКУД; занятый — `409 IDENTIFIER_TAKEN`. Роли, пользователи, группы и каталоги создаются в черновике прав, а режимы объекта уходят списком целиком, поэтому их UUID задаёт клиент, а сервер принимает их как есть. Устаревшие ссылки в данных — ошибка бэкенда, а не повод для эвристики: права ролей ссылаются на папки и объекты по id.
- **Что считает сервер, а что клиент.**
  - **Сервер:** версии, каскады, выдачу номеров, проверку дисков тома (`409 DISK_TAKEN`), перенос при удалении, защиту от самоблокировки, ход долгих действий, сдвиг сроков по своим часам (`GET /me` отдаёт `serverTime` и `timezone`), проверку и запуски правил, текущий режим объекта, историю версий правил.
  - **Клиент:** дерево и счётчики, поиск по всему, план «было → станет», последствия черновика прав для людей и вкладку «Проверка», подсказки об ошибках правил и «Проверить все правила», превью расписаний — это показ над прочитанным.
- **Что встроенный сервер упрощает — так переносить нельзя:**
  - нет входа, сессий и прав администратора (см. выше); данные живут в памяти вкладки и пропадают при перезагрузке;
  - ассистент — заглушка с записанными ходами: разбор по словам, модели и проверки плана нет;
  - в сеть он не ходит:
    - «отвечает ли адрес» — по хешу адреса;
    - модель устройства — по сумме чисел адреса;
    - проверка подключения к NAS или бакету — по заполненности полей;
    - синхронизация каталога всегда «изменений нет»;
    - имя, нагрузку и диски нового сервера он придумывает;
  - поиск в сети находит то, что записано в `network` набора, и отдаёт заводские логин и пароль найденных (`DiscoveryCandidate.password`) — открытым текстом;
  - времена фиксированы: шаг операции — 90–230 мс, находка — раз в 140 мс, форматирование и синхронизация — 1,5 с;
  - отказы шагов операции — только `SERVER_OFFLINE`, `LICENSE_EXCEEDED`, `VERSION_MISMATCH`. В продукте нужны и `DEVICE_OFFLINE` (учётные данные и видео не применить к устройству без связи), и отказы самого устройства;
  - правила не срабатывают сами — ни по событиям, ни по расписанию: журнал запусков — демо-история набора (её посчитал тот же движок, `tools/fixture_fires.js`), «Запустить», пробный запуск и повтор. Действия ничего не делают с устройствами: «Выключить камеру на время» камеру не выключает;
  - исходы `waitEvent` в демо заданы номером запуска, `wait` не ждёт: трасса считается сразу. `ask` и `escalate` запуска «Запустить» и `/test/events` ждут по-настоящему, в памяти стенда: `GET /rule-prompts`, ответ, срок. В демо-истории набора их исходы посчитаны номером запуска, отвечает первый пользователь роли. Правило, запущенное шагом `runrule`, не спрашивает: его `ask`, `escalate` идут как без ответа;
  - событие запускает правило только через `/test/events` с `type: io.input` и только правило с одним таким событием;
  - защиты от правки объекта, который в этот момент удаляется по отсчёту у другого администратора, нет.

## Универсальное ядро: что реализовать адаптеру

Бэкенд VMS (w2c, NGP) не повторяет таблицы встроенного сервера, а **отдаёт свои виды объектов**. Адаптер к системе делает четыре вещи.

1. **Описания видов** — `GET /kinds`, `GET /kinds/{kind}`. На каждый вид, который есть в системе (в том числе плагина): `kind`, подписи `Text {key, text, lang}`, `parents`/`createParents`/`children`, `implements`, `capabilities`, `schema` (JSON Schema свойств с `x-*`), `actions`, `events`, `access`. ETag — хэш описаний; `If-None-Match` → `304`. Описание вида — **данные системы**: топология, подписи, обязательность полей, команды и события не должны остаться таблицами в коде интерфейса. Вид, в котором система не умеет часть (нельзя завести второй домен), объявляет это в `capabilities`.
2. **Объекты** — `/units`: перечень страницами с отборами, `POST` группой с вложенными детьми и частичным успехом, `PATCH` (Merge Patch, `If-Match`), `DELETE`, `move`, `actions`, `creatable`, `schema`, `validate`. Проверка тела — **по схеме вида**: ошибка с `field` — JSON Pointer в теле (`/properties/port`), `params.keyword` — ключевое слово схемы (`maximum`, `required`, `x-unique`…); `readOnly` в теле — `422`; `x-immutable` после создания — `422`; ссылка `x-ref` на несуществующий объект — `422 keyword: x-ref`; родитель не из `parents` — `422 PARENT_MISMATCH`, `field: /parentId`. Вид без описания читается (общая иконка, код вида), но не пишется: `422 NOT_SUPPORTED`, `field: /kind`.
3. **Секреты.** Поле `writeOnly` в ответах не возвращается нигде — ни при создании, ни в `PATCH`, ни в теле `412` (`current`), ни в событиях потока; вместо него `Unit.secrets[имя] = true`. Смена поля из `x-bound-to` без нового секрета — `422` с указателем на поле секрета.
4. **Групповые операции по объектам разных видов.** Шаг `patch` для объекта, у которого поля нет в схеме или значение не по схеме, падает **по строке**: `fail` с кодом, указатель — `params.field` (JSON Pointer в теле шага, `/properties/<имя>`), слово схемы — `params.keyword`; отдельного поля `field` у `OperationItem` нет. Остальные шаги проходят.

**Дерево** остаётся отдельным API: `GET /tree/children` (раскладки `folders`, `servers`, `archives`, `detectors`) и `GET /tree/paths`; `TreeNode.kind` — вид объекта, у узла `icon`, `implements`, вместо `row` — `UnitBrief`. На домене в 250 000 камер `/tree/children`, `/units?parentId=` и `/units?ids=` отвечают страницами в пределах `reference.limits`, без полного прохода склада: так проходит `check_scale.py`. `Unit.hasChildren` и `TreeNode.hasChildren` — есть ли дочерние объекты, которые показывает дерево; потоки (`stream`) и документы (`shape: document`) дочерними не считаются.

**Права.** `UnitKind.access {class, levels}`: класс объединяет виды с общим набором уровней (`cam`, `tel`, `acfa`…), вид без класса получает `view < edit < admin` и класс, равный своему коду. `Role.kindAccess {класс: уровень}`; `folderAccess`/`objectAccess` — по `uid`. Право на команду — `ActionDescriptor.right`, на событие правила — `EventDescriptor.right`, на путь предметного API — `UnitKind.apiRights`. Роль с уровнем ниже — `403 PERMISSION_DENIED`, `params.right`.

**Правила** берут события и действия из описаний видов: триггер `{source: "unit", kinds | implements, event, match}`, шаг `{type: "unitAction", action, params}`; цели — по `uid` или области. `EventDescriptor.rule: false` — события нельзя брать триггером (запись `422 NOT_SUPPORTED`, `field: triggers`); `EventDescriptor.alarm: false` — событие не входит в «Что считать тревогой» (`alarms.domain`, `Job.alarms` — `422` с `field`).

### Хуки профилей

То, чего из схемы не вывести, — смысл профиля: каскады, вычисляемые поля, исполнитель шага. Во встроенном сервере это [`profiles.js`](profiles.js), `ConsolemProfiles.HOOKS: { [профиль]: {…} }`; хук получает `ctx {units, kinds, db, problem, send, now}`.

| Хук | Что делает | Пример |
|---|---|---|
| `view(unit, ctx)` | вычисляемые поля ответа | `status.observed` камеры и тома, `recordState` |
| `beforeCreate(unit, parent, ctx)` | проверка до записи, `Problem` или `null` | камера: номер от сервера, адрес, MAC; хранилище: занятый диск |
| `beforeSet(unit, patch, whole, ctx)` | проверка правки | запись камеры, `recordMode`, шифрование |
| `afterSet(unit, before, ctx)` | последствия правки | переразмещение раздачи, приём записей |
| `dependents(unit, ctx)` | `{remove: uid[], detach: uid[]}` — каскад удаления | камера с детьми и записью детекторов, хранилище с томами |
| `executor(unit, ctx)` | сервер-исполнитель шага операции | сервер камеры, держатель тома |
| `actions[id](unit, params, ctx)` | команда: `{result}`, `{operation: {until, free?}}` или `Problem`; `free` — операция объект не держит | `probe`, `check`, `format`, `output`, `ARM` |

Поведение и коды ошибок у известных видов — те же, что в старом макете; разделы выше описаны путями и полями этого контракта. Что чем заменено против контракта старого макета — [README, «Ломающие изменения против контракта старого макета (до 0.2.0, коммит 47d1310)»](README.md#ломающие-изменения-против-контракта-старого-макета-до-020-коммит-47d1310).

### Стандартные профили

Профиль — имена свойств (`Unit.properties`) и наблюдаемого (`status.observed`) с фиксированным типом и смыслом (схема `Profile`). Вид, объявивший профиль в `implements`, несёт свойство под тем же именем, того же типа и с тем же смыслом — тогда ручной экран интерфейса работает с ним без правки. Источник таблиц ниже — схемы видов эталонного набора (`GET /kinds/{kind}` на [`fixtures/demo.json`](fixtures/demo.json)): у свойства вида есть ещё подпись (`x-label`), умолчание и ограничения. Свой вид системы берёт из профиля то, что у него есть; своё сверх профиля — под своими именами. Несовместимая правка профиля — новая версия (`vms.camera/2`).

Своих свойств нет: профиль — возможность предметных путей объекта.

### `kinds.changed` после перезапуска

Описания видов меняются при установке плагина или обновлении VMS. Сервер шлёт `kinds.changed`, но он **подсказка**: после перезапуска стенда или потери потока (`stream.reset`) клиент перечитывает `GET /kinds` с `If-None-Match`; ETag не изменился — `304`, изменился — описания целиком. Пока клиент не перечитал, объекты вида без известного ему описания показываются с общей иконкой и кодом вида, правка запрещена, черновик открытой карточки не теряется и перерисовывается после перечитывания. На тестовом стенде описание подменяют `PUT /test/kinds/{kind}`.

### Известные отличия от старого макета и отложенное

- **`POST /units` с папкой при домене без связи** отвечает строкой `SERVER_OFFLINE`, `field: /folders`; в старом макете создание устройства с папкой отвечало `VALIDATION_FAILED` по полю папки. Единообразие не решено.
- **`hiddenIds` шире старого макета:** скрытое от роли учитывается на всех перечнях `/units`, а `total` считается без фильтра; на `ids=` скрытое не отбирается. В старом макете скрывались только устройства.
- **Членство в папках строже старого макета на одном пути.** Право «Администратор» судится и у шага `folders` операции (старый макет судил его только у состава папки, шаг папок операции — нет): правило теперь одно на `PATCH {folders}`, шаг `folders` и шаг `patch` только с `folders`.
- **Отключённое правило с пропавшим событием** по правам не судится: событие вида, которого больше нет, уходит в `gone`, а право на него не проверяется.
- **В `one-domain` и `large` нет класса `tel`:** у камеры нет дополнительного класса доступа, роли без `tel`; тесты прав `tel` пропускаются (`needs: class:tel`).
- **`field: "/moveTo"`** у `DELETE /units/{uid}` — указатель на параметр запроса, а не на тело: единственное исключение из правила «`field` на путях ядра — JSON Pointer в теле».

## Возможности системы

Контракт один для всех систем, но система может уметь не всё: один домен на установку, не все виды устройств, без лицензий или поиска в сети. Тогда она не изображает неподдержанное, а объявляет, что умеет, — и интерфейс с тестами подстраиваются.

**Объявление** — `GET /reference` → `capabilities` (схема `Capabilities`: `operations`, `features`) и описания видов `GET /kinds`: какие виды есть у системы, что она умеет с каждым (`UnitKind.capabilities`), что у объекта правится (`readOnly` в схеме вида, `Unit.writable`, `Unit.capabilities`):

| Поле | Что значит | Неподдержанное |
|---|---|---|
| `operations` | `operationId` операций контракта, которые система выполняет. `getMe`, `getReference`, `stream` — всегда; служебные `test-support` сюда не входят | `404 NO_ROUTE` — до разбора адреса и тела: клиент по этому коду понимает «не поддержано», а не «нет записи» |
| виды (`GET /kinds`) | какие виды объектов есть у системы, в том числе плагинов; вид, которого нет, — нет и его объектов | создать объект вида вне `GET /kinds` — `422 NOT_SUPPORTED`, `field: /kind`; в `POST /units` — строкой в `failed`, в операции — до выполнения |
| `UnitKind.capabilities` | что система умеет с видом: `create`, `delete`, `rename`, `enable`, `move`, `folders`, `bulkSet`. Вид без `create` и `delete` находит сервер сам (по описанию устройства): объекты появляются и пропадают сами (`entity.created`, `entity.deleted`); `createParents` — под кем вид заводит оператор (единицы СКУД — только под родителем из СКУД) | `POST /units`, шаг `createUnit`, `DELETE` без возможности — `422 NOT_SUPPORTED`, `field: /kind`, `params.capability`; `folders` без возможности `folders` — `422 NOT_SUPPORTED`, `field: /folders` |
| `readOnly`, `Unit.writable` | что у объекта правится: поле `readOnly` в схеме вида заполняет сервер; `Unit.writable` — что правится у этого объекта сейчас (карта камеры w2c, камера-кластер) | `readOnly` в теле, в том числе `null`, — `422 VALIDATION_FAILED`, `params.keyword: readOnly`; поле вне `Unit.writable` — `422 NOT_SUPPORTED` с `field`. Интерфейс показывает такие поля только для чтения |
| `features` | необязательные настройки (`Feature`): `serverRoles` — роль сервера, `serverNetwork` — маска, шлюз, DNS сервера, `archiveEncryption` — шифрование хранилища, `assist` — ассистент (вместе с операцией `assistTurn`). Части прав: `accessCatalogs` — каталоги, `accessSupervision` — правка `Role.supervision` (надзор над выгрузкой от неё не зависит), `accessLoginSchedule` — расписание входа, `accessSessions` — лимиты сессий, `accessDepth` — глубина архива, `accessRestrictions` — запреты, `accessUserRights` — выбор `ur`; без неё `ur` следует за функцией: `ALL` при `USERS_RIGHTS_SETUP`, иначе `NO` | поле есть в записи, но изменить его нельзя: `422 NOT_SUPPORTED` с `field`. Часть прав без возможности: интерфейс прячет поле, значение не по умолчанию в `POST /access/apply` — тот же отказ, `field` — путь поля (`global.depth`, `supervision`), `params.id` — запись |

**Каталог «Автоматизации»** объявляется данными, а не списком операций: события — `UnitKind.events` видов (`rule: false` — не триггер), действия объектов — `UnitKind.actions` с `ruleAction`, действия системы — `reference.ruleActions`, а ещё `ruleConditions`, `ruleControls`, `ruleStarts`, `ruleTargets` — это то, что система исполняет. У поля действия `options` — его значения, поля нет в `fields` — у действия его нет: запись только на минуты — `duration` с `options: ["min"]` и без `afterSec`. Форма предлагает только объявленное.

| Что вне каталога | Ответ |
|---|---|
| включённое правило в `POST /rules`, `PUT /rules/{id}` | `422 NOT_SUPPORTED`, `field` — раздел (`start`, `triggers`, `conditions`, `steps`), `params.issue` — `{code, params}`: `rule.startNotDeclared`, `trigger.notDeclared`, `cond.notDeclared`, `action.notDeclared`, `action.fieldNotDeclared`, `control.notDeclared`, `target.notDeclared` |
| включение в `/rules/update` | элемент `failed`, `code: NOT_SUPPORTED` |
| запуск уже включённого | `409 NOT_RUNNABLE`, `params.reason` — та же причина |
| выключенное правило | хранится как есть: чтение, правка, «Запустить» не предлагается. Форма показывает такой шаг с пометкой «нет в этой системе» и не даёт включить |

Правила:

- **Форма зовёт только объявленное.** При запуске обязательны `getMe`, `getReference`, `stream`, всё остальное — по `capabilities`. Раздела без своей операции нет: «Автоматизация» — `listRules`, «Права» — `getAccess`, «Журнал» — `listJournal`. `403` на `GET /access` скрывает «Права», запуск не падает.
- **Объявленное работает по контракту целиком.** Объявил `patchUnit` и вид с `rename` — значит, и 412, и 428, и поток, и `idempotencyKey`, как у всех. «Поддержано частично» выражается только тем, чего в списках и в `capabilities` вида нет.
- **Данные не противоречат объявленному.** Нет `archiveEncryption` — все хранилища `encrypted: false`; у вида тома нет `create` — у хранилища один том; у вида домена нет `create` — домен один; нет `listLicenses` — `licenseExceeded` у объектов не бывает. Это проверяет `tools/check_api.py` для наборов.
- **Объявление постоянно для системы.** Клиент читает его один раз при старте. Если возможности меняются (обновили VMS), клиент узнает о них после перезагрузки страницы.
- **Новый код в `features` или новая операция — правка контракта**, как и любая другая: незнакомый код клиент пропускает, но спрятать его поля он может, только если знает его.

Чего нет в объявлении сейчас и может понадобиться: ограничения числа (сколько доменов, томов, камер на сервер), разные возможности у разных объектов одного вида (одни серверы умеют роли, другие нет) — сейчас только `Unit.capabilities` и `Unit.writable` объекта.

## Тестовый стенд

Чтобы бэкенд проверялся теми же тестами, что встроенный сервер, ему нужны 5 служебных операций (тег `test-support`). В боевой системе их нет.

| Операция | Что делает |
|---|---|
| `POST /test/reset` | Загружает набор `fixture` заново: `demo` — [`fixtures/demo.json`](fixtures/demo.json), `one-domain` — [`fixtures/one-domain.json`](fixtures/one-domain.json). Стенд умеет те наборы, что подходят его системе: не умеет — `404 NOT_FOUND`. Все даты и моменты сдвигаются на «сейчас − `capturedAt`», даты — на целые сутки. По умолчанию останавливает часы; `freezeClock: false` — часы идут. Стенд, который часы остановить не может, принимает только `freezeClock: false`. `fixturePatch` — изменения набора на один прогон, JSON Merge Patch (RFC 7396): объекты сливаются, `null` удаляет поле, массивы заменяются целиком. `actAs` — логин, от имени которого идёт прогон. Шлёт в поток `test.reset` |
| `POST /test/clock` | Сдвигает часы на `advanceSec` и выполняет всё, что за это время наступило, в свой момент: шаги операций, находки поиска, форматирование, синхронизацию. В ответе — что сработало (`fired`). Стенд на настоящих часах её не реализует: тесты тогда запускают с `&clock=real` |
| `PUT /test/kinds/{kind}` | Добавляет или заменяет описание вида на ходу: `kinds.changed`, новый ETag `/kinds`; объекты вида остаются. Тестам нужен для сценария «вид появился после выпуска WebUI» |
| `POST /test/stream-elsewhere` | Второй экземпляр консоли: открытые потоки идут дальше, а `PUT /stream/{clientId}/watch` на них отвечает `404`. Поток, открытый после вызова, работает как обычно |
| `POST /test/events` | Событие извне (`deviceId` — `uid` объекта): `device.signal` — пропало или вернулось соединение (`online`, `fault`), `device.fault` — сменилась причина: объект меняется, изменение уходит в поток, версия не растёт. `device.found` — устройство назвало новый объект (`found`), `device.lost` — объект пропал, `device.parent` — сменился родитель (`parentId`). `io.input` — сигнал входа (`value`), `journal.event` — запись журнала об объекте, `scenario.outcome` — исход сценария между камерами, `domain.link` — связь с центром домена (`online`), `unit.event` — событие объекта по описанию его вида (`eventId`, `match`): запускает включённые правила по нему |

Образец стенда — [`tools/serve_api.mjs`](../tools/serve_api.mjs): встроенный сервер за HTTP, с CORS и потоком SSE ровно так, как их ждёт клиент (`node tools/serve_api.mjs`). На нём проверено, что всё ниже работает со страницы с диска.

С `--webui <папка>` он ещё и изображает консоль VMS: сборка WebUI ([`tools/build_webui.py`](../tools/build_webui.py)) — под `/backend/` с заголовком CSP консоли, API — под `/backend/api/`. Так проверяется сборка для w2c — [TESTS.md, раздел 7](TESTS.md#7-сборка-webui-под-csp-консоли).

Запуск: откройте `tests/api.html?api=https://адрес-стенда` — с диска (двойной клик) или со своей раздачи. Итог — строка вверху страницы и `data-apitest="pass|fail"` у `<html>`, чтобы гонять без человека. Один тест — `&only=<имя>`.

- **Набор:** `&fixture=one-domain` — тесты берут ожидаемое из этого набора, а стенд сбрасывается на него. По умолчанию — `demo`.
- **Часы:** `&clock=real` — часы идут по-настоящему, `/test/clock` не вызывается. Тест, который ждёт итог (операция, форматирование, поиск, синхронизация), спрашивает четыре раза в секунду, пока итог не наступит, но не дольше минуты. Тест, которому нужны именно остановленные часы («часы стоят и сдвигаются ровно на 90 с»), пропускается.
- **Возможности:** перед тестами страница читает `capabilities`. Тест неподдержанного пропускается (`SKIP` с тем, чего не хватило), покрытие считается по объявленным операциям, а каждая необъявленная проверяется на `404 NO_ROUTE`. Прототип с `?api=https://адрес-стенда` работает с бэкендом вместо встроенного сервера.

**CORS.** Страница с диска приходит с `Origin: null`, с сайта — со своим адресом. Стенд должен отвечать так:

- `Access-Control-Allow-Origin` — тот `Origin`, что пришёл (в том числе строкой `null`, только на стенде), и `Access-Control-Allow-Credentials: true`: клиент шлёт запросы с `credentials: "include"`, поток — `EventSource` с `withCredentials`;
- на предварительный `OPTIONS` — `Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE` и `Access-Control-Allow-Headers: Content-Type, If-Match, Last-Event-ID`;
- `Access-Control-Expose-Headers: ETag` — без него клиент не увидит версию записи;
- кука сессии — `SameSite=None; Secure`, если страница и стенд на разных адресах.

## Когда готово

1. `tests/api.html?api=<стенд>` (с `&fixture=` и `&clock=`, если система умеет часть контракта) проходит целиком: итог «Тесты API: все N прошли», `data-apitest="pass"`. Пропущенные тесты (`SKIP`) — то, чего система не объявила; провалом они не считаются.
2. Покрытие — 100% объявленного: строка «Каждая объявленная операция покрыта тестами» — PASS, исключений нет. Строка «Неподдержанные операции отвечают 404 NO_ROUTE» — PASS.
3. Каждый ответ стенда соответствует схемам контракта: строка «Ответы соответствуют openapi.json» — PASS.
4. Прототип с `?api=<стенд>` работает так же, как со встроенным сервером. Проверка — те же сценарии интерфейса: `index.html?api=<стенд>&selftest`; сценарии идут по одному, перед каждым — `POST /test/reset` с идущими часами (`freezeClock: false`).

Всё это разом: `python3 tools/check_stand.py https://адрес-стенда`; для системы с частью контракта — `python3 tools/check_stand.py https://адрес-стенда --fixture one-domain --clock real` (самопроверка прототипа пока идёт только на `demo`: её сценарии написаны под весь контракт).

Для этого стенд должен стартовать с набором, а `/test/reset` — возвращать его в любой момент.
