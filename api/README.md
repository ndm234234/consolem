# API конфигуратора

Прототип 10 (`index_10_api-server.html`) — это макет конфигуратора, переведённый на API. Выглядит и работает он так же, как прототип 09, но своих данных у интерфейса нет: всё, что в продукте хранит бэкенд, интерфейс читает и меняет запросами контракта [`openapi.json`](openapi.json).

## Как устроено

```
интерфейс (index_10_api-server.html)
   │  кэш прочитанного: дерево, карточки, черновики — меняется только ответом сервера или событием потока
   ▼
клиент API (client.js) ── ?api=https://… ──▶ бэкенд (fetch + SSE)
   │ по умолчанию
   ▼
встроенный сервер (server.js) — та же вкладка, данные — эталонный набор (fixtures/demo.json)
```

- **Контракт — источник истины.** Если встроенный сервер расходится с `openapi.json`, ошибка в сервере. Встроенный сервер проверяет тела запросов по контракту (`contract.js`): что не подходит под схему, получает `422 VALIDATION_FAILED`.
- **Интерфейс говорит только с клиентом API.** Ответ встроенного сервера приходит обещанием и копируется — «как по сети». В интерфейсе есть кэш прочитанного: рендер читает его синхронно, а меняют кэш только ответы сервера и события потока.
- **По умолчанию запросы только изображаются.** В сеть клиент не ходит: он вызывает функцию `server.handle(метод, путь, тело, заголовки)` в той же вкладке и получает статус, тело и заголовки, как от HTTP. В DevTools → Network их не видно. С `?api=https://адрес` тот же клиент делает настоящий `fetch`. Пошагово, с кодом — в [BACKEND.md, «Запрос без сети»](BACKEND.md#запрос-без-сети-что-именно-происходит).
- **С диска и с сайта.** Всё подключается обычными `<script>`. Контракт и набор подключаются собранными `openapi.js` и `fixture.js`: с `file://` загрузить JSON через `fetch` нельзя.
- **Режимы страницы:**
  - `?api=https://адрес` — работать с настоящим бэкендом;
  - `?latency=300` — задержка ответа, как в медленной сети;
  - `?selftest` — самопроверка (см. «Проверки»).

## Карта API — 60 операций и 3 служебные

| Раздел (тег) | Операции |
|---|---|
| `session`, `reference` | `GET /me` — кто вошёл, часы и часовой пояс сервера; `GET /reference` — справочники кодами |
| `hardware` — домены | `GET`, `POST /domains`; `GET`, `PATCH`, `DELETE /domains/{id}` (удаление с переносом содержимого `?moveTo=`) |
| `hardware` — серверы | `GET`, `POST /servers`; `POST /servers/probe` (опросить адреса); `POST /servers/assign` (в домен и из него, группой); `GET`, `PATCH /servers/{id}` |
| `hardware` — устройства | `GET /devices`; `POST /devices` (добавить группой, с дочерними); `POST /devices/update` (изменить группой сразу); `POST /devices/probe` (определить модель); `GET`, `PATCH`, `DELETE /devices/{id}` |
| `hardware` — папки | `GET`, `POST /folders`; `GET`, `PATCH`, `DELETE /folders/{id}`; `POST /objects/delete` (групповое удаление любых объектов) |
| `storage` | `GET`, `POST /archives` (с первым томом); `POST /archives/check`; `GET`, `PATCH`, `DELETE /archives/{id}`; `POST /archives/{id}/volumes`; `GET /volumes`; `GET`, `PATCH`, `DELETE /volumes/{id}`; `POST /volumes/{id}/format` |

| `discovery` | `GET`, `POST`, `DELETE /domains/{id}/discovery` — поиск устройств в сети домена |
| `automation` | `GET /rules`, `GET`, `PUT /rules/{id}`, `GET /rules/{id}/fires` |
| `access` | `GET /access` — снимок прав; `POST /access/apply` — черновик пакетом; `POST /access/catalogs/{id}/sync` |
| `settings`, `journal` | `GET`, `PATCH /settings`; `GET /licenses`; `GET /journal` |
| `stream` | `GET /stream` — поток событий (SSE) |
| `test-support` | `POST /test/reset`, `/test/clock`, `/test/events` — только на тестовом стенде |

## Договорённости

- **Идентификаторы — UUID.** Новые записи «Оборудования», правил и хранилищ получают id от сервера. В наборе первая цифра UUID — вид записи: `1…` домен, `2…` сервер, `3…` устройство, `4…` папка, `5…` хранилище, `6…` том, `7…` правило, `8…` роль, `9…` пользователь. Это удобно читать при отладке, но в продукте полагаться на это нельзя. У ролей, пользователей, групп и каталогов id нового задаёт клиент (`crypto.randomUUID`): права применяются пакетом, и пакету нужны id до записи. Номер для показа — отдельные поля: `short` («3.3.1»), `identifier` («16»).
- **Версии записей.** У изменяемых записей есть `version`. Ответ отдаёт его в `ETag` (`"3"`), изменение приходит с `If-Match`. Нет заголовка — `428 PRECONDITION_REQUIRED`, версия не та — `412 VERSION_MISMATCH` с актуальной записью в `current`. У прав и опций версия одна на весь снимок.
- **Ошибки** — `application/problem+json`: `{code, message, field?, params?, current?}`. Интерфейс показывает свой текст по `code`; `message` — для журнала и разработчика. Перечень кодов — схема `ProblemCode`.
- **Групповые изменения.**
  - **Долгие** — `POST /operations`: план карточки, правка выборки, копирование настроек. Шаги выполняются по одному, ход приходит в поток. Частичный успех — норма: у каждого шага свой `state` и `code`. Пауза, отмена оставшегося, повтор неудачных и «Отменить» — запросы к операции; «Отменить» — новая операция, которая возвращает объекты к состоянию «до».
  - **Быстрые** — синхронные запросы с частичным успехом (`done` / `failed`): `POST /servers/assign`, `/devices`, `/devices/update`, `/objects/delete`.
  - **Повторы.** У всех групповых запросов есть `idempotencyKey`: повтор с тем же ключом в течение 10 минут возвращает прежний ответ и ничего не выполняет снова.
- **Поток событий** `GET /stream` (SSE). На каждое сообщение — строки `id:` и `data:` (схема `StreamMessage`), строки `event:` нет. Типы сообщений:
  - `entity.created`, `entity.changed`, `entity.deleted` — с `kind` и `entityId`;
  - `operation.progress`, `operation.finished`;
  - `discovery.progress`, `discovery.finished`;
  - `stream.reset`, `test.reset`.
  
  Клиент перечитывает запись по `id`. После обрыва браузер шлёт `Last-Event-ID`: сервер досылает пропущенное, а если оно уже потеряно — `stream.reset`, и клиент перечитывает всё.
- **Удаление с «Отменить».** Отсчёт ведёт клиент. Запрос `DELETE` (или `POST /objects/delete`) уходит, когда отсчёт закончился; «Отменить» во время отсчёта ничего не отправляет. Каскады делает сервер:
  - устройство — с дочерними, из папок и из записи по детекторам;
  - хранилище — с томами; камеры переходят на следующее хранилище или перестают писать;
  - домен — с переносом содержимого.
  
  В «Правах» удаление попадает в черновик, а на сервер — при «Применить».
- **Тексты.** Сервер отдаёт коды (`role: "primary"`, `detectorKind: "motion"`, `fault: "auth"`) и числа (`sizeBytes`, `usedPercent`), подписи и переводы — в интерфейсе. Имена объектов, тексты журнала и истории прав — данные.
- **Время** — в UTC (ISO 8601), даты — `ГГГГ-ММ-ДД`. Интерфейс показывает время в часовом поясе системы из `GET /me` (`timezone`).
- **Пароли** только записываются: в запросе `password` (у облачного тома — `secret`), в ответе — `hasPassword` / `hasSecret`.
- **Черновики** остаются у клиента. У «Оборудования» это черновик карточки: «Применить» отправляет операцию. Если запись тем временем поменял другой администратор, нетронутые поля обновляются, а правки пользователя остаются поверх. У «Прав» черновик — весь снимок, «Применить» уходит пакетом.

## Модель данных

| Запись | Главное | Связи |
|---|---|---|
| `Domain` | имя, лицензия | — |
| `Server` | адрес, роль, нагрузка, GPU, диски | `domainId`; `allocated: false` — «нераспределённый» |
| `Device` | вид (`type`), подключение, запись (`archiveId`, `recordMode`, `extraArchives`), состояние (`online`, `fault`) | `parentId` (канал → регистратор, периферия и детектор → камера), `domainId`, `serverId` |
| `Folder` | имя, `deviceIds` по порядку | `domainId`, `parentId` |
| `Archive`, `Volume` | вид, хранение, шифрование, срок; том — диск, размер, состояние | владелец — `serverId` или `domainId`; том → `archiveId` |
| `Rule`, `RuleFire` | события → действия, частота, окно; срабатывания | устройство в правиле — текстом, как его ввёл администратор |
| `Access` | роли, пользователи, группы, каталоги, история | права роли: `folderAccess` (папка или домен), `objectAccess` (устройство, хранилище, `vw:<сервер>`, `macro:<правило>`, `plug:<код>`) |
| `Settings`, `License`, `JournalEvent` | значения опций, лицензии, журнал | — |

Устройства не принадлежат серверу. Они лежат в пуле домена и раскладываются по папкам. Связь с сервером возникает через хранилище записи (камера, регистратор), расчёт детектора или службу сервера.

## Эталонный набор

`fixtures/demo.json` — данные прототипа 09 в виде ответов API. Его собрал `tools/extract_fixture.py`: прототип 09 открывается в headless Chrome с остановленными часами, данные берутся из памяти после старта и приводятся к контракту (`tools/fixture_normalize.py`). Повторная сборка даёт тот же файл байт в байт. Набор можно править руками, тогда пересобирать его нельзя: без `--force` скрипт откажется перезаписывать.

- `capturedAt` — момент снимка. При загрузке каждая дата и каждый момент сдвигаются на «сейчас − `capturedAt`», даты — на целые сутки. Так «вошёл вчера» и «истекает через неделю» остаются правдой в любой день.
- `network` — что «видно» в сети каждого домена: это находит поиск. `discovery` — итог последнего поиска.
- `me` — администратор, от имени которого работает стенд.

## Тестовый стенд

Служебные операции (тег `test-support`) есть только у встроенного сервера на странице тестов и у тестового стенда бэкенда:

- `POST /test/reset` — загрузить набор (`fixturePatch` — изменения на прогон в формате JSON Merge Patch, `actAs` — от имени другого логина), остановить часы;
- `POST /test/clock` — сдвинуть часы на `advanceSec` и выполнить всё, что за это время наступило: шаги операций, форматирование, поиск в сети, синхронизацию каталогов;
- `POST /test/events` — событие извне: устройство потеряло или вернуло связь, сменилась причина.

## Проверки

| Команда | Что проверяет |
|---|---|
| `python3 tools/check_api.py --lint` | контракт и `redocly lint`; набор — по схемам и целостности ссылок; сборку `openapi.js` и `fixture.js`; что в HTML прототипа нет данных сервера и интерфейс не трогает внутренности сервера; досылку потока; что сервер и контракт совпадают по операциям; числа в `BACKEND.md` |
| `python3 tools/run_api_tests.py` | тесты API `tests/api.html` (двойной клик — то же): сценарии по разделам, каждый ответ — по схеме, покрытие всех операций |
| `python3 tools/check_loopback.py` | те же тесты по HTTP и SSE через Service Worker (`tests/loopback-sw.js`) |
| `python3 tools/check_ui.py [--latency 300]` | сценарии интерфейса `tests/ui-*.js`: действия пользователя → запросы → экран и сервер |
| `python3 tools/check_ui.py --selftest` | самопроверку прототипа `?selftest`: те же сценарии изнутри страницы |
| `python3 tools/check_stand.py [адрес]` | внешний режим целиком: тесты API и прототип `?selftest` открываются с диска и работают со стендом по HTTP — с образцом `tools/serve_api.mjs` или со стендом бэкенда по адресу |
| `python3 tools/compare_screens.py` | внешний вид: 52 экрана прототипа 10 против прототипа 09 по разметке; известные расхождения перечислены в самом скрипте с объяснением |

`tests/api.html?api=https://адрес` — те же тесты API против стенда бэкенда (см. `BACKEND.md`). `node tools/serve_api.mjs` — образец тестового стенда: встроенный сервер за HTTP, с CORS и SSE, как их ждёт клиент.
