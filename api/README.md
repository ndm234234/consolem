Зачем: виды объектов расширяемых VMS (плагины psim в NGP, подсистемы w2c) появляются после выпуска WebUI. Сервер отдаёт описания видов, интерфейс строит дерево, мастер, фильтры, подписи и форму по ним; у известных видов остаются ручные экраны, привязанные к **профилю** (`vms.camera/1`…), а не к виду. Объект незнакомого вида показывается, создаётся, правится, удаляется, получает команды, участвует в правилах и правах без кода интерфейса под вид.

**Где команды.** Инструменты `tools/*.py` по умолчанию работают с основным макетом: `index.html`, `api/`, `tests/` — без параметров. Прототип проверяют с `--page index_NN_….html` (его API и сценарии — общие с `index.html`). Все команды — «[Проверки](#проверки)» и [TESTS.md](TESTS.md).


## Как устроено

```
интерфейс (index.html)
   │  кэш прочитанного: дерево, карточки, черновики — меняется только ответом сервера или событием потока
   ▼
клиент API (client.js) ── ?api=https://… ──▶ бэкенд (fetch + SSE)
   │ по умолчанию
   ▼
встроенный сервер (server.js поверх kinds.js, units.js, profiles.js + rule-engine.js) — та же вкладка, данные — эталонный набор (fixtures/demo.json)
```

- **Контракт ведёт владелец — joynickray — в этом репозитории (`ndm234234/consolem`).** Расширить контракт, сервер и наборы (только добавить, старое — `deprecated: true`) может любой, с уведомлением владельцу; ломающую правку делает только владелец, остальные пишут [запрос](requests/README.md) в `api/requests/`. Порядок — скилл `api-contract` ([`.claude/skills/api-contract/SKILL.md`](../.claude/skills/api-contract/SKILL.md)). Перевод `backend` (V/11) держит копию контракта по коммиту.
- **Контракт — источник истины.** Если встроенный сервер расходится с `openapi.json`, ошибка в сервере. Встроенный сервер проверяет тела запросов по контракту (`contract.js`): что не подходит под схему, получает `422 VALIDATION_FAILED`.
- **Интерфейс говорит только с клиентом API.** Ответ встроенного сервера приходит обещанием и копируется — «как по сети». В интерфейсе есть кэш прочитанного: рендер читает его синхронно, а меняют кэш только ответы сервера и события потока.
- **По умолчанию запросы только изображаются.** В сеть клиент не ходит: он вызывает функцию `server.handle(метод, путь, тело, заголовки)` в той же вкладке и получает статус, тело и заголовки, как от HTTP. В DevTools → Network их не видно. С `?api=https://адрес` тот же клиент делает настоящий `fetch`. Пошагово, с кодом — в [BACKEND.md, «Запрос без сети»](BACKEND.md#запрос-без-сети-что-именно-происходит).
- **С диска и с сайта.** Всё подключается обычными `<script>`. Контракт и набор подключаются собранными `openapi.js` и `fixture.js`: с `file://` загрузить JSON через `fetch` нельзя.
- **Режимы страницы:**
  - `?api=https://адрес` — работать с настоящим бэкендом;
  - `?latency=300` — задержка ответа, как в медленной сети;
  - `?drop=listRules,getSettings` — система, которая не объявила эти операции: запуск без необязательного;
  - `?fixture=one-domain` — встроенный сервер с набором профиля: система, которая умеет часть контракта, и интерфейс без неподдержанного;
  - `?fixture=agents` — встроенный сервер с набором «оркестратор агентов»: система не из мира VMS;
  - `?assist=https://адрес` — ход ассистента идёт в службу с настоящей моделью, со снимком встроенного сервера: только встроенный сервер и набор `demo`; код доступа нужен, только если служба ответила `401` (`BACKEND.md`, «Служба демо-страницы»). Метка страницы `consolem-assist` — то же адресом в разметке, в `index.html` её нет. В учебном режиме (`?demo`, раздел «Обучение») службы нет ни из `?assist=`, ни из меток: отвечает встроенная заглушка;
  - `?tour=<тема>&ch=<глава>&demo=` — учебный показ главы по устойчивым ID (`assets/tour.js`); `&demoFail=server|storage` — проверка отказа показа: сервер показа не загрузился, хранилище не отделилось;
  - `?selftest` — самопроверка (см. «Проверки»).

Шаг (`OperationItemRequest`) — `uid` и ровно одно из: `patch` (правка, как `PATCH /units/{uid}`), `folders` (папки объекта), `createUnit` (дочерний объект), `move` (+`params`: перенос к родителю), `action` (+`params`: команда вида), `delete: true`. Отказ шага — `code`, указатель — `params.field` (JSON Pointer в теле шага), слово схемы — `params.keyword` |

Что стало действием вида (`UnitKind.actions`, `POST /units/{uid}/actions/{action}` или `POST /kinds/{kind}/actions/{action}`), а не путём: определение модели камеры и регистратора (`probe`), опрос адресов серверов (`probe` вида `server`), проверка подключения хранилища (`check`), форматирование тома (`format`), команда реле и двери (`output`), `ARM` контроллера psim и всё, что объявит новый вид. Назначение сервера в домен и исключение из него — `POST /units/{uid}/move`.

## Договорённости

- **`uid` объекта — UUID.** Ключ объекта любого вида в `/units`; в наборе он равен прежнему `id` записи старого контракта, формат не менялся.
- **Идентификаторы — UUID.** Новые записи «Оборудования», правил, хранилищ, расписаний, особых дней и окон обслуживания получают id от сервера. В наборе первая цифра UUID — вид записи: `1…` домен, `2…` сервер, `3…` устройство, `4…` папка, `5…` хранилище, `6…` том, `7…` правило, `8…` роль, `9…` пользователь, `d…` запуск правила; у видов «Автоматизации» — `f…` и номер во второй группе (`-0001-` расписание, `-0002-` особые дни, `-0003-` режим, `-0004-` окно обслуживания, `-0005-` версия правила, `-0006-` раскладка, `-0007-` монитор). Это удобно читать при отладке, но в продукте полагаться на это нельзя. У ролей, пользователей, групп, каталогов и режимов объекта id нового задаёт клиент (`crypto.randomUUID`): права и режимы уходят пакетом, и пакету нужны id до записи. Номер для показа — отдельные поля: `short` («3.3.1»), `identifier` («16»).
- **Версии записей.** У изменяемых записей есть `version` — непрозрачная строка: её сравнивают только на равенство и возвращают как есть, порядка и «+1» у неё нет (что обязан соблюдать сервер — [BACKEND.md, «Версии и 412»](BACKEND.md#на-что-обратить-внимание)). Ответ отдаёт её в `ETag` (`"v3k"`), изменение приходит с `If-Match`. Нет заголовка — `428 PRECONDITION_REQUIRED`, версия не та — `412 VERSION_MISMATCH` с актуальной записью в `current`. У прав, опций и режимов объекта версия одна на весь снимок. Течение времени (истёкшее приглушение, смена режима по расписанию) версией не считается.
- **Ошибки** — `application/problem+json`: `{code, message, field?, params?, errors?, current?}`. На путях ядра `field` — JSON Pointer в теле запроса (`/properties/mode`, `/parentId`, `/params/count`); `errors[]` необязателен, если он есть — в нём минимум одна ошибка. Исключение — `field: "/moveTo"` у `DELETE /units/{uid}`: это параметр запроса, а не тело. В описаниях операций ядра `field` тоже пишется указателем (`field: /streamId`, свойство объекта — `field: /properties/ptz`); имя без `/` остаётся только у параметра адреса (`?noDetector=` у `GET /units`). Это проверяет `check_api.py`. Интерфейс показывает свой текст по `code`; `message` — для журнала и разработчика. Перечень кодов — схема `ProblemCode`.
- **Групповые изменения.**
  - **Долгие** — `POST /operations`: план карточки, правка выборки, копирование настроек. Шаги выполняются по одному, ход приходит в поток. Частичный успех — норма: у каждого шага свой `state` и `code`. Пауза, отмена оставшегося, повтор неудачных и «Отменить» — запросы к операции; «Отменить» — новая операция, которая возвращает объекты к состоянию «до».
  - **Быстрые** — синхронные запросы с частичным успехом (`done` / `failed`): `POST /units` (группа строк с детьми), `POST /objects/delete`, `POST /rules/update`. `POST /operations` с `wait: true`, все шаги которой мгновенные (`patch`, `folders`, `move`), выполняется в самом запросе: ответ `200` — законченная операция, итог по строкам в `items`. Так пишутся состав папки, привязки и приём серверов — вместо синхронных `/folders/{id}/devices`, `/devices/update`, `/servers/assign` старого контракта. Состав папок в шагах проверяется до запуска: объекта шага нет, папка чужого домена или запись, которая в папки не входит, — отклоняется вся операция (`422`, `field` — `/items/{i}/…`, `params.targetId`).
  - **Повторы.** У всех групповых запросов есть `idempotencyKey`: повтор с тем же ключом в течение 10 минут возвращает прежний ответ и ничего не выполняет снова.
- **Страницы ограниченного прохода.** Отбор `GET /units` без члена (`q`, `kind` без `domainId`, `status`, `domainId`, `noFolder`, `noRecord`, `noDetector`) сервер проходит по разделам своего хранилища и может ответить, не дочитав домен: ответ с `nextCursor`, продолжение — с места остановки, ничего не теряется и не повторяется. **Рекомендация бэкенду: дописывай страницу до `limit` или до бюджета ~100–200 мс на запрос и только тогда отдавай курсор.** Иначе редкий поиск по большому домену — сотни запросов почти пустых страниц, и на каждую клиент отвечает волной и перерисовкой. Пустая страница с курсором при этом допустима (бюджет вышел, ничего не нашлось): клиент её выдерживает и читает дальше. `reference.limits.scanPartsMax` — сколько разделов запрос смотрит самое меньшее, если страница не набралась раньше; клиент на него не опирается. Встроенный сервер — не меньше `scanPartsMax` разделов, дальше до `limit` или до 40 мс (`SCAN_BUDGET_MS` в `server.js`: он работает в той же вкладке, и бюджет — время, когда страница не отвечает); на `large` редкий поиск — около десятка запросов вместо 512 (в настоящем времени; число зависит от машины). `stand.sparsePages: true` — встроенный сервер как бэкенд, который страницу не дописывает: ровно `scanPartsMax` разделов, пустые страницы подряд (`tests/api-pages.js`); что форма их выдерживает, проверяет `tests/scale-large.js`.
- **Поток событий** `GET /stream` (SSE). На каждое сообщение — строки `id:` и `data:` (схема `StreamMessage`), строки `event:` нет. Типы сообщений:
  - `kinds.changed` — описания видов изменились (подсказка): клиент перечитывает `GET /kinds` с `If-None-Match`; то же — после `stream.reset`;
  - `entity.created`, `entity.changed`, `entity.deleted` — с `kind` (вид объекта) и `entityId` (`uid`) (в том числе новый запуск правила — `kind: ruleFire`, смена текущего режима объекта — `kind: objectMode`);
  - `operation.progress`, `operation.finished`;
  - `discovery.progress`, `discovery.finished`;
  - `stream.reset`, `test.reset`.
  
  Клиент перечитывает запись по `id`. После обрыва браузер шлёт `Last-Event-ID`: сервер досылает пропущенное, а если оно уже потеряно — `stream.reset`, и клиент перечитывает всё.
- **Удаление с «Отменить».** Отсчёт ведёт клиент. Запрос `DELETE` (или `POST /objects/delete`) уходит, когда отсчёт закончился; «Отменить» во время отсчёта ничего не отправляет. Каскады делает сервер:
  - объект — с дочерними по `parentId` (камера — с потоками и детекторами), из папок и из записи по детекторам;
  - хранилище — с томами; камеры переходят на следующее хранилище или перестают писать;
  - домен — с переносом содержимого;
  - объект в правилах — остаётся в целях удалённым, по имени; расписание — где использовалось, переходит на «Никогда»; группа особых дней — уходит из расписаний; режим — из условий правил.
  
  В «Правах» удаление попадает в черновик, а на сервер — при «Применить».
- **Возможности системы.** Контракт один для всех систем, но система может уметь только его часть. Что она умеет, она объявляет в `GET /reference` → `capabilities` (схема `Capabilities`):
  - `operations` — `operationId` операций, которые она выполняет; остальные отвечают `404 NO_ROUTE`;
  - какие виды есть — `GET /kinds`, что система умеет с видом — `UnitKind.capabilities` (`create`, `rename`, `delete`, `enable`, `folders`, `bulkSet`…), что правится у объекта — `readOnly` в схеме вида и `Unit.writable`; создать то, чего вид не умеет, — `422 NOT_SUPPORTED`, `field: "/kind"`;
  - `sections` (с 0.27.0) — разделы приложения, которые система показывает в консоли, в порядке рельса: `{id, label?, icon?}`. Раздел объявляют, только если система выполняет его операции (`objects` — `listKinds`, `listUnits`, `getTreeChildren`; `automation` — `listRules`; `access` — `getAccess`; `settings` — `getSettings`; `vms.export` — `listExports`, раздел VMS; `journal` — `listJournal`). Незнакомый код клиент пропускает. С 0.32.0 поле обязательное: рельс клиент строит только из `sections`. Таблица кодов — [BACKEND.md, «Разделы приложения»](BACKEND.md#разделы-приложения);
  - `features` — необязательные настройки (`serverRoles`, `serverNetwork`, `archiveEncryption`); без них поле видно в записи, но менять его нельзя — `422 NOT_SUPPORTED`.

  Интерфейс читает `capabilities` при старте и прячет неподдержанное, тесты API его пропускают, а покрытие считают по объявленному. Объявленное обязано работать по контракту целиком: «умею, но по-своему» не бывает. Что обязан бэкенд — [BACKEND.md, «Возможности системы»](BACKEND.md#возможности-системы). Тесты API идут по слоям (механизм, профили, API видео): тест профиля, которого система не объявила, пропускается, а не падает ([TESTS.md, раздел 1](TESTS.md#1-тесты-api)).
- **Слои контракта.** Одни схемы и пути нужны любому бэкенду, другие — только тому, кто объявил профиль подсистемы. Слой пишет расширение `x-layer` у схемы, у пути или у поля общей схемы:
  - **Нет `x-layer` — механизм.** Его делает каждый бэкенд: виды, объекты, профили, права, правила, операции, поток событий.
  - **`x-layer: <id профиля>`** (например `vms.pos/1`) — схема, путь или поле нужны бэкенду, который объявил этот профиль.
  - **`x-layer: video`** — просмотр, архив, выгрузка: их заберёт будущий API видео.
  - **`x-layer: vms`** — часть VMS без своего профиля. Её вынесет переделка по слоям, а не этот контракт.
  - Клиент пропускает `x-layer`, как любой ключ `x-*`. Ответы сервера и запросы от пометки не меняются.
  - Механизм не ссылается на схему подсистемы. Поле подсистемы в общей схеме (`UnitKind.x-archive`) получает `x-layer`, а владелец контракта вносит его в `KNOWN_LEAKS` в `tools/layers.py`: список только сокращается. `python3 tools/check_api.py` проверяет границу, `python3 tools/check_layers.py` — саму проверку.
  - Какой слой у каждой версии с 0.3.0, написано в [`docs/contract-layers/versions-by-layer.md`](../docs/contract-layers/versions-by-layer.md). Новая версия контракта добавляет туда строку, а `check_api.py` следит, чтобы она была.
- **Мост страницы подсистемы (`x-bridge`, с 0.34.0).** Своя страница подсистемы (`setupUi.mode: iframe`) просит consolem вызвать операцию контракта, и consolem выполняет вызов своим токеном и с правами человека ([`SETUP-UI.md`](SETUP-UI.md), «Шаг 2: мост к механизму»). Что странице можно, говорит расширение `x-bridge` у операции:
  - **`read`** — чтение. consolem выполняет вызов сразу. Это `GET`, а из `POST` — только `validateUnits`: он ничего не записывает;
  - **`act`** — команда объекта или долгая работа, которую карточка consolem тоже запускает сразу (`runUnitAction`, поиск в сети, `uploadFile`). Команду своему объекту и его потомкам consolem выполняет сразу, команда видна в журнале. С 0.35.0 команду объекту вне своего (и команду вида, `runKindAction`) consolem сначала подтверждает своим диалогом, а `cancelOperation` выполняет только для операций, которые запустила эта рамка;
  - **`draft`** — правка объектов склада (`patchUnit`, `createUnits`, `deleteUnit`, `moveUnit`, `deleteObjects`, `createOperation`). consolem кладёт шаг в черновик карточки и выполняет его по «Применить» вместе с правкой самой страницы;
  - **нет `x-bridge`** — операция закрыта, мост отказывает `NOT_SUPPORTED`. Мост закрывает права и сеанс, запись автоматизации (правила, расписания, режимы, группы особых дней), настройки системы и ключи (и чтение, и запись), работу оператора (видео, архив, выгрузка), откат и повтор операций, поток и служебные пути `/test/*`. `act` получают только операции из списка `BRIDGE_ACT`: `runUnitAction`, `runKindAction`, `cancelOperation`, `startDiscovery`, `stopDiscovery`, `uploadFile`. Чтение автоматизации мост открывает как `read`: `listRules`, `getRule`, `listSchedules`, `getSchedule`, `getModes`, `getModeCurrent`. Журнал событий мост тоже открывает как `read`: `listJournal`, `listJournalFacets`, `listJournalKinds`. С 0.35.0 журнал страница читает только по своему объекту и его потомкам и без аудита. Выгрузку журнала (`exportJournal`) мост закрывает: рамка не сохраняет файлы. Запуски правил (`listRuleFires`), версии правил (`listRuleVersions`) и группы особых дней (`listDayGroups`, `getDayGroup`) мост закрывает и для чтения. Список закрытых с причиной у каждой — `BRIDGE_CLOSED` в `tools/check_api.py`.
  
  Клиент и сервер пропускают `x-bridge`, как любой ключ `x-*`: ответы и запросы от пометки не меняются, а права сервер проверяет на каждом пути, как раньше. `python3 tools/check_api.py` («Мост страницы») не пропускает операцию без `x-bridge` и без строки в `BRIDGE_CLOSED`: о новой операции решают сразу, когда её добавляют в контракт.
- **Область системы** (с 0.28.0). Область системы (домен) — часть системы, у которой свои объекты, права и лицензии. У VMS это домен, у оркестратора агентов — рабочее пространство. Область и папку бэкенд узнаёт по профилю механизма, а не по коду вида:
  - **`core.domain/1`** — вид области. Объект области — корень: `parentId: null`, `domainId: null`. У остальных объектов `domainId` — `uid` их области. Области — верх дерева в каждой раскладке.
  - **`core.folder/1`** — вид папки: `name`, `parentId` — родительская папка или `null` (корень области). Состав папки — `Unit.folders` у членов.
  - Профили механизма ведёт владелец контракта (`owner` в [`api/profiles/core.domain.json`](profiles/core.domain.json), [`core.folder.json`](profiles/core.folder.json)). Свойств у них нет. Профили `vms.domain/1` и `vms.folder/1` сняты в 0.32.0: область и папку бэкенд узнаёт только по `core.*`.
- **Раскладки дерева.** Раскладку дерева объявляет система: `GET /kinds` → `layouts` (схема `TreeLayout`, с 0.26.0). Порядок раскладок — порядок кнопок срезов. Раскладка — список правил места `place` (`PlaceRule`): первое подходящее правило решает, где объект лежит.
  - **Правило подходит**, если подходят `what` (отбор видов `KindSelector`, как `x-ref`: код вида или профиль; нет — любой вид), `root` (`true` — только корни, `false` — только дочерние) и `where` (значение свойства объекта) **и** правило даёт место. `by`: `area` — прямо под областью объекта (домен); `parent` — под `parentId`, корень — под областью; `folders` — под каждой папкой из `Unit.folders`; `ref` — под целью первого свойства вида с `x-ref`, подходящим под `ref` (значение из `status.observed` под тем же именем главнее `properties`); `group` — под узлом группы; `none` — объекта в раскладке нет. У `folders` место есть, только если у объекта есть папки; у `ref` — если у ссылки есть значение; у `parent` — если у дочернего объекта есть родитель. Не подошло ни одно правило — объекта в раскладке нет. Объект вида с `shape: document` в дереве не бывает никогда. `show` — объект виден, если подходит сам или у него в раскладке есть подходящий потомок; `hide` — объекты этих видов не видны вместе с поддеревом.
  - **Порядок детей:** у области, группы и папки — по номеру правила, затем порядок бэкенда (`partKey`, неизменный между страницами); у остальных узлов — по номеру правила, затем по имени.
  - **Узел группы** (`TreeLayout.groups`): `TreeNode {id: "<id группы>:<uid области>", kind: <id группы>, name: <label.text>, parentId: <uid области>, hasChildren: true, group: true}`. Объекта за ним нет. В `GET /tree/paths` шага группы нет: шаг — всегда объект.
  - **Код раскладки.** Параметр `layout` у `GET /tree/children` и `GET /tree/paths` — `id` из `layouts`, другой — `422 VALIDATION_FAILED`, `field: layout`. `tree.changed {layout, parentIds}` приходит по каждой объявленной раскладке; незнакомую раскладку клиент пропускает. `folders` — раскладка механизма (папки); свою раскладку система называет с префиксом системы (`agent.models`).
  - **Раскладки VMS** — данные набора `demo.json`: `folders`, `servers` (группа `unalloc` — «Нераспределённые серверы»), `archives`, `detectors`. Камера-кластер в `servers` лежит под доменом: свойства-ссылки на сервер у неё нет. Её детекторы видны только при раскрытии, сводного списка по домену в `detectors` нет. Под детектором раскладка `detectors` показывает и его поддетекторы (вид `subdet`). Подписи — `Text` с ключами `layout.<id>`, `layout.<id>.hint`, `layout.servers.unalloc`.
- **Подписи.** Любая подпись в описании вида (`label`, `x-label`, `x-enum-labels`, `ActionDescriptor.label`…) — `Text {key, text, lang}`. Интерфейс сначала ищет `key` в своём словаре (`i18n`), и если ключа нет — показывает `text`: так новый вид приходит с готовыми подписями, а известные переводятся у интерфейса.
- **Описания видов и ETag.** `GET /kinds` отдаёт ETag — хэш описаний, профилей и раскладок (`layouts`); `If-None-Match` с тем же тегом — `304`. Описание вида могут поменять на ходу (плагин поставили, обновили): сервер шлёт `kinds.changed`. Объект вида, описания которого нет (`GET /kinds/{kind}` — 404), читается как есть: общая иконка, код вида, правка запрещена; черновик открытой карточки не теряется.
- **Незнакомое поле — только чтение.** Интерфейс пропускает незнакомый ключ `x-*` и поле неизвестного типа или виджета показывает текстом только для чтения; значение не теряется.
- **Секреты.** Поле `writeOnly` в ответе не приходит никогда, о нём говорит `Unit.secrets[имя]: true`. Смена поля из `x-bound-to` без нового секрета — `422` с указателем на поле секрета.
- **Версия объекта и применение.** `PATCH /units/{uid}` отвечает сразу; пока система не применила правку, `status.observedVersion` отстаёт от `version` (условие `Applied`).
- **Тексты.** Сервер отдаёт коды (`role: "primary"`, `detectorKind: "motion"`, `fault: "auth"`) и числа (`sizeBytes`, `usedPercent`), подписи и переводы — в интерфейсе. Трасса запуска правила и проверка правила — тоже кодами с параметрами (`{code: "device.offline", params: {deviceId}}`). Имена объектов, тексты журнала и истории прав, шаблоны текстов в правилах — данные.
- **Время** — в UTC (ISO 8601), даты — `ГГГГ-ММ-ДД`, время суток в расписаниях — `ЧЧ:ММ` в поясе системы. Интерфейс показывает время в часовом поясе системы из `GET /me` (`timezone`); расписания и режим объекта сервер считает в нём же.
- **Пароли** только записываются: в запросе `password` (у облачного тома — `secret`), в ответе — `hasPassword` / `hasSecret`.
- **Черновики** остаются у клиента. У «Оборудования» это черновик карточки: «Применить» отправляет операцию. Если запись тем временем поменял другой администратор, нетронутые поля обновляются, а правки пользователя остаются поверх. У «Прав» черновик — весь снимок, «Применить» уходит пакетом. У «Автоматизации» — черновик правила (новое правило до «Применить» есть только у клиента) и расписания в редакторе.

## Модель данных

Две записи ядра и профили. Всё «данное» о виде приходит с сервера, код остаётся только для смысла профилей.

### `UnitKind` — описание вида (`GET /kinds`)

| Поле | Что значит |
|---|---|
| `kind` | код вида: `camera`, `archive.local`, `security_controller/CONTROLLER`, `<подсистема>/<таблица>` для строк таблиц w2c |
| `label`, `labelPlural`, `labelCount`, `icon` | подписи (`Text`) и значок; `labelCount` необязателен |
| `parents`, `createParents`, `children` | кто может быть родителем; под кем вид заводит оператор (`createParents` пуст — только вместе с новым родителем, как том с хранилищем); какие виды бывают дочерними |
| `implements` | профили вида (`vms.camera/1`…): по ним интерфейс выбирает ручной экран, сервер — хуки |
| `capabilities` | что система умеет с видом: `create`, `rename`, `delete`, `enable`, `folders`, `bulkSet`… Вид, который сервер находит сам, не создаётся и не удаляется |
| `schema` | JSON Schema свойств `Unit.properties`; расширения полей `x-*`: `x-label`, `x-enum-labels`, `x-ui-tab`, `x-ui-group`, `x-ui-order`, `x-ui-unit`, `x-ui-widget`, `x-ui-filter`, `x-search`, `x-ref {kinds, implements}`, `x-immutable`, `x-bound-to`, `x-rights`, `x-inherit`, `x-template`, `x-transient`, `x-dev` (см. «Расширения описаний» ниже); независимые условия — `allOf` из `if/then/else`; `examples` (с 0.30.0) — подсказки значений: форма предлагает их и принимает ввод руками, сервер по ним не проверяет; `readOnly` — заполняет сервер, `writeOnly` — секрет |
| `schemaPerUnit`, `shape` | схема своя у каждого объекта (`GET /units/{uid}/schema`: условия, в том числе части `allOf`, решены по свойствам объекта; так камера получает параметры своего драйвера); `shape: document` — документ, а не узел дерева (общие настройки домена) |
| `access {class, levels[], also[]}`, `apiRights` | класс доступа вида и его уровни (общий набор `view < edit < admin`, если не объявлен); дополнительные классы (`tel` у камеры); права на пути предметных API. Право (`Right.class`) может назвать и класс другого вида: событие источника событий судится уровнем камер `cam`, а своего класса `cam` у источника нет — в «Правах» у него один тип доступа, как в старом макете |
| `actions[]` | `ActionDescriptor`: `id`, `label`, `execution` (`instant` — ответ сразу, `longRunning` — операция), `scope` (`unit`, `kind`), `params` и `result` (схемы), `right`, `ruleAction`, `ruleOnly`, `ruleRight` |
| `events[]` | `EventDescriptor`: `id`, `label`, `severity`, `params` (по ним — `RuleTrigger.match`), `right`, `ends` (у события есть конец), `rule` (можно брать триггером правила, по умолчанию `true`), `alarm` (попадает в «Что считать тревогой», по умолчанию `true`) |
| `setupUi {url?, kinds, mode, protocol?, origin?}` | своя страница подсистемы: `mode: tab` — новая вкладка, страница пишет сама; `mode: iframe` (с 0.33.0) — страница в карточке по протоколу `protocol` (нет поля — `setup/1`), правку записывает клиент, сообщения — только с `origin` (нет поля — происхождение адреса), право — `view`. У `mode: tab`: есть `url` — постоянный адрес, клиент дописывает `?type=&id=&lang=`; нет `url` — адрес на одно открытие из `POST /units/{uid}/setup-ui`. У `mode: iframe` consolem всегда берёт адрес из `POST /units/{uid}/setup-ui`, даже при `url`: бэкенд дописывает объект, язык и разовый ключ. Ссылка — только с отметкой `setupUi` в `Unit.capabilities` |
| `statusSchema` | схема `status.observed`: типы и подписи (`x-label`) наблюдаемых полей |
| `x-archive`, `x-ui-category` | расширения уровня вида: что умеет вид хранилища; где вид в мастере и срезах (см. «Расширения описаний» ниже) |

#### Расширения описаний (`x-*`)

Описание вида и схема его свойств открыты: незнакомое `x-*` клиент пропускает. Четыре расширения набора несут данные, без которых известные экраны не строятся, — их надо отдавать. Схемы — в контракте: `UnitKind.x-archive`, `UnitKind.x-ui-category`, описание `JsonSchema`.

| Расширение | Где | Что значит | Кто читает | Что без него |
|---|---|---|---|---|
| `x-archive {serverRequired, encryption, check, address, recordModes, replicaSource, serverWide, archiveModes, archiveModeDefault?, admits}` | вид хранилища (`vms.archive/1`) | что умеет вид: под сервером или на весь домен, поля тома (`address`: `disk`, `nas`, `bucket`), режимы записи камер, источник `replica`, одно на сервер, свои режимы хранилища, принимает ли записи | сервер (смысл хранилища, проверки тома и записи камеры) и интерфейс (экраны хранилищ, выбор хранилища в записи камеры) | вид хранилища не заводится и в записи камеры не предлагается; объект виден общей формой по схеме |
| `x-ui-category [{group, view, subtype?}]` | вид | группа мастера добавления (`video`, `io`, `acfa`, `integ`, `svc`), срез экрана оборудования (`cam`, `acfa`, `sys`), подвид пункта мастера (`ipsrv-nvr`) | интерфейс | вид не попадает в мастер; объекты вида видны в дереве и правятся формой по схеме |
| `x-hidden` | поле схемы | форма поле не рисует; сервер отдаёт его в `properties`, `PATCH` без поля значение не меняет (служебное поле плагина) | интерфейс | поле видно в форме |
| `x-transient` | поле схемы | значение только в запросе: сервер его судит, но не хранит и не отдаёт (`confirmShrinkBytes` тома, `configMode` и `templateId` камеры при добавлении) | сервер (проверка), интерфейс (поле формы без значения в записи) | поле хранилось бы и возвращалось как обычное |
| `x-template` | поле схемы (строка) | текст с подстановками `{…}` события правила (текст тревоги, письма) | интерфейс (предлагает подстановки) | простая строка без подсказки подстановок |
| `x-dev` | поле схемы | параметр самого устройства (драйвера камеры): бэкенд записывает его в устройство, только когда объект передаёт свои настройки устройству — у камеры это флажок `streamsMode` (профиль `vms.camera/1` 1.4): `console` — «Отправлять настройки устройству», `device` (умолчание, нет поля — тоже `device`) — «Использовать настройки устройства». В режиме `device` значение сообщает устройство: части `allOf` схемы камеры делают поля `x-dev` только для чтения, схема объекта (`GET /units/{uid}/schema`) это показывает, правку сервер отклоняет `422` | бэкенд (пишет в устройство), интерфейс (поле только для чтения, пока объект не передаёт настройки) | поле консоли: правится всегда и в устройство не уходит |
| `x-conflicts {значение: [значения]}` (с 0.30.0) | свойство `analyticsKind` вида детектора — расширение профиля `vms.detector/1` (версия 1.1) | несовместимые на одном сервере виды серверных детекторов; связь двусторонняя, достаточно строки у одного из значений; прежнее место — `reference.analyticsConflicts` (устарело) | сервер (`409 BUSY`, `reason: incompatible`) и интерфейс (плашка, мастер детекторов) | несовместимых видов нет |
| `x-events {значение: [коды событий]}` (с 0.40.0) | свойство `analyticsKind` вида детектора — расширение профиля `vms.detector/1` (версия 1.3) | какие события камеры (`UnitKind.events` вида `camera`) поднимает серверный детектор этого вида сверх `other`: `fireSmoke` — `fire` и `smoke`, `sceneChange` — `tamper` | сервер (`POST /test/events`, `unit.event`: код вне строки — `422 VALIDATION_FAILED`, `field: eventId`) и интерфейс (события детектора в правиле) | только `other` |

### `Unit` — объект (`GET /units`)

`uid`, `kind`, `parentId` (`null` — корень домена), `name`, `domainId`, `folders[]`, `version` (непрозрачная строка), `properties` (по схеме вида), `secrets {имя: true}`, `inherited {имя: {from: unit | domain | default}}`, `status {link, observed, observedVersion, conditions…}` (то, что система видит сама), `writable[]` (что правится у этого объекта сейчас), `capabilities`, `hasChildren` (есть дочерние объекты, которые показывает дерево: потоки и документы не считаются), `match {field}` — в ответе поиска, в каком поле нашлось. Краткий вид для узла дерева — `UnitBrief` (`uid`, `kind`, `name`, `parentId`, `domainId`, `version`, `subtype`, `status`, `brief`): `subtype` — подвид (`nvr`, `io`…): значение свойства `subtype` объекта (`properties.subtype`); `brief` — свойства с `x-search` и `x-ui-filter`, `enabled`, `serverId`.

Остальные записи — как в старом контракте:

| Запись | Главное | Связи |
|---|---|---|
| `Rule`, `RuleVersion`, `RuleFire` | события → условия → шаги, запуск, «Только журнал», приглушение, порядок; версии истории; запуски с трассой | события — `{source: "unit", kinds[] \| implements[], event, match}` из `UnitKind.events`; действия — `{type: "unitAction", action, params}` из `UnitKind.actions`; цели — `{uid}` или область `{area: folder \| server \| domain, uid}`; удалённое — по имени |
| `RulePrompt` | открытый вопрос оператору: шаг `ask` или уровень `escalate`, роль, срок | `ruleId`, `fireId`, `step` |
| `Schedule`, `DayGroup`, `Modes`, `ModeCurrent`, `MaintenanceWindow` | расписания, особые дни, режимы объекта, окна обслуживания | как в старом контракте |
| `Access` | роли, пользователи, группы, каталоги, доступ учёток потоков, история | `Role.kindAccess {класс: уровень}` вместо полей категорий; `folderAccess` и `objectAccess` — карты, ключ — `uid`, значение — уровень класса объекта |
| `Settings`, `License`, `JournalEvent` | значения опций, лицензии, журнал | — |

Объекты не принадлежат серверу: они лежат в пуле домена и раскладываются по папкам. Связь с сервером — через хранилище записи (камера), расчёт детектора, службу сервера (`status.observed.serverId` или свойство вида с `x-ref` на сервер).

### Профили

Профиль публикует контракт (`GET /kinds` → `profiles`, схема `Profile`); вид объявляет `implements`. Ручной экран привязан к профилю, а не к виду. Профиль — это имена свойств (`properties`), имена наблюдаемого (`status.observed`) и предметные пути (`apis`), а тип и смысл каждого имени фиксирует сам профиль: вид, объявивший профиль, несёт свойство под тем же именем, того же типа и с тем же смыслом. **Эталон схемы вида** — `GET /kinds/{kind}` эталонного набора (`camera`, `archive.local`, `volume`…). Каждый профиль лежит в файле [`api/profiles/<имя>.json`](profiles/README.md) (источник истины), таблица для людей — `api/profiles/<имя>.md`; их собирает `tools/build_api.py`. Правила файла, версий и зависимостей — [`api/profiles/README.md`](profiles/README.md).

**Клиент и незнакомая версия.** Сервер отдаёт профиль с младшей версией (`version`), а вид пишет в `implements` только старшую (`vms.camera/1`).

1. Версия выше, чем знает клиент (`1.7` при известной `1.5`): особый экран работает, новые поля клиент показывает в «Все параметры».
2. Версия ниже (`1.4` при известной `1.5`): особый экран не показывает поля, которых в `1.4` нет.
3. Незнакомая старшая версия (`vms.camera/2` без `vms.camera/1`): клиент пропускает профиль и открывает объект формой по схеме.

### Виды набора

Вид на каждый вид устройства старого контракта (`camera`, `ipsrv`, `det`, `acfa`…), плюс `domain`, `server`, `folder`, `volume`, `stream`; хранилища — вид на каждый вид хранилища (`archive.local`, `archive.network`, `archive.cloud`, `archive.backup`, `archive.edge`, `archive.incidents`): у них разные схемы адреса и режимы. Подвиды `ipsrv` — свойством. Потоки камеры — дочерние объекты вида `stream`; поддетекторы (с 0.12.0) — дочерние объекты вида `subdet` под детектором. Незнакомые виды — для приёмки: `security_controller/CONTROLLER` и `security_controller/SENSOR` (перевод настоящего манифеста psim из `plugins/`: ссылки на камеры `x-ref`, команды, события, `setupUi`), `security_controller/KEYPAD` (вид стенда, в манифесте `plugins/security_controller/plugin.json` его нет: своя страница `setupUi.mode: iframe`, с 0.33.0), `test.unknown` (все виды полей и виджетов `x-ui-*`), `test.perunit` (схема на объект), `w2c.example/rows` (строка таблицы с хозяином), `domain.shared` (документ общих настроек домена).

## Что добавлено в 0.3.0

Запрос команды mockup о цепочке правила (`requests/2026-11-05-130700Z-mockup-rule-chain-request.md`). Всё необязательно, умолчание сохраняет прежнее поведение, ничего не снято и не переименовано, поэтому в «Ломающие изменения» это не входит.

- `Rule.whenLogic` и `Rule.condLogic` — `any` или `all` (умолчание `all`): «или» между событиями и между условиями.

- Шаги хода выполнения `check` (проверить `record`, `safe`, `armed` или `online`, ветки `yes` и `no`), `after`, `abort`; их объявляет `reference.ruleControls`.
- `Rule.runAt.everyMin` и `randomShift` — расписание с интервалом.
- События и команды видов камеры, реле, сервера, тома и динамика; действия `ntf.push`, `client.sound`, `client.voice`, `client.view`, `client.program`; новые поля `record`, `alarm`, `alarmclose`, `preset`, `ntf.email`, `net.http`. События и команды видов — в `UnitKind`, поэтому форма показывает их сама.
- Встроенный сервер исполняет «или», `check`, `abort` и расписание с интервалом по-настоящему; остальные новые шаги, команды и действия объявляет и пишет в журнал запуска, но ничего не делает (`BACKEND.md`, «Автоматизация — поля и действия»).

## Что добавлено в 0.33.0

Своя страница подсистемы, шаг 1: вид с `setupUi.mode: iframe` показывает свою страницу в карточке, в рамке. Правку страница отдаёт сообщениями протокола `setup/1`, а записывает её клиент своим обычным путём карточки. Основание — запрос владельца к w2c «Своя страница подсистемы в рамке» (`requests/2026-11-18-120707Z-owner-setup-ui-iframe-request.md`, ответ w2c — `…-response.md` рядом) и описание решения `docs/contract-layers/2026-11-18-setup-ui-iframe-design.md` (раздел 10). Правку механизма сделал владелец контракта (joynickray). Слой — механизм. Ломающих изменений нет: право `view` у `iframe` расширяет доступ, а `mode: iframe` в контракте и раньше значил «позже».

- **Смысл `setupUi.mode: iframe`.** Страница внутри карточки по протоколу `protocol`; правку записывает клиент. `mode: tab` — как раньше: ссылка в новой вкладке, страница пишет сама. Какой экран видит человек: есть страница `iframe` — она, иначе ручной экран по профилю, иначе форма по схеме.
- **`setupUi.protocol`** — версия протокола, `^setup/[0-9]+$`; нет поля — `setup/1`. Незнакомую версию клиент не встраивает и показывает свой экран или форму по схеме.
- **`setupUi.origin` и `SetupUiLink.origin`** — происхождение страницы после перенаправлений двери и прокси, если оно другое, чем у адреса. Клиент принимает сообщения только с него; нет поля — происхождение адреса.
- **`SetupUiLink.readOnly`** — только у `mode: iframe`, бэкенд ставит всегда: `true` — у человека право `view` без `edit`. Клиент передаёт странице `readOnly` и не показывает «Применить».
- **Право по `mode`.** `POST /units/{uid}/setup-ui` и отметка `setupUi` в `Unit.capabilities`: у `mode: iframe` — уровень `view` класса вида (страница сама ничего не пишет, правку записывает клиент правом человека), у `mode: tab` — `edit`, как раньше. Нет права — `403 PERMISSION_DENIED`, `params.right.level` — нужный уровень. У `mode: iframe` клиент берёт адрес этим путём и при постоянном `url`: бэкенд дописывает к нему объект, язык и разовый ключ.
- **Адрес.** Разовый ключ бэкенд кладёт в запрос или в путь адреса, клиент открывает адрес как есть. Относительный адрес клиент разрешает от адреса своей страницы. Встроенный сервер у `mode: iframe` без `url` отдаёт относительный адрес тестовой страницы плагина `api/plugins/<origin.plugin>/setup/index.html?type=&id=&lang=&t=`; у `mode: tab` — по-прежнему `stub://plugin/<плагин>/setup`.
- **Что в эталонном наборе.** Вид стенда `security_controller/KEYPAD` «Клавиатура» (в манифесте `plugins/` его нет) под контроллером: `setupUi {mode: iframe, protocol: setup/1}`, схема из пяти полей (`code_length`, `display_text`, `backlight`, `beep`, `lock_after_tries`), без `create` — мастера под контроллером и в корне прежние. Объект «Клавиатура у входа» под «Контроллер охраны — вход». У `CONTROLLER` и `SENSOR` `mode: tab` не изменился.
- **Протокол `setup/1`** — [`SETUP-UI.md`](SETUP-UI.md) и JSON Schema сообщений [`setup-ui.schema.json`](setup-ui.schema.json) (для сценариев интерфейса её собирает `python3 tools/build_api.py` в `setup-ui.schema.js`, `window.CONSOLEM_SETUP_UI_SCHEMA`). Каждое сообщение — `{proto: "setup/1", type, …}`, незнакомый `type` и незнакомое поле получатель пропускает. consolem отправляет странице `init`, `draft`, `applied`, `errors`, `revert`, `theme`, `flush`; страница отправляет `ready`, `change`, `invalid`, `height`, `flushed`. Правка страницы — JSON Merge Patch к `unit.properties`, всегда весь черновик; указатели полей — `/properties/<имя>`, как `Problem.errors[].field`. Записывает правку клиент своим обычным путём карточки: `POST /units/validate`, план, `POST /operations` с `expectedVersions`. `init.host` шага 1 — `{proto, apply}` без `bridge`. Сверка `check_api.py` «Протокол страницы setup/1»: разрешённые ключевые слова схемы, ссылки только в `$defs`, примеры по схеме, таблицы `SETUP-UI.md` против `$defs`, `problem` против `Problem`.
- **Библиотека страницы `setup-bridge.js`** — для автора своей страницы, описание — [`SETUP-UI.md`](SETUP-UI.md), раздел «Библиотека». `SetupBridge.connect(opts)` отправляет `ready` и сбывается на `init`; `Session.change(patch)` отправляет черновик целиком (`false` при `readOnly`), `invalid`, `height`; на `flush` библиотека зовёт `onFlush`, отправляет неотправленный черновик и `flushed`. `merge` и `diff` — JSON Merge Patch. Библиотека принимает сообщения только от `window.parent` и с происхождения consolem (`opts.origin`, иначе `location.ancestorOrigins[0]`, иначе `document.referrer`). Правило стенда (приём с `"null"` и `"file://"`) — только у страницы с диска или с непрозрачным своим происхождением; настоящая страница без происхождения consolem не подключается и пишет причину в консоль. Сверка `check_api.py` «Библиотека страницы setup-bridge.js: протокол setup/1»: сценарий 13 проверяет тестовую страницу стенда, остальные — библиотеку на поддельном окне (каждое сообщение — по схеме своего `type`). Число сценариев сверка печатает в итоге.
- **Тестовая страница стенда** `plugins/security_controller/setup/` — образец своей страницы на `setup-bridge.js` для `security_controller/KEYPAD`. Две вкладки: «Код» (`code_length`) и «Экран» (`display_text`, `backlight`, `beep`). Поле `lock_after_tries` страница нарочно не показывает: на нём клиент проверяет ошибки поля не на странице, а прототип 80 — ещё и строку покрытия (режима сравнения в `index.html` нет). `ready.fields` — четыре указателя этих полей. Страница отправляет `invalid`, если `code_length` вне 4–8 или `display_text` длиннее 32 знаков. Ошибки `errors` страница показывает красной рамкой у поля, при `readOnly` поля неактивны. Тексты страница берёт по `init.lang` (`ru`, иначе `en`), тему — из `theme.tokens`. Запросов страница не делает и своих кнопок сохранения не рисует. С 0.34.0 страница на хосте шага 2 показывает ещё блоки по контроллеру и вызывает операции через мост consolem (`call`, `subscribe`, `navigate`, `confirm`): как это устроено, говорит [`SETUP-UI.md`](SETUP-UI.md), «Библиотека», абзац «Образец».

- **Проверки `subdet`.** Родитель принимает поддетекторы, если `detectorKind: motion` или `other` с `analyticsKind` `tracker` или `neural`, иначе `422 NOT_SUPPORTED`, `field: /parentId`, `params.reason: "noSubdetectors"`. `abandoned` — только под `tracker`, иначе `422 NOT_SUPPORTED`, `field: /properties/subdetectorKind`. `line` требует `zone.shape: line`, остальные виды — `rect` или `polygon`, иначе `422 VALIDATION_FAILED`, `field: /properties/zone`, `params.reason: "shape"`. `a2a` требует `zoneTo`, остальные виды его не принимают, иначе `field: /properties/zoneTo`, `params.reason: "required"` (нет у `a2a`) или `"unexpected"` (есть у другого вида). `stop` и `abandoned` требуют `timeSec` не меньше 1, иначе `field: /properties/timeSec`, `params.reason: "required"`. `speed.min` выше `speed.max` — `reason: "minAboveMax"`. Принимает ли родитель поддетекторы, сервер проверяет при создании. Правило `abandoned` (только под `tracker`) сервер проверяет при создании и в правке, которая называет `subdetectorKind`: вид родителя сменили позже — поддетектор остаётся, и его можно править. Хук не берёт блокировку родителя: над детектором может идти операция плана (запрос [`2026-11-10-103516Z-mockup-stream-steps-in-operations-request.md`](requests/2026-11-10-103516Z-mockup-stream-steps-in-operations-request.md), пп. 1–2).
- **Дерево.** `GET /tree/children` с `layout=detectors` под детектором отдаёт и его поддетекторы; у детектора с поддетекторами `hasChildren: true`. В раскладке `servers` дети те же.
- **Удаление.** Поддетекторы уходят с детектором (`entity.deleted` на каждый, вид `subdet`). Удаление детектора, как и прежде, назад не возвращается; удаление самого поддетектора шагом `delete` возвращается откатом.
- **Что в эталонном наборе.** Новые настройки — у детекторов «Детектор движения», «Детектор 5» и «Детектор 8»; новые детекторы «Трекер объектов» (`other`/`tracker`) и «Нейросетевой трекер» (`other`/`neural`) под камерой «Запасной вход». Поддетекторы: у «Трекера объектов» — «Долго у входа» (`dwell`) и «Въезд на парковку» (`line`), у «Детектора движения» — «Вход у двери» (`enter`). Профиль «один домен» этих видов, свойств и детекторов не объявляет.

## Эталонный набор

`fixtures/demo.json` — данные основного макета в виде ответов API: разделы `kinds` (описания видов), `profiles` и `units` вместо `domains`, `servers`, `devices`, `folders`, `archives`, `volumes`; остальные разделы (правила, расписания, права, опции, журнал, справочники) — как в ответах API, ссылки на объекты в них — по `uid`. `uid` равен прежнему `id` записи старого макета. Набор правится руками: описания видов (включая `security_controller/*` по манифесту из `plugins/` и синтетические `test.*`) и объекты; после правки — `python3 tools/profile_fixture.py` и `python3 tools/build_api.py`. Демо-запуски правил посчитаны тем же движком, что у встроенного сервера (`tools/fixture_fires.js`). Сдвиг дат и остальные поля:

- `capturedAt` — момент снимка. При загрузке каждая дата и каждый момент сдвигаются на «сейчас − `capturedAt`», даты — на целые сутки. Так «вошёл вчера» и «истекает через неделю» остаются правдой в любой день. Календарь — расписания и особые дни — не сдвигается: праздник остаётся праздником.
- `modeManual` — режим объекта, включённый вручную (`null` — по расписаниям).
- `network` — что «видно» в сети каждого домена: это находит поиск. С 0.36.0 у строки есть `serverIds` (какие серверы её видят; нет — все серверы домена) и `category` (нет — `ip`). `discovery` — итог последнего поиска.
- `me` — администратор, от имени которого работает стенд.
- `reference.capabilities` — что умеет система с этим набором: в `demo.json` — весь контракт.

### Набор профиля one-domain

`fixtures/one-domain.json` — система, которая умеет часть контракта. Так выглядит VMS с одним доменом на установку, камерами и детекторами, хранилищами из одного тома без шифрования, правилами и пользователями. Набор собирает `tools/profile_fixture.py` из `demo.json`: берёт первый домен, его серверы, камеры с детекторами, папки, хранилища (первый том, без шифрования), правила, у которых после этого остались события и действия (из целей уходит то, чего в профиле нет), всех пользователей. Чего в профиле нет:

| Нет | Как это выглядит в API |
|---|---|
| второго домена | у вида `domain` нет `create` и `delete` в `UnitKind.capabilities`, `createParents` пуст |
| видов, кроме камер и детекторов, плагинов и тестовых видов | в `GET /kinds` их нет; тесты с `needs: kind:…` пропускаются. Исключение — виды, чьи события и действия предлагает редактор правил (`ruleActions` профиля): датчик (`io.input`), источник событий (`text`), СКУД и её единицы (`unit`), реле (`output`). Их описания в `GET /kinds` есть — каталог правил собирается из них, — но объектов нет и завести их нельзя: без `create`, `createParents` пуст, без `x-ui-category` (`RULE_ONLY_KINDS`). Тесту объектов такой вид не годится: `needs: kind:…` требует, чтобы вид заводился или его объекты были в наборе |
| лицензий | нет `listLicenses` |
| поиска в сети | нет `getDiscovery`, `startDiscovery`, `stopDiscovery` ; у вида `domain` нет профиля `vms.discovery/1` |
| томов сверх первого | у вида `volume` нет `create` и `delete`; первый том заводится строкой нового хранилища (`children`), под существующим — `422 NOT_SUPPORTED`. Класса доступа `tel` у камеры нет |
| ролей и сетевых настроек серверов, шифрования | `features: []` |

Набор не правят руками: правят `demo.json` или правила в `tools/profile_fixture.py` (отбор по видам и профилям, `KIND_MISSING`, `PLUGIN_KINDS`, `RULE_ONLY_KINDS`, `MISSING`) и собирают заново: `python3 tools/profile_fixture.py`. Макет с этим набором — `index.html?fixture=one-domain`. Набор `large.json` — тот же профиль без записей оборудования, в `stand.large` только числа (250 000 камер, 500 серверов): записи считает заглушка при загрузке (`expandLarge` в `server.js`). В отличие от `one-domain`, у `large` и `xl` есть ассистент (`assistTurn`, функция `assist`): стенд меряет поиск вместе с ним. Набор `xl` — тот же `large` с другими числами (1 000 000 камер, 2 000 серверов, 1 200 папок): в `fixtures/xl.json` только наложение — `"$base": "large"` и `stand`, в `fixture.js` он собран `Object.assign` поверх `large`, а не второй копией (`tools/build_api.py`, `tools/serve_api.mjs`). Макет — `index.html?fixture=xl`.

### Набор agents

Набор `agents.json` — система не из мира VMS: оркестратор агентов. Он нужен, чтобы доказать: механизм контракта (всё без `x-layer`) работает без камер, серверов и хранилищ. Набор пишут руками; раздел `profiles` собирает `python3 tools/build_api.py` (только профили, которые называют виды набора: `core.domain/1`, `core.folder/1`). Раскладки дерева (`layouts`, с 0.26.0): `folders` (как в `demo`, без `hide` потоков: потоков в наборе нет), `agent.pipelines` (конвейер под областью, шаги под конвейером), `agent.models` (модель под областью, агент под своей моделью по ссылке `modelId`, агент без модели — под областью).

Что в нём:

- виды `domain` («Рабочее пространство», без `create` и `delete`) и `folder` — область системы и папка; виды `agent.pipeline` («Конвейер», дети — `agent.step`; команды `start`, `stop`; события `finished`, `failed`), `agent.step` («Шаг», ссылка `agentId` на агента), `agent.agent` («Агент»: ссылки `modelId` на модель и `toolIds` на инструменты; команды `start`, `stop`, `check` для правил; события `failed`, `done`; класс доступа `agent` с уровнями `view`, `run`, `edit`), `agent.model`, `agent.tool`;
- объекты: одно рабочее пространство, папки «Поддержка» и «Аналитика», две модели, три инструмента, три агента (у одного `modelId: null`), два конвейера; одно правило «Агент упал — перезапустить»;
- `reference.capabilities.operations` — все операции путей без `x-layer`, кроме настроек (`getSettings`, `patchSettings`), лицензий и ключей, ассистента и каталогов доступа; `features: []`. Справочников VMS в `reference` нет (сняты в 0.32.0). Каталог правил (с 0.31.0) — только механизм: условия `time`, `online`, проверка `online` (`ruleChecks`), действия `net.http`, `rule.runrule`; область папки — раскладка `folders` (`ruleTargets.areaLayouts`).

Проверки: `python3 tools/check_api.py` (набор против контракта и строка «agents: только операции механизма»), `python3 tools/run_api_tests.py --fixture agents` (тесты механизма идут, тесты видео и профилей пропускаются с причиной). Макет с этим набором — `index.html?fixture=agents`. Загрузить в стенд: `POST /test/reset {fixture: "agents"}`, `node tools/serve_api.mjs --fixture agents`.

Числа `stand.large` — на весь набор: `cameras`, `servers`, `folders`, `serverCameras` (камеры под серверами), `clusters`, `relayed` (кластеры за ретранслятором); `firstBranch` — ветка первого сервера, она своя в каждом домене. Необязательные `domains` (доменов, по умолчанию 1) и `domainNames` (имена по порядку, иначе «Домен N») делят набор на домены: `expandLarge` раскладывает всё поровну блоками по порядку. Домены сверх первого — копии первого домена набора (те же свойства и доступ; роли стенда на домены не завязаны). У каждого домена свои серверы с хранилищами и томами, свои кластеры, папки в корне домена и камеры: камера сервера — в домене сервера, камеры без сервера — поровну, камера в папке — только в папке своего домена. Ретранслятор — у первого домена, за ним его доля `relayed`. Номера — сквозные: uid, имена серверов («Кластер N/Сервер NNN»), папок и камер не повторяются в наборе, а при `domains: 1` раскладка та же, что у `large`. У `xl` — `domains: 4`: Москва, Санкт-Петербург, Казань, Новосибирск; каждый — как `large`: 250 000 камер, 500 серверов в 40 кластерах, 300 папок, 50 000 камер под серверами, ветка первого сервера — 1 000 камер, ретранслятор (5 кластеров) — у Москвы. Домены `xl` заводит стенд из чисел при загрузке; завести или удалить домен профиль по-прежнему не даёт: у вида `domain` нет `create` и `delete`.

## Тестовый стенд

Служебные операции (тег `test-support`) есть только у встроенного сервера на странице тестов и у тестового стенда бэкенда:

- `POST /test/reset` — загрузить набор по имени (`fixture`: `demo`, `one-domain`, `large`, `xl` или `agents`; `fixturePatch` — изменения на прогон в формате JSON Merge Patch, `actAs` — от имени другого логина), остановить часы (`freezeClock: false` — пусть идут);
- `POST /test/clock` — сдвинуть часы на `advanceSec` и выполнить всё, что за это время наступило: шаги операций, форматирование, поиск в сети, синхронизацию каталогов;
- `POST /test/events` — событие извне: устройство потеряло или вернуло связь, сменилась причина; событие объекта по описанию его вида (`unit.event`);
- `PUT /test/kinds/{kind}` — добавить или заменить описание вида на ходу: `kinds.changed`, новый ETag `/kinds`;
- `POST /test/stream-elsewhere` — открытые потоки ушли на другой экземпляр: `PUT /stream/{clientId}/watch` на них отвечает `404`.

| `python3 tools/check_ui.py [--latency 300]` | сценарии интерфейса `tests/ui-*.js` (в том числе `ui-unknown.js` — незнакомый вид): действия пользователя → запросы → экран и сервер; `ui-profile.js` — на наборе one-domain: неподдержанное спрятано |
| `python3 tools/check_ui.py --selftest` | самопроверку прототипа `?selftest`: те же сценарии изнутри страницы |
| `python3 tools/check_stand.py [адрес] [--fixture one-domain] [--clock real]` | внешний режим целиком: тесты API и прототип `?selftest` открываются с диска и работают со стендом по HTTP — с образцом `tools/serve_api.mjs` или со стендом бэкенда по адресу |
| `python3 tools/compare_screens.py --page index_NN_….html --against index.html` | внешний вид прототипа против основного макета: те же экраны, разметка по разметке (оба над `api/`) |

Прототип проверяют теми же командами с `--page index_NN_….html`.

`tests/api.html?api=https://адрес` — те же тесты API против стенда бэкенда (см. `BACKEND.md`); `&fixture=one-domain` — с набором профиля, `&clock=real` — без остановки часов. `node tools/serve_api.mjs` — образец тестового стенда: встроенный сервер за HTTP, с CORS и SSE, как их ждёт клиент.
