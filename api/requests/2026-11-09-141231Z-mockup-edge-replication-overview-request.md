# Запрос от команды mockup: дополнение к запросу о репликации со встроенного хранилища — общий вид, состояние по камере, события

**Статус: новый**

Дополняет [запрос о репликации со встроенного хранилища](2026-11-08-174806Z-mockup-edge-replication-request.md). Запрос оставляем как есть, ниже — что в нём меняется и что нужно ещё.

## Что изменилось в прототипе 37

- **Типы с макросами — только правила.** У встроенного хранилища два постоянных типа: «Выключена» и «Забирать всё». «Заполнять пропуски», «По расписанию» и «Только события» — карточки, которые открывают мастер правила с шаблоном и камерами хранилища. Общего правила, которое ведёт консоль, больше нет: правила создаёт пользователь, консоль только показывает их на странице хранилища.
- **Общий вид.** Срез «Хранилища», домен или сервер, вкладка «Встроенные хранилища»: таблица всех камер со встроенным хранилищем — своя карта или диск регистратора. Строка — камера: у регистратора строка на каждую его камеру. В строке тип репликации, правила, состояние сейчас и подробности; камеры с проблемами стоят наверху.
- **Состояния строки:** «записи потеряны», «нет связи», «забирает», «всё забрано», «не входит» (камера регистратора исключена из постоянной репликации), «не забирает».

Всё это — заглушка: состояние консоль выдумывает по `uid`.

## Что меняется в прежнем запросе

1. **П. 1:** `mode` — только `off` и `all`. Значения `gaps`, `schedule`, `events` не нужны: эти типы делают правила с командой `replicate` (п. 4).
2. **П. 5 больше не нужен.** Метка `managedBy` и общее правило на тип не нужны: консоль находит правила хранилища по команде `replicate`, которая указывает на его камеры.

## Что нужно ещё

1. **Состояние по камере.** У регистратора одно встроенное хранилище на все камеры, а состояние у каждой камеры своё. Нужно `replicationStatus` из п. 2 прежнего запроса на каждую камеру регистратора, например `replicationStatus.cameras: [{cameraId, state, lastTransferAt, nextTransferAt, gaps}]`. Зачем: строка общего вида — камера; без этого у всех камер регистратора одно состояние.
2. **Состояния для всего сервера или домена одним запросом.** Общий вид показывает десятки и сотни камер. Нужен способ получить `replicationStatus` всех встроенных хранилищ сервера или домена одним запросом, например `GET /units?kind=storage&scope=<uid сервера или домена>&fields=replicationStatus`. Зачем: запрос на каждое хранилище — сотни запросов при открытии вкладки.
3. **Изменение состояния — в поток событий.** Событие при смене `replicationStatus.state` и при новом пропуске в `gaps`, с `uid` хранилища и `cameraId`. Зачем: таблица общего вида и страница хранилища обновляются сами, без опроса.
4. **События для правил и журнала.** События встроенного хранилища:
   - `replication.failed` — сервер не смог забрать записи (нет связи дольше срока, ошибка носителя, нет места в хранилище сервера); причина — в параметре;
   - `replication.lost` — устройство записало поверх записей раньше, чем сервер их забрал; параметры — `from`, `to`.
   Зачем: правило может предупредить оператора, а журнал — показать историю. Состояние «записи потеряны» в общем виде берётся из `gaps` с `result: lost`.

## Что сломается у тех, кто уже работает по контракту

Ничего: все пункты добавляют новое. Пункты «Что меняется» сужают прежний запрос, на который ещё нет ответа.
