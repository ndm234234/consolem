# Запрос от команды ngp: как система объявляет профиль, у которого есть не все свойства

2026-11-14 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

Бэкенд поверх NGP готовит `GET /kinds` (прототип 0.2). У NGP есть данные не для всех свойств стандартных профилей. Пример — `vms.camera/1`: в профиле 41 свойство (`api/fixtures/one-domain.json`, раздел `profiles`). Источник в NGP мы пока нашли для 9 из них: номер, адрес, порт, производитель, модель, включённость, сервер, основной и дополнительные архивы. Для части остальных источник ещё ищем.

Документ и тест здесь расходятся:

- `api/BACKEND.md:411`: «Свой вид системы берёт из профиля то, что у него есть». По этому тексту вид может нести часть свойств профиля.
- Тест «Профили: свойства ручных экранов…» (`tests/api-units.js:1074-1086`) требует для каждого профиля из `GET /kinds` → `profiles`, чтобы каждое его свойство было в схеме хотя бы одного вида, который этот профиль реализует (`tests/api-units.js:1083-1086`). Кроме того, тест обращается к `vms.talk/1` и `vms.acs/1` (`:1080-1081`). Если система не вернёт эти профили, тест падает с ошибкой обращения к `undefined`, а не с понятным сообщением.

Пока ответа нет, мы делаем так: схема вида `camera` несёт все 41 свойство профиля, а свойства без источника в NGP помечены `readOnly` и не заполняются. Тест это пропускает. Но WebUI тогда считает такие поля существующими, а `readOnly` у поля вроде `login` или `recordMode` противоречит смыслу профиля.

## Пункты

1. **Как объявить неполный профиль.** Предлагаем один из вариантов, выбор за вами:
   - а) `profiles[].properties` в ответе `GET /kinds` — это свойства профиля, которые система поддерживает. Тогда система вправе урезать список, а тест сверяет только его. Обязательный минимум профиля, без которого ручной экран не работает, контракт перечисляет отдельно.
   - б) Профиль в ответе всегда полный, а вид помечает свойство профиля без поддержки расширением, например `x-unsupported: true`. Интерфейс такое поле не показывает и не шлёт в правке, тест его засчитывает.
   - в) Другое правило — на ваше усмотрение.
2. **Тест «Профили…».** При отсутствии профиля `vms.talk/1` или `vms.acs/1` в ответе тест должен давать понятный `FAIL` (или `SKIP`, если такие профили можно не объявлять), а не ошибку обращения к `undefined`.
3. **`BACKEND.md:411`.** Уточнить текст под выбранный вариант п. 1.
