## Что проверить: запрос о репликации

1. **Тип репликации.** Профиль `vms.edge/1` у вида `storage`, свойство `replication`: `mode` (`off` | `all`), `archiveId`, `speedLimitMbps` (0 — без предела), `excludedCameras`.
   - Типы «заполнять пропуски», «по расписанию» и «только события» — не значения `mode`, а правила с командой `replicate` (п. 4). Шаблоны правил — в интерфейсе.
   - `mode: all` и `recordMode: replica` камеры — одно и то же. `mode` в ответе — `all`, только если каждая камера, кроме `excludedCameras`, забирает с хранилища; иначе `off`. Правка, которая называет `mode`, `archiveId` или `excludedCameras`, меняет режим только тем камерам, у которых он должен измениться.
   - Сервер помнит прежний режим записи и архив камеры, когда ставит ей `replica`. Выключение репликации и исключение камеры возвращают их; если прежнего нет, камера получает `always`. Эта память — внутри сервера, в теле объекта её нет.
2. **Состояние.** `status.observed.replicationStatus`: `state` (`off`, `waiting`, `planned`, `running`, `ok`), `lagSec`, `timeLeftSec`, `lastTransferAt`, `nextTransferAt`, `bytesToday`, `gaps` за 7 дней `{from, to, result: queued | done | lost}`. Камера получила описание `status.observed.replicaLagSec`.
3. **Забор периода вручную.** Отдельной команды нет. `POST /units/{uid}/archive-fetch` камеры заказывает и забор её пропусков внутри периода (`edgeOrdered` в ответе). Новый флаг `edgeOnly: true` заказывает только это: квота «закрепить» (7 на человека) не тратится.
4. **Команда `replicate`.** К `period` `event` и `offline` добавлены `whole` и `last`; новые поля `minutes`, `beforeSec`, `afterSec`, `archive`. Встроенный сервер исполняет команду: забирает пропуски или период, а при отказе поднимает `replication.failed`.
5. **Правило, которое ведёт консоль.** Метки `managedBy` нет: правила создаёт пользователь по шаблонам, как в итоговом прототипе. Страница хранилища находит правила по шагу `replicate`, который называет камеры хранилища.
6. **Проверки перед репликацией.** `status.observed.mediaOk` и `profileG`. `false` у любой проверки: сервер ничего не забирает, состояние `waiting`, один `replication.failed` с `reason` `media` или `profile`.
7. **Событие «Связь восстановлена».** Это событие камеры `device.restored` из 0.3.0, шаблон «Связь вернулась: забрать пропуски с карты» берёт его.

## Что проверить: дополнение об общем виде

1. **Состояние по камере.** У регистратора `replicationStatus.cameras[]`: `cameraId`, `state`, `excluded`, `lastTransferAt`, `nextTransferAt`, `gaps`.
2. **Список одним запросом.** `GET /units?kind=storage` с `serverId` или `domainId` отдаёт `replicationStatus` в каждой строке. Нового пути нет.
3. **Поток событий.** Событие `replication.changed` (`kind: storage`, `payload {state, cameraId?, gap?}`): при смене `state` и при новом или закрытом пропуске. Правка камеры (`recordMode`, `replicaFrom`, `archiveId`) тоже даёт `replication.changed` её хранилища.
4. **События для правил и журнала.** `replication.done` и `replication.failed` (`reason`: `no_link`, `media`, `archive`, `space`, `profile`). Событие камеры `segment.lost` приходит и тогда, когда устройство записало поверх записей раньше забора; у него появились поля `from` и `to`.

## Сверх запросов

- Связь встроенного хранилища следует за связью камеры или регистратора (`device.signal`).
- События, которые сервер поднимает внутри запуска правила, правила слышат из очереди: не больше 50 за раз, правило с `allowChain: false` их не слышит. Так правило «отказ репликации → начать репликацию» не уходит в бесконечный цикл.
- `writable` каждого встроенного хранилища теперь содержит `replication`. Клиент, который по непустому `writable` отличал карту камеры от других хранилищ, должен проверять профиль.
- Стенд: забор идёт по 4 секунды часов сервера на минуту записи; пропуск, не забранный за срок хранения устройства, становится `lost`. `POST /test/events` подкладывает `edge.gap`, `edge.check`, `edge.fail`.

## Чего пока нет

- **Срок хранения карты или диска.** Интерфейс оценивает его как объём / 43 ГБ в сутки на камеру: в контракте есть только `sizeBytes`.
- **`bytesToday` по камере регистратора.** Есть только у хранилища целиком.
- **Забор периода у регистратора** — по запросу `archive-fetch` на каждую камеру. Камера без основного архива получает `409 NO_PRIMARY`. Один запрос на хранилище был бы проще.
- **Связь хранилища с правилами.** Какие правила забирают записи хранилища, интерфейс считает сам по списку правил.
- **Тексты карточек типов** («Когда выбрать», строки об аналогах в Axxon One) — константы интерфейса.
- **Событие начала забора.** Журнал показывает только конец забора и отказы: события `replication.started` нет.
- **`device.restored` по `device.signal`.** Встроенный сервер не поднимает это событие, когда связь камеры вернулась. Шаблон «Связь вернулась» на стенде срабатывает только от `POST /test/events` с этим событием.

## Что сломается у тех, кто уже работает по контракту

Ничего не снято. Камеры с `recordMode: replica` работают, как раньше. Клиент, который проверяет `writable` хранилища, увидит новое свойство `replication`.

- Нужен ли отдельный забор периода на хранилище вместо `archive-fetch` по камерам.
- Поднимать ли `device.restored` на стенде, когда связь камеры вернулась.
- Статус прежних запросов о репликации.
