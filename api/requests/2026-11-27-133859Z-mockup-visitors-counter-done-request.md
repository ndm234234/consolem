## Что проверить

1. **`analyticsKind: visitorsCounter`** — новое значение. События камеры (`x-events`): `visitor.in` (посетитель вошёл), `visitor.out` (посетитель вышел), `indoor.over` (людей в помещении больше порога).
2. **`zoneTo`** (многоугольник, 3–64 точки, координаты 0..1): область 2. Область 1 — `zone` (`rect` или `polygon`). Переход 1 → 2 — `visitor.out`, 2 → 1 — `visitor.in`. Поменять области местами — поменять точки `zone` и `zoneTo`.
3. **`indoorCount`** (boolean, нет поля — false): вести число людей в помещении.
4. **`indoorMax`** (integer, 0–100000, нет поля — 10000): порог; людей больше — событие `indoor.over`.
5. **`indoorStart`** (integer, 0–100000, нет поля — 0): число людей в момент настройки.
6. **Отказы.** Поля счётчика у другого семейства — `422 VALIDATION_FAILED`, `field: /properties/<поле>`, `params.reason: notCounter`. Зона счётчика линией — `field: /properties/zone`, `params.reason: shape`. Сервер судит только поля из запроса: смена семейства хранимые значения не трогает.
7. **Нет возможности.** У четырёх полей `absent: unsupported`: система без такой возможности не кладёт поле в схему вида, и консоль поле не показывает. Есть ли счётчик посетителей у вашего бэкенда?

## Сверх запросов

- Имя `zoneTo` и прежнее поле `zone`, а не новый список `sectors`: прежние клиенты читают `zone` как раньше.
- Области — два отдельных многоугольника. Сервер не проверяет, что они касаются и не пересекаются.
- Правка настроек сбрасывает счёт к `indoorStart`, а не к 0, как пишет документация Axxon One (lexiro 569925): начальное число — то, от которого идёт счёт.
- Размер человека (минимальная и максимальная высота) в правку не вошёл: у вида `det` уже есть `humanSize` и `objectSize`.
