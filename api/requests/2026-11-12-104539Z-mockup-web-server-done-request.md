## Что проверить

1. **Профиль `vms.webserver/1`** у вида `server`. Свойство `webServer` (`WebServerSettings`): `enabled`, `httpPort`, `httpsPort`, `urlPrefix`, `cors`, `recompress`, `rtspPort`, `rtspHttpPort`. Поля нет — умолчание, как в Axxon One (80, 443, «/», 554, 8554). Правка — JSON Merge Patch по полям.
2. **Проверки портов.** Порты 1–65535; четыре порта разные и вне `status.observed.webReservedPorts` (порты видео для браузера, 9001 и по одному на ядро). Иначе — `422 PORT_TAKEN`, `field` — указатель на порт, `params.port` и `params.other`. В операции порты сверяются с итогом всех её шагов по этому серверу: обмен портами HTTP и HTTPS двумя шагами проходит.
3. **Сертификат.** `status.observed.webCertificate` (`WebCertificate`, только чтение; `null` — только HTTP). Команда `webcert.set` загружает сертификат и закрытый ключ PEM, `check: true` только проверяет пару и отдаёт сведения. Команда `webcert.remove` убирает сертификат. Отказы — `CERTIFICATE_INVALID`, `CERTIFICATE_EXPIRED`, `KEY_MISMATCH` с `field` у параметра. Право — `admin`.
4. **Ключ нигде не отдаётся.** Ни в объекте, ни в итоге команды, ни в журнале аудита, ни в операциях, ни в правилах. Параметр `privateKey` — `writeOnly`.
5. **RTSP.** Кроме портов, в контракте для RTSP ничего нового нет: клиент RTSP входит под пользователем консоли и получает видео по его правам. Учётки потоков — отдельный запрос (выше).

## Сверх запросов

Решения, которые мы приняли сами. Владелец может их отклонить:

- **`ActionDescriptor.direct`** — новое необязательное поле описания команды. `true` — команду дают только прямым вызовом `POST /units/{uid}/actions/{id}`. Шаг операции с такой командой — `422 NOT_SUPPORTED`, `field: /items/{i}/action`, `params.reason: direct`. Правило с таким шагом, включённое или выключенное, — `422 NOT_SUPPORTED`, `field: steps`, `params.reason: direct`. Причина: сервер хранит шаги операций и правила и отдаёт их в `GET /operations` и `GET /rules`, а `webcert.set` несёт закрытый ключ. Так сейчас только у `webcert.set`.
- **Сертификат — командой, а не свойством.** Ключ — секрет, а свойство объекта сервер отдаёт в ответах. Поэтому консоль отправляет сертификат отдельным запросом до операции, и «Отменить» после применения его не вернёт.
- **Четыре новых кода ошибок** (`PORT_TAKEN`, `CERTIFICATE_INVALID`, `CERTIFICATE_EXPIRED`, `KEY_MISMATCH`). Они приходят только в ответах на новые запросы: свойство `webServer` и команда `webcert.set`.
- **Хуки профилей получили итог операции.** `beforeSet` хука видит поздние шаги той же операции по этому объекту (`ctx.planSteps`), а `ctx.secret` хранит секрет вне объекта. Это внутреннее устройство встроенного сервера, в контракт не входит.
- **Стенд.** Встроенный сервер X.509 не разбирает. Сведения он берёт из заголовка `openssl x509 -text` перед блоком PEM; ключ стенда со словом `mismatch` вне блока — «ключ не подходит». Блок `EC PARAMETERS` перед ключом EC он пропускает.

## Чего пока нет

- **Сверки пары по-настоящему.** Её делает бэкенд: стенд только имитирует её.
- **Пути к файлам Axxon One.** Axxon One (`HttpServerConfig`) знает только пути `CertificateFile` и `PrivateKeyFile`: бэкенд сам кладёт присланный PEM в файлы, которые служба может читать, и прописывает пути (`api/BACKEND.md`).
- **Шаг `check_perf` «поиск в дереве «Кластер»»** не проходит предел и на этой правке (486 мс), и на коде до неё (499 мс). Это известный шаг из `api/TESTS.md`.

## Что сломается у тех, кто уже работает по контракту

Ничего не снято. Бэкенд, который не объявил `vms.webserver/1` у вида сервера, проходит те же тесты, что и с 0.10.0, а консоль не показывает вкладку «Веб-сервер».

## Что решить владельцу

- Принять имена полей и команд или назвать свои. Тогда мы поправим `index.html` и тесты.
- Принять поле `direct` или предложить другой способ не хранить секрет в шагах операций и правил.
