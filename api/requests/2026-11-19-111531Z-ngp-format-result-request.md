# Запрос от команды ngp: «Том отформатирован», хотя форматирование не выполнено

2026-11-19 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

При ручном прогоне WebUI поверх нашего бэкенда (прототип 1.3, поддельный NGP) форматирование тома на сервере без связи закончилось отказом. При этом WebUI показал уведомление «Том отформатирован». Пользователь уверен, что данные стёрты, хотя на диске ничего не изменилось.

Как воспроизвести на наборе `one-domain`:

1. «Хранилища» → «Склады/Сервер — КПП» → «Хранилище — КПП» → том «D:» (`mode: part`). Сервер этого тома в наборе без связи.
2. «Форматировать…» → «Форматировать».
3. `POST /units/{uid}/actions/format` отвечает `202`, операция завершается `fail` с кодом `SERVER_OFFLINE`. WebUI показывает «Том отформатирован».

Почему так:

* `formatVolume` (`index.html:35865-35872`) после ответа на команду не смотрит итог операции. Он кладёт том в `volFormatting` и сразу перечитывает его `GET /units/{uid}`.
* `hwApplyVolume` показывает «Том отформатирован», как только том в `volFormatting` пришёл в состоянии `ready` (`index.html:6323`).
* Том, который сервер не форматировал, остаётся в `ready`. Первое же чтение после команды WebUI принимает за конец форматирования.

Ответ на команду — операция (`unitAction`, `index.html:5222`), но её итог WebUI не проверяет.

## Пункты

1. **Итог по операции.** Предлагаем ждать итог операции команды `format`, как WebUI уже делает для отката (`opFollow`, `index.html:39551`). При `fail` убирать том из `volFormatting` и показывать причину, например «Сервер без связи». «Том отформатирован» — только при успехе операции.
2. **Состояние `ready` сразу после команды — не итог.** Если итог берётся из состояния тома, считать форматирование законченным только после перехода `format` → `ready`, а не по первому `ready` после команды.
