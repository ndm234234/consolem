# Запрос от команды mockup: режим записи `motion` — «По событию», как «Нет» в Axxon One

2026-11-10 · коммит контракта `534c115` (0.6.0) · от команды mockup, для владельца контракта

Кому: владелец контракта

**Статус: новый**

## Зачем

Пользователь (Maxim Kabenin) попросил переделать режим записи «По детектору». Причина: у камеры бывает несколько детекторов, и выбор «какой детектор пишет» на вкладке «Архив» путает. Пользователь хочет режимы как в Axxon One:

- **«Всегда»** — постоянная запись.
- **«По событию»** — камера привязана к хранилищу, но сама не пишет. Запись запускает правило автоматизации (действие «Записывать») или оператор. Если для камеры нет такого правила, интерфейс предупреждает и предлагает создать правило.
- **«По расписанию»** — запись внутри выбранного расписания. Расписание выбирают в той же строке, что и режим.

Так устроен Axxon One:

- Список «Постоянная запись» содержит «Нет» (`CameraRecordMode.OnDemand`), «Всегда» (`Permanently`) и все расписания (time zones). Источник — `ONE/axxonnext.ui`, `ArchiveTypeDescriptor.initRecordPeriodValues`.
- «Нет» значит, что поток пишется в архив, только когда оператор поднимает тревогу или срабатывает автоматическое правило. Источник — документация Axxon One 3.0, «Configuration of recording to an archive for a camera».
- Выбор расписания создаёт автоматическое правило записи в этом расписании. Источник — `DomainServiceProxy.SetWriteArchiveTimeZoneAutomaticRuleAsync`.

В прототипе 46 (`index_46_ponyatnye-knopki-kamery.html`) это уже сделано в интерфейсе:
- значение `motion` показано как «По событию»;
- карточки «Детекторы, запускающие запись» больше нет;
- консоль больше не заполняет `recordDetectorIds`.

## Пункты

1. **Новый смысл `motion`.** В `RecordMode` (`api/openapi.json`) и в таблице полей `api/BACKEND.md` описать `motion` так: «По событию: камера привязана к хранилищу и пишет, только когда правило автоматизации с действием `record` или оператор запускает запись». Сейчас там написано «пишет по детекторам из `recordDetectorIds`».
2. **`recordDetectorIds` — устарело.** Пометить поле как устаревшее (`deprecated: true`) или снять его. Поле больше не задаёт запись: при `motion` сервер не пишет по детекторам камеры, если правило этого не просит. Если поле остаётся, сервер принимает его и не меняет по нему запись.
3. **Состояние записи.** Для `motion` без включённого правила записи по камере сервер может отдавать `recordState: "waiting"` с причиной (`recordReason`), например «Нет правила, которое запускает запись». Это необязательно: интерфейс считает это сам по `GET /rules`. Но тогда предупреждение увидят и другие клиенты.
4. **Имя значения.** Если владелец хочет, чтобы имя совпадало со смыслом, можно ввести `event` и считать `motion` устаревшим синонимом. Тогда это ломающее изменение (раздел ниже). Мы просим вариант с наименьшей ломкой: оставить `motion` и поменять описание.
5. **Тест:** в `tests/api-*.js` проверить, что камера с `recordMode: "motion"` и без `recordDetectorIds` проходит `PATCH` без `422`.

## Что сломается у тех, кто уже работает по контракту

- **Клиенты, которые пишут `recordDetectorIds`.** Поле перестанет влиять на запись. Если раньше камера писала по этим детекторам без правила, теперь для такой записи нужно правило «детектор → Записывать». Владелец может перенести такие камеры: для каждой камеры с `recordDetectorIds` создать правило записи по этим детекторам.
- **Пункт 4, если выберут `event`:** клиенты, которые сравнивают `recordMode === "motion"`, перестанут узнавать режим.
- Режим «По расписанию» (`sched` и `recordScheduleId`) не меняется. Интерфейс только перенёс выбор расписания в строку хранилища.
