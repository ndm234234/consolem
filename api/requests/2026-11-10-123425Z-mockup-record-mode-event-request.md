# Запрос от команды mockup: режим записи «По движению», как On motion в Axxon One

Кому: владелец контракта

**Статус: новый**

## Зачем

Пользователь (Maxim Kabenin) попросил переделать режим записи «По детектору». У камеры бывает несколько детекторов, и вопрос «какой детектор пишет» в карточке камеры и в мастере добавления устройств путает и добавляет шаги. Ресёрч (Axxon One, Milestone, Genetec, HikCentral, Meraki; claude.ai/artifact/HBFucHCKMMv6QiuroSXwqf) показал: никто не спрашивает, какой детектор создать, в момент выбора режима. Axxon One в режиме **On motion** сам создаёт детектор движения (встроенный, если модель его умеет, иначе серверный) и правило записи. Источник — документация Axxon One 3.0, «Configure IP device settings»; код `ONE/axxonnext.ui`: `CameraRecordMode.ByMotion` / `ByEmbeddedMotion`, `MotionDetectorSetup`. На новых серверах клиент ставит только режим, детектор создаёт сервер.

Режим «По правилам» (камера пишет только по правилу, как «Нет» / `OnDemand` в Axxon One) пользователь отклонил: привязывать камеру к правилу, которого ещё нет, нелогично, а привязка к существующему правилу — редкая операция. Правило с действием `record` по-прежнему добавляет запись к любому режиму.

В прототипе 46 (`index_46_ponyatnye-knopki-kamery.html`) список режимов везде один — строка хранилища камеры, карточка регистратора, мастер добавления, импорт CSV: «Всегда», «По движению», «По расписанию», «Репликация». Пока сервер этого не умеет, «По движению» в прототипе — три изменения одним «Применить»:

| Что | Как в прототипе |
|---|---|
| режим | `recordMode: "motion"` |
| детектор | шаг `create` детектора движения в той же операции: встроенный, если камера объявила вид `motion` в `detectorOptions`, иначе серверный; `recordDetectorIds` — номер детектора, а если детектор создаётся той же операцией — поля нет (все детекторы камеры) |
| правило | отдельный `POST /rules` до операции: событие `det` вида `motion` на камере, действие `record` с `ref: "$src"`, `dur: "event"`, `after: 10`. Событие стоит на камере, а не на детекторе, поэтому правилу не нужно ждать детектор. Мастер добавления создаёт одно правило на все камеры плана в этом режиме |

## Пункты

1. **`motion` = «По движению».** Описать в `RecordMode` и в `api/BACKEND.md`: камера пишет, пока детектор движения видит движение. Если у камеры нет детектора движения или правила, которое запускает запись по нему, сервер создаёт их сам — детектор встроенный, если камера объявила вид `motion` в `detectorOptions`, иначе серверный на втором потоке; правило «движение — запись» на эту камеру — как Axxon One по режиму On motion. Это закрывает массовое добавление и импорт CSV: клиент ставит режим и не создаёт детекторы и правила по одному.
2. **Одна операция вместо двух запросов.** Сейчас правило создаётся отдельным `POST /rules`: если операция с режимом и детектором откажет, правило останется. Нужно одно из двух: шаг `create` правила в `/operations`, или пункт 1 (тогда клиенту правило создавать не нужно).
3. **Ссылка на детектор, который создаётся той же операцией.** Сейчас `/operations` не может поставить в `recordDetectorIds` номер детектора из шага `create` той же операции: сервер отвечает `422 VALIDATION_FAILED`. Нужно одно из двух: временный номер шага (`ref`) в `create` и ссылка на него в других шагах, или пункт 1 (тогда клиенту ссылка не нужна).
4. **Состояние записи.** Для `motion` без включённого правила записи по движению сервер может отдавать `recordState: "waiting"` с `recordReason` «Нет правила, которое запускает запись по движению». Необязательно: интерфейс считает это сам по `GET /rules`.
5. **Тесты:** после пункта 1 — `PATCH` камеры с `recordMode: "motion"` без детектора движения создаёт детектор и правило, повторный `PATCH` не создаёт вторые.

## Что сломается у тех, кто уже работает по контракту

- Пункт 1 — сервер начнёт создавать детекторы и правила сам. Клиент, который создаёт их и ставит `motion` в одной операции, получит дубли, если сервер не проверит, что детектор и правило уже есть.
- Пункты 2 и 3 — новый шаг или поле операции, старые клиенты их не шлют; ломки нет.
- Режим «По расписанию» (`sched`, `recordScheduleId`) не меняется.
