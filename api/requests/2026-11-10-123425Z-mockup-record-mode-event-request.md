# Запрос от команды mockup: режимы записи «По движению» и «По правилам», как On motion и «Нет» в Axxon One

2026-11-10 · коммит контракта `534c115` (0.6.0) · от команды mockup, для владельца контракта

Кому: владелец контракта

**Статус: новый**

## Зачем

Пользователь (Maxim Kabenin) попросил переделать режим записи «По детектору». У камеры бывает несколько детекторов, и вопрос «какой детектор пишет» в карточке камеры и в мастере добавления устройств путает и добавляет шаги. Ресёрч (Axxon One, Milestone, Genetec, HikCentral, Meraki; claude.ai/artifact/HBFucHCKMMv6QiuroSXwqf) показал: никто не спрашивает, какой детектор создать, в момент выбора режима, а Axxon One разделяет два случая:

- **On motion** — система сама создаёт детектор движения (встроенный, если модель его умеет, иначе серверный) и правило записи. Источник — документация Axxon One 3.0, «Configure IP device settings»; код `ONE/axxonnext.ui`: `CameraRecordMode.ByMotion` / `ByEmbeddedMotion`, `MotionDetectorSetup`. На новых серверах клиент ставит только режим, детектор создаёт сервер.
- **«Нет» (`CameraRecordMode.OnDemand`)** — камера привязана к архиву и пишет, только когда правило или оператор запускает запись. Источник — документация Axxon One 3.0, «Configuration of recording to an archive for a camera».

В прототипе 46 (`index_46_ponyatnye-knopki-kamery.html`) список режимов везде один — строка хранилища камеры, карточка регистратора, мастер добавления, импорт CSV: «Всегда», «По движению», «По правилам», «По расписанию», «Репликация». Пока своего значения нет, прототип выражает оба новых режима через текущий контракт:

| Режим в интерфейсе | `recordMode` | `recordDetectorIds` |
|---|---|---|
| «По движению» | `motion` | номер детектора движения камеры; поля нет — все детекторы камеры (так консоль делает, когда детектор создаётся той же операцией) |
| «По правилам» | `motion` | `[]` — ни один детектор не пишет, запись запускает правило автоматизации или оператор |

## Пункты

1. **Значение для «По правилам».** Ввести в `RecordMode` значение `event` (или `rules`): «камера привязана к хранилищу и пишет, только когда правило автоматизации с действием `record` или оператор запускает запись». Тогда «По правилам» не зависит от `recordDetectorIds`, и пустой список перестаёт быть особым случаем.
2. **`motion` = «По движению».** Описать в `RecordMode` и в `api/BACKEND.md`: камера пишет, пока детектор движения видит движение. Если у камеры нет детектора движения, сервер создаёт его сам — встроенный, если камера объявила вид `motion` в `detectorOptions`, иначе серверный на втором потоке — как Axxon One по режиму On motion. Это закрывает массовое добавление и импорт CSV: клиент ставит режим и не создаёт детекторы по одному.
3. **Ссылка на детектор, который создаётся той же операцией.** Сейчас `/operations` не может поставить в `recordDetectorIds` номер детектора из шага `create` той же операции: сервер отвечает `422 VALIDATION_FAILED`. Нужно одно из двух: временный номер шага (`ref`) в `create` и ссылка на него в других шагах, или пункт 2 (тогда клиенту ссылка не нужна).
4. **Режим на строку хранилища.** `recordDetectorIds` — поле камеры, а режим — у каждой строки хранилища (`recordMode` камеры и `recordMode` в строках `extraArchives`). Строки с «По движению» и «По правилам» на одной камере сейчас выразить нельзя. После пункта 1 это решается само.
5. **Состояние записи.** Для «По правилам» без включённого правила записи по камере сервер может отдавать `recordState: "waiting"` с `recordReason` «Нет правила, которое запускает запись». Необязательно: интерфейс считает это сам по `GET /rules`.
6. **Тесты:** камера с `recordMode: "motion"` и `recordDetectorIds: []` проходит `PATCH`; после пунктов 1–2 — `event` проходит `PATCH`, `motion` без детектора движения получает детектор.

## Что сломается у тех, кто уже работает по контракту

- Пункт 1 — новое значение в перечислении: клиенты, которые не знают `event`, покажут его как неизвестное.
- Пункт 2 — сервер начнёт создавать детекторы движения сам. Клиент, который создаёт детектор и ставит `motion` в одной операции, получит два детектора, если сервер не проверит, что детектор уже есть.
- Пункт 3 — новое поле в шаге операции, старые клиенты его не шлют; ломки нет.
- Режим «По расписанию» (`sched`, `recordScheduleId`) не меняется.
