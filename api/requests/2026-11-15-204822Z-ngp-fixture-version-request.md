# Запрос от команды ngp: тесты берут версию и uid потока из набора, а наблюдение потока ставят отдельным PUT

2026-11-15 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

Бэкенд поверх NGP в прототипе 1.1 объявил `patchUnit`. С этим тесты правки объекта перестали пропускаться и начали выполняться против нашего бэкенда. Часть из них падает не из-за правки: тесты берут из набора то, что бэкенд не может воспроизвести (версию объекта и uid потока), или ставят наблюдение потока запросом, который может уйти на другой экземпляр.

Версия у нас непрозрачная, как разрешил ответ на запрос w2c (`2026-10-29-161220Z-w2c-capabilities-response.md`, п. 4): `<epoch>.<n>`, где `epoch` — случайная метка записи версии в хранилище NGP. Сразу после `/test/reset` она не равна `version` из набора (`"1"`). Набор знает только встроенный сервер; NGP о нём ничего не знает.

## Пункты

1. **Версия из набора вместо версии из ответа.** Тесты сравнивают версию с `FX.devices[].version` или шлют её в `If-Match`:
   - `tests/api-hardware.js:62`, `:76` — «Устройство: пустое имя…»: все проверки 422 и 404 у нас проходят, падает последнее сравнение `GET … version` с `cam.version`;
   - `tests/api-hardware.js:128` — «Устройство: null убирает поле…»: `If-Match: "1"` даёт `412 VERSION_MISMATCH` до записи, и тест не доходит до того, что проверяет;
   - `tests/api-read.js:190`, `:197-198` — «Неподдержанные вид устройства и настройки»: `422 NOT_SUPPORTED` приходят, падает сравнение версии хранилища с `a.version`.

   Тот же приём есть и в тестах, которые у нас пока пропускаются: `tests/api-hardware.js:148`, `:177`, `:181` (операции) и `tests/api-read.js:291`.

   Просим брать версию из ответа API: `env.etag(U(id))` или `GET` перед правкой, как уже делают соседние тесты (`tests/api-hardware.js:37`, `:51`). Сравнение «версия не изменилась» — с версией, прочитанной в начале теста.

2. **uid потока из набора.** «readOnly: null в правке» (`tests/api-units.js:521-536`) выбирает объекты через `ofKind`, то есть из `FX.units` (`tests/api-units.js:20-22`). Для камеры, сервера и тома uid у нас совпадают с набором, а для потока — нет: NGP называет поток точкой доступа, и бакенд выводит uid из неё. Тест получает `GET /units/30000013-0001-4000-8000-000000000000 → 404` и дальше не идёт.

   Просим выбирать объект вида через API (`GET /units?kind=stream&limit=1`) или пропускать вид, объекта которого нет в ответе, так же, как тест уже пропускает вид без нужного свойства (`continue` в `tests/api-units.js:527`).

3. **Наблюдение потока отдельным `PUT` без проверки ответа.** `subscribeForTest` открывает `GET /stream` без списка и на `stream.hello` шлёт `PUT /stream/{clientId}/watch`, не глядя на ответ (`tests/harness.js:512-517`). Наша приёмка чередует экземпляры бэкенда на соседних запросах, как разрешает `BACKEND.md` (поток живёт на своём экземпляре, `PUT` чужому — `404`). Тогда `PUT` в половине случаев уходит на другой экземпляр, получает `404`, и поток остаётся без наблюдения. Тест не видит `entity.changed` наблюдаемой камеры, хотя бэкенд его отправил. Так падают в зависимости от порядка запросов:
   - «Устройство: переименовать — 200, версия +1, ETag, изменение в потоке» (`tests/api-hardware.js:32-46`) — проверка «в потоке — с видом объекта»;
   - «Поток: stream.hello первым…» (`tests/api-pages.js:463-493`) — тот же `PUT` из `subscribeForTest` и `PUT` в теле теста;
   - «Поток: PUT не тому экземпляру…» (`tests/api-pages.js:495-523`) — последний `PUT` ждёт `204` (`:521`).

   Просим открывать поток теста сразу со списком: `GET /stream?watch=<ids>`, как WebUI переоткрывает поток после `404` (`BACKEND.md`, «Поток»). Тест на сам `PUT watch` тогда стоит проверять ответом `PUT` и допускать `404` с переоткрытием, как допускает контракт.

4. **Версия из набора в тестах удаления и операций (добавлено 2026-11-17, прототип 1.3).** Бэкенд объявил `createUnits`, `deleteUnit`, `deleteObjects`, `moveUnit`, и тесты ниже начали выполняться. Они шлют `version` или `expectedVersions` из `FX`, а не из ответа API, как в пункте 1:
   - `tests/api-hardware.js:256` (`longPlan` — `expectedVersions` из `c.version` набора) и `:269` (`If-Match` из `cam.version`) — «Операция: пока идёт, её объекты не меняются…»: `POST /operations → 412` до проверки `BUSY`;
   - `tests/api-hardware.js:293` (`If-Match` из `folder.version`) — «Операция: папку, в которую ещё не выполненный шаг кладёт объект, удалить нельзя…»;
   - `tests/api-bulk.js:19` — «Групповое удаление: устройства, папка, том…»: `items[].version` из набора;
   - `tests/api-bulk.js:35` — «Групповое удаление: хранилище…»: `version` хранилища из набора;
   - `tests/api-domains.js:162`, `:175` — «Серверы: групповой перенос…» и «Серверы: повтор операции с тем же idempotencyKey…»: `expectedVersions` из `unalloc.version` набора.

   Тот же приём ломает строку покрытия «Каждая объявленная операция покрыта тестами»: `cancelOperation` и `retryFailedOperation` вызывают только тесты, которые падают раньше на `412`.

   Просим то же, что в пункте 1: брать версию из `GET` или из ответа `GET /units?…` перед удалением и операцией.

## Что у нас сейчас

Строки пунктов 1–3 внесены в `known_fail` манифеста приёмки 1.1, строки пункта 4 — в `known_fail` прототипа 1.3, со ссылкой на этот запрос. Поведение, которое они проверяют, покрыто нашими Go-тестами и сценариями двух экземпляров. После правки тестов мы вернём строки в обязательные.
