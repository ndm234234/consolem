# Запрос от команды mockup: репликация со встроенного хранилища камеры и NVR

**Статус: новый**

## Что мы делаем

Мы добавили в [прототип 37](../../index_37_vstroennoe-hranilishche.html) настройку репликации со встроенного хранилища: с SD-карты камеры и с диска NVR в архив сервера. Вид утверждён. Настройка есть в трёх местах:

- встроенное хранилище камеры или NVR, вкладка «Репликация»: тип репликации, хранилище для забора, состояние, «Забрать период…»;
- архив сервера, вкладка «Встроенные хранилища»: список встроенных хранилищ устройств этого сервера и тип для группы строк;
- камера: итог на вкладке «Архив», встроенное хранилище во вкладке «Периферия».

Типы «Заполнять пропуски», «По расписанию» и «Только события» в Axxon One делают макросы. Поэтому консоль ведёт одно общее правило автоматизации на каждый такой тип. Пользователь выбирает тип у хранилища, и консоль добавляет камеры в правило этого типа. Другой тип убирает камеры из правила. Если камер не осталось, консоль выключает правило.

Всё новое в прототипе — заглушка. Тип и настройки хранятся в памяти браузера. Состояние репликации консоль выдумывает по `uid`. Команду `replicate` скрипт прототипа добавляет в описание вида `camera`. Без контракта это нельзя перенести в `index.html`.

## Источники

- Axxon One: настройка репликации (Lexiro 581523), встроенное хранилище камеры (Lexiro 292033), действие макроса «Camera: Start replication» с периодами Whole period, Offline periods, Time schedule, During, Finish after (Lexiro 292462). Живого сервера Axxon мы не проверяли.
- Genetec Security Center 5.13: «Archive transfer», «Retrieve from edge», повтор Manual / Minutes / Hourly / Daily / Weekly, забор после восстановления связи, данные «All» или «Specific» с событиями.
- Milestone XProtect: забор с Edge Storage после восстановления связи, по правилу и вручную.
- Hikvision, TP-Link VIGI, Omada: ANR — забор пропусков после обрыва связи.

## Что есть в контракте сейчас

- `recordMode: replica` и `replicaFrom` камеры: камера пишет только на встроенное хранилище, сервер забирает всё. В прототипе это тип «Забирать всё».
- `replicaSource` у вида хранилища: хранилище бывает источником `replica`.
- Отдельного типа репликации, состояния репликации и команды для правил нет.

## Что нужно

Имена полей ниже — из заглушки. Владелец контракта может выбрать другие.

1. **Тип репликации встроенного хранилища.** Новое поле встроенного хранилища, например `replication`:
   - `mode`: `off`, `gaps` (после обрыва связи забрать пропущенные минуты), `all` (забирать всё, нынешний `replica`), `schedule` (забирать в заданное время), `events` (забирать фрагменты вокруг событий);
   - `archiveId`: хранилище сервера, куда сервер кладёт записи;
   - `speedLimitMbps`: предел скорости забора, `0` — без предела;
   - у NVR — `excludedCameras`: камеры регистратора, записи которых сервер не забирает.
   Зачем: сейчас контракт выражает только «Забирать всё». Нужно решить, как `mode: all` связан с `recordMode: replica` камеры.
2. **Состояние репликации, только чтение.** Например `replicationStatus`:
   - `state`: `off`, `waiting` (ждёт связи), `planned` (ждёт времени запуска), `running`, `ok`;
   - `timeLeftSec`, `lastTransferAt`, `nextTransferAt`, `bytesToday`;
   - `gaps`: список `{from, to, result}`, `result` — `queued`, `done` или `lost` (устройство перезаписало записи раньше забора).
   Образец полей — Genetec «Archive transfer status» и Axxon One «Replication time left».
3. **Забор периода вручную.** Команда встроенного хранилища, например `pull` с параметрами `from` и `to`. Сервер забирает период, даже если тип репликации его не берёт.
4. **Команда камеры `replicate` для правил.** Параметры: `period` — `offline` (пропуски, пока не было связи), `whole` (всё, чего нет в архиве), `last` (последние `minutes` минут), `event` (от начала события до его конца); `minutes`; `beforeSec`; `afterSec`; `archive` (пусто — хранилище из типа репликации). Этот пункт уточняет команду `replicate` из пункта 7 [запроса о цепочке правила](2026-11-05-130700Z-mockup-rule-chain-request.md). Там у команды только период.
5. **Правило, которое ведёт консоль.** Сейчас прототип находит общее правило типа по тексту `purpose`. Нужна явная метка, например `managedBy: {feature: "edgeReplication", mode: "gaps"}`. Тогда клиент находит своё правило и предупреждает пользователя, что консоль меняет камеры этого правила сама. Нужно также решить:
   - одно общее правило на тип во всей системе или на каждый сервер (правило исполняет один сервер, `serverId`);
   - что делает сервер, если пользователь вручную изменил камеры такого правила.
   Другой вариант: сервер сам выполняет типы `gaps`, `schedule` и `events` по пункту 1, без правил. Тогда пункт 5 не нужен, а время и события входят в пункт 1.
6. **Проверки перед репликацией.** Поля встроенного хранилища только для чтения: носитель на месте и пишет; устройство отдаёт записи по ONVIF Profile G. Прототип показывает эти две проверки.
7. **Событие «Связь восстановлена».** Правилу «Заполнять пропуски» нужно событие камеры о восстановлении связи, как «Signal restored» в Axxon One. Сейчас прототип запускает правило по событию `silent` (обрыв потока). Событие `device.restored` уже есть в пункте 3 запроса о цепочке правила.

## Что сломается у тех, кто уже работает по контракту

Все пункты добавляют новое. Если поле `replication` необязательно и его нет, консоль считает тип по `recordMode` камеры, как сейчас. Бэкенд, который объявит команды `replicate` и `pull`, должен их исполнять. Остальные бэкенды их не объявляют, и интерфейс их не предложит.

## Что заработает без правки интерфейса

Команду `replicate` интерфейс `index.html` покажет сам, как только сервер объявит её в описании вида `camera` в `/kinds`. Поля 1–3, 5 и 6 требуют переноса экранов из прототипа 37 после вашего ответа.

## Чего нет в этом запросе

Забор аудио и метаданных событий со встроенного хранилища, синхронизация часов устройства, удаление записей на устройстве после забора. Этого нет и в прототипе.
