# Запрос от команды ngp: ручной экран показывает поля ввода, когда записи нет

2026-11-15 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

Бэкенд поверх NGP объявляет `GET /kinds` в прототипе 0.2. Записи объектов в этом прототипе ещё нет: `patchUnit`, `createUnits` и `deleteUnit` в `capabilities.operations` не объявлены, они придут в прототипах 1.1 и 1.3.

Ручной экран WebUI считает поле правимым только по схеме вида. Список правимых полей строится из свойств схемы без `readOnly`, `x-immutable` и `x-transient` (`index.html:4756`). Проверка `canWrite` смотрит только на этот список (`index.html:4419-4422`) и не проверяет, объявлена ли операция `patchUnit`. Поэтому карточка камеры покажет поля ввода, а сохранение получит `404 NO_ROUTE`.

Помечать все свойства `readOnly`, пока нет записи, мы не хотим. Тогда схема вида перестанет отличать смысл поля (наблюдаемое значение) от того, что умеет бэкенд сейчас. А когда запись появится, схемы и `ETag` описаний сменятся у всех клиентов.

Пока ответа нет, мы принимаем поведение как есть и описываем его в сценарии показа.

## Пункты

1. **Правка поля зависит от операции.** Предлагаем: ручной экран считает поле правимым, только если объявлена операция записи этого вида: `patchUnit` для правки, `createUnits` для мастера, `deleteUnit` для удаления. Так же уже устроены другие разделы WebUI через `can(...)` (`index.html:4434-4438`). Если операции нет, поле показывается только для чтения.
2. **`capabilities` вида.** Уточнить в `BACKEND.md`, как `UnitKind.capabilities` (`create`, `rename`, `delete` …) связаны с `capabilities.operations`. Наше понимание: `UnitKind.capabilities` говорит, что вид умеет в принципе, а `operations` — что бэкенд умеет сейчас. Клиент берёт пересечение.
