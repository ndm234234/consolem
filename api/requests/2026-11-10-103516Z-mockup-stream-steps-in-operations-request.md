# Запрос от команды mockup: шаги потоков камеры в /operations отклоняются BUSY

2026-11-10 · коммит контракта `534c115` (0.6.0) · от команды mockup, для владельца контракта

Кому: владелец контракта

**Статус: новый**

## Зачем

Пользователь (Maxim Kabenin) попросил, чтобы в окне камеры все правки всех вкладок шли через один план: «Добавить в план» у блока, затем «Показать план» → «Применить» внизу. В прототипе 46 (`index_46_ponyatnye-knopki-kamery.html`) так и сделано. Разрешение и к/с потока, новый поток и удаление потока — тоже строки плана.

По контракту их можно отправить шагами одной операции `POST /operations`: `patch` по uid потока, `createUnit` под камерой, `delete` по uid потока (`OperationItemRequest`). Встроенный сервер такие шаги отклоняет, хотя контракт их разрешает. Поэтому прототип пока отправляет потоки отдельными запросами до операции (`PATCH /units/{uid}`, `POST /units`, `DELETE /units/{uid}`). Из-за этого у плана нет одного отката.

## Пункты

1. **`createUnit` потока под камерой в `/operations` получает `BUSY` всегда.** Шаг `{uid: <камера>, createUnit: {kind: "stream", …}}` держит камеру своей операцией. Хук вида потока `beforeCreate` (`api/profiles.js`) проверяет `ctx.lockedProblem([cam.id])` без `ctx.held`, поэтому видит блокировку своей же операции. Проверка: `POST /operations` с одним таким шагом и `wait: true` → шаг `fail`, `code: "BUSY"`, `params.targetId` — сама камера.
2. **`patch` и `delete` потока получают `BUSY`, если шаг по камере в той же операции стоит позже и ещё ждёт.** Пример: разрешение потока, затем имя камеры. Хуки `beforeSet` и `beforeDelete` → `streamDropProblem` проверяют `ctx.lockedProblem([cam.id])` без `ctx.held`. Если шаг по камере стоит раньше, шаги потока проходят.
3. **Что просим:** в хуках потока передать блокировки своей операции (`ctx.held`), как это уже сделано для томов (`ctx.lockedProblem(…, ctx.held)`). Тогда план камеры отправит потоки шагами той же операции в любом порядке, и «Отменить» после «Применить» вернёт их вместе с остальным.
4. **Тест:** в `tests/api-*.js` проверить операцию из трёх шагов: `patch` камеры (имя), `patch` потока (`res`), `createUnit` потока под камерой. Ожидается: все три шага `ok`.

## Что сломается у тех, кто уже работает по контракту

Ничего: контракт не меняется, меняется только поведение встроенного сервера в сторону контракта.

## «Сервер записи» — для сведения, не просьба

`PUT /units/{uid}/recording-target` не шаг `/operations`. Прототип отправляет его в плане тоже отдельным запросом до операции. Если владелец захочет, чтобы и он откатывался вместе с планом, нужен отдельный запрос: здесь мы его не просим.
