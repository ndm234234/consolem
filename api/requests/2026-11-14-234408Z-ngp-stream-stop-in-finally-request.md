# Запрос от команды ngp: проверки с потоком не закрывают его при отказе, и страница тестов зависает

2026-11-15 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

Бэкенд поверх NGP в прототипе 0.2 объявил `listKinds`. После этого харнесс тестов API видит виды набора и запускает проверки, которые раньше пропускал из-за `kind:camera`. Часть из них открывает поток через `ApiTest.subscribeForTest` и закрывает его вызовом `stop()` в последней строке проверки, а не в `finally`.

Если проверка падает раньше на операции, которую бэкенд ещё не объявил, `stop()` не вызывается, и `EventSource` остаётся открытым. Пример: проверка «Поток: stream.hello первым…» (`tests/api-pages.js:463`) вызывает `PATCH /units/{id}` в строке 475, получает `404 NO_ROUTE`, и до `stop()` в строке 492 выполнение не доходит.

По сети страница тестов работает в Chrome по HTTP/1.1, а там не больше шести соединений к одному хосту. В нашем прогоне на `one-domain` к проверке «Поток: PUT не тому экземпляру…» (`tests/api-pages.js:495`) было открыто шесть потоков: общий поток харнесса и пять оставленных упавшими проверками. Следующий `fetch` этой проверки ждёт свободного соединения бесконечно. Отчёт страницы не приходит, и `tools/check_stand.py` пишет «отчёт не пришёл за 900 с». Число живых потоков мы измерили счётчиком `EventSource` на копии страницы.

Скрипт `docs/dev-notes/работа/stream_stop_audit.py` в нашем репозитории перечисляет проверки с `subscribeForTest`. На коммите `564ba43` их 30 (на `590e3cc` было 27), и ни одна не закрывает поток в `finally`.

Пока ответа нет, наш запуск приёмки открывает копию `tests/api.html` с обёрткой. Обёртка запоминает потоки, которые открыла проверка, и закрывает их, когда проверка закончилась. Сами проверки и их порядок не меняются.

## Пункты

1. **Закрывать поток при любом исходе.** Предлагаем, чтобы `ApiTest.test` сам закрывал потоки, которые проверка открыла через `subscribeForTest`, когда она закончилась, успешно или с ошибкой. Тогда 30 проверок не нужно править по одной. Другой вариант — `try { … } finally { stop(); }` в каждой проверке.
2. **Отказ вместо зависания.** Предлагаем ограничить время одной проверки, например 60 с, и считать превышение отказом этой проверки. Сейчас одна зависшая проверка оставляет без отчёта весь прогон, и бэкенд не узнаёт, что прошло, а что нет.
