## Что проверить

1. **Поля потока в ответах.** `defaults` и `readConfig` возвращают у строки потока необязательные поля `codec`, `codecProfile`, `bitrateMode`, `bitrateKbps`, `quality`, `gopFrames`. Типы и значения — как у этих свойств вида `stream` (профиль `vms.stream/1` 1.2). Нет поля — значение неизвестно. Ваш бэкенд может сообщать эти значения: умолчания модели и то, что хранит камера?
2. **Параметры драйвера в `readConfig`.** Новое необязательное поле `result.properties`: имя свойства → значение. В нём только параметры с `x-dev` в схеме объекта камеры (`GET /units/{uid}/schema`). Нет свойства — камера его не сообщила. Нет поля `properties` — сервер не сообщает параметры драйвера; тогда консоль строит значения сама и помечает строки окна «заглушка». Подходит?
3. **Умолчания параметров драйвера.** `defaults` параметры драйвера не возвращает: консоль берёт умолчания из `default` в схеме объекта. Этого достаточно, или умолчания драйвера зависят от модели так, что схема их не знает?
4. **Схемы ответов** закрыты (`additionalProperties: false`), и новые поля в них объявлены. Клиент, который проверяет ответ по старой схеме (профиль 1.5), откажет на новых полях. Такой клиент у вас есть?

## Сверх запросов

- Стенд `stand.deviceConfig` теперь принимает ключ по uid камеры (параметры драйвера) и поля кодека у потока. Правка поля (`PATCH`) стирает его в стенде: сервер передал значение камере.
- Умолчания встроенного сервера: основной поток — H.264, high, VBR, 4096 кбит/с, качество 5, опорный кадр каждые 50 кадров; остальные — main и 512 кбит/с, прочее так же. Это значения стенда, а не правило.
