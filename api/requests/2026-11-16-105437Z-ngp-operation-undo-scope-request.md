# Запрос от команды ngp: общая ли стопка отката у всех пользователей

2026-11-16 · коммит контракта `564ba43` (0.35.0; ссылки пересчитаны 2026-11-20, первая редакция — `590e3cc`) · от команды ngp (бэкенд конфигуратора поверх NGP)

Кому: владелец контракта

**Статус: новый**

## Зачем

Бэкенд поверх NGP работает на каждом сервере домена и принимает запросы разных администраторов. Для `revertOperation` и `redoOperation` нам нужно знать, образуют ли их операции одну общую стопку или отдельную стопку у каждого пользователя.

Текст контракта говорит об одной «последней» операции и одной стопке (`api/openapi.json:555`, `:600`). `GET /operations` не имеет отбора по пользователю (`api/openapi.json:203-223`), а `Operation` не содержит автора или владельца (`api/openapi.json:11204-11224`). Образец сервера хранит общие `ops` и `redoStack` без деления по текущему пользователю (`api/server.js:597-615`, `:2365-2376`). Мы читаем это как общую стопку, но не нашли прямого правила о правах на чужие записи.

## Пункты

1. **Область стопки.** Подтвердить, что все пользователи, которым доступны операции над одними объектами, видят одну стопку отката и повтора. Правка пользователя B становится верхней и мешает откатить более раннюю правку пользователя A с причиной `notLast`. Так?
2. **Список и права.** Должны ли `GET /operations` и `GET /operations/{id}` показывать операции других пользователей? Может ли пользователь вызывать `revert`, `redo`, `cancel` и `retry-failed` для чужой операции, если его прав на объекты достаточно? Просим описать отказ для недоступной операции: `404 NOT_FOUND` или `403 PERMISSION_DENIED`.
3. **Тест двух пользователей.** Просим добавить сценарий с двумя `actAs`: A и B правят один объект, B видит верхнюю операцию A или свою, затем проверяются `revertible`, `redoable` и отказ `notLast`. Сейчас тесты стопки используют одного администратора (`tests/api-hardware.js:404-519`).

До ответа реализация считает стопку общей для домена, потому что ни схема, ни образец не дают пользовательского ключа для её разделения.
