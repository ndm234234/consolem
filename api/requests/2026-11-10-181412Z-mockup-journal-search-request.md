Кому: владелец контракта

**Статус: новый**

## Зачем

Пользователь (Maxim Kabenin) попросил переработать журнал событий и аудита: найти нужное событие за минимум шагов в базе на сотни тысяч записей. Утверждён прототип 51 (`index_51_zhurnal-poisk-i-fasety.html#log`). В нём:

- строка поиска в шапке: текст и условия «поле = значение» и «поле ≠ значение» (событие, объект, пользователь, категория);
- фасеты слева: у каждого значения — число событий при текущих условиях;
- гистограмма за период, протяжка по ней сужает период;
- виртуальный список и карточка события, в карточке — «Рядом»: события до и после этого, по объекту или по всему журналу.

Сейчас прототип берёт 200 000 событий из заглушки `assets/proto-journal-stub.js`: отбор, счётчики и гистограмму считает браузер. Правило макета — данные через контракт. Пользователь решил оставить заглушку в прототипе и написать этот запрос.

Что есть сейчас (по `origin/main`):

- `GET /journal`: параметры `category` (одно значение из `audit`, `alarm`, `info`), `deviceId` (одно), `from`, `to`, `source` (одно), `limit` (до 1000), `cursor` (только к старым записям). Ответ: `items`, `truncated`, `withheldCount`, `nextCursor`. Поля `total` нет, хотя у других списков (`/units`, `/access/history`) оно есть — оценка без фильтра. Страница идёт в порядке записи (новые первыми), а `from` и `to` отбирают по `occurredAt`, если оно есть, иначе по `at`.
- `deviceId` принимает uid любого объекта склада, не только устройства (`api/BACKEND.md`, раздел журнала). Совпадение не точное: встроенный сервер (`journalAbout` в `api/server.js`) берёт и записи о детях объекта, о его камере и об источниках событий.
- `JournalEvent`: `id`, `at`, `occurredAt`, `category`, `text`, `deviceId`, `cameraId`, `source`, `kind`, `fields` (`additionalProperties: true`). У самого события `additionalProperties: false`. Поля автора нет.
- Встроенный сервер (`GET /journal` в `api/server.js`) фильтрует только эти параметры: без текста и без счётчиков.
- Имена событий объектов есть: `UnitKind.events` → `EventDescriptor` (`id`, `label`, `severity` из `info`, `warning`, `error`, `critical`, `alarm`). Встроенный сервер при записи события объекта сводит `severity` к `category` (`alarm`, `critical`, `error` → `alarm`, остальное → `info`). В контракте этого правила нет. Записи набора и `POST /test/events` несут `category` как есть.
- Автор действия в контракте есть, но не в журнале: `actor` в истории прав и ячеек («логин или «система»»), `RuleVersion.by`, `ModeCurrent.by`, `Bookmark.by`, `Export.by` и другие. В наборе логин есть только в тексте записи («Вход root с 10.20.1.5»).
- Поток `/stream` отдаёт `journal.event` только тем, кто наблюдает объект (`PUT /stream/{clientId}/watch`). Записей без объекта и потока «все новые записи журнала» в контракте нет.
- Поиск `q` есть у `GET /units` (подстрока, параметр `fields` — где искать, в ответе `match`) и у `/access/history` («текст»). Встроенный сервер ищет подстроку без учёта регистра, «ё» = «е», без операторов.
- Несколько значений контракт задаёт списком через запятую: `GET /units?kind=a,b` («ИЛИ»).

## Пункты

1. **Поиск по тексту.** Параметр `q` у `GET /journal`, со своим синтаксисом, в отличие от подстроки у `/units`: слова через пробел — все должны встретиться (И), `|` — ИЛИ, слово в кавычках — точная фраза, `-слово` — без него; регистр не важен, «ё» = «е». Где искать — в `text`, имени вида события, имени объекта и авторе; можно взять соглашение `fields`, как у `/units`.
2. **Несколько значений и исключение.** Списки через запятую, как у `/units`: `category=audit,alarm`, `kind=a,b`, `deviceId=uid1,uid2`, `actor=…`. Пары `categoryNot`, `kindNot`, `deviceIdNot`, `actorNot` — скрыть такие записи. Для «по объекту» нужен и выбор: с детьми объекта (как сейчас) или точно этот объект.
3. **Автор события.** Необязательное поле `actor` в `JournalEvent` в том же виде, что в истории прав: логин или «система». У входа — адрес, например `fields.ip`, описанный в контракте. Отбор по `actor` — по п. 2. Без автора не сделать фильтр «Пользователь» и вопрос «кто менял камеру».
4. **Уровень события в отборе.** Прототипу нужны пять групп: тревоги, ошибки, аудит, информация, служебные (служебные скрыты по умолчанию). Сейчас `category` — три значения, ошибки сведены в `alarm`. Предложение: `category` остаётся для аудита, а новое необязательное поле `severity` в `JournalEvent` (из `EventDescriptor.severity`) и параметр `severity` дают тревоги, ошибки и информацию. Для служебных записей (начало и конец срабатывания детектора, запуск правила) нужно решение: новое значение `severity` или признак в каталоге событий (п. 8). Другой путь — новые значения `category`; он ломает клиентов, см. ниже.
5. **Общее число и счётчики по полям.** Необязательная операция `GET /journal/facets` с теми же параметрами, что `GET /journal`: `total` и для `category`, `severity`, `kind`, `deviceId`, `actor` — значения с числом записей. Счётчик поля считается без условия на само это поле, иначе у выбранного значения все остальные — ноль. Нужен предел числа значений (`facetLimit`) и признак, что значений больше. Система объявляет операцию в `capabilities.operations`; без неё клиент считает сам, как сейчас.
6. **Гистограмма.** Необязательная операция `GET /journal/histogram` с теми же параметрами плюс `buckets` (число столбцов): для каждого отрезка времени — число записей по уровню (п. 4). Объявление — как в п. 5.
7. **«Рядом».** События до выбранного уже можно получить: `to=<occurredAt события>&limit=N` (с `deviceId` — по объекту). Нет событий после него: порядка от старых к новым или курсора назад. Нет и якоря по id события, который решает записи с равным `occurredAt`. Предложение: параметр `around=<id события>` с `limit` и необязательное поле `prevCursor` в ответе. Нужно также сказать, по какому времени идёт порядок страницы: сейчас отбор — по `occurredAt`, порядок — по записи.
8. **Имена событий без объекта.** События объектов, в том числе сервера (`server.down`, `server.up` и другие), имеют имя в `UnitKind.events`. У событий без объекта (вход, выход, изменение настроек, синхронизация времени) каталога имён нет: в наборе их `kind` — `audit`, `alarm`, `info`. Нужен каталог, например необязательная операция `GET /journal/kinds`: `id`, `label`, уровень, признак «служебное».
9. **Объём.** Цель — 1 000 000 записей и больше: ответ `GET /journal`, `/journal/facets` и `/journal/histogram` на типовом запросе — до 1 с. Описать в `api/BACKEND.md` индексы и пределы.
10. **Тесты** `tests/api-*.js`: по одному на п. 1–3 и 5–7 на наборе `demo.json`.
11. **Новые записи в открытом журнале** (решение за вами). Сейчас экран журнала читает `/journal` один раз. Если журнал должен дописывать новые записи сам, нужен поток всех новых записей журнала, а не только об объекте, который клиент наблюдает.

## Что сломается у тех, кто уже работает по контракту

- П. 1, 2, 5–8 — новые необязательные параметры и операции. Операции система объявляет в `capabilities.operations`, клиент без них работает как сейчас. Ломки нет.
- П. 3 и вариант `severity` в п. 4 — новые необязательные поля ответа. По правилам контракта это добавление: так добавлены `Rule.whenLogic` в 0.3.0 и `ArchiveFetchResult.edgeOrdered` в 0.6.0 при `additionalProperties: false`. Ломки нет. То же — `prevCursor` в п. 7.
- Новые значения `category` (другой путь в п. 4) — ломка: новое значение в прежнем поле ответа, а контракт не говорит, что клиент пропускает незнакомое значение `category`.
- П. 9 — только требования к бэкенду.

Почти всё здесь — добавления, и mockup мог бы внести их сам, с уведомлением. Запрос написан по решению пользователя: сначала ваше решение по форме (п. 2, 4, 7, 11), затем правка.
